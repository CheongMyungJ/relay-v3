# 1부. 무엇을 했고 어디까지 왔나

## 1. 한 줄 요약

**AI 에이전트가 옛 앱(relay-v2)을 분석해 새 앱(relay-v3)의 철학을 세우고, 마일스톤 여섯(M1, M2, M2.1, M2.2, M3, M4)을 만들고 평가했다. 지금 relay-v3는 사람이 계약과 머지를 맡는 앱으로 돌고, 자동 머지는 꺼져 있으며, 자동 머지를 열 근거(실제 실적)는 아직 하나도 없다.**

- relay-v2는 Claude Code 세션으로 소프트웨어 일을 하는 데스크톱 앱이다. 분석해 보니 품질 장치와 절차의 비용이 같은 곳에 묶여 있었다.
- relay-v3는 둘을 뗀다. 사람과는 '무엇이 되면 끝인지'(계약)만 맞추고, 앱이 결과를 따로 재고, 품질의 바닥은 레포에 둔다.
- 첫 비교(M2)에서 결과의 질은 옛 앱과 비슷했지만 사람 손이 훨씬 많이 들었다. 마찰을 고친 M2.1에서는 사람 손이 줄고 결과도 나빠지지 않았다.
- 여러 Work에 걸친 품질 장치 넷(M3)은 켜도 꺼도 결과가 갈리지 않았고 비용만 늘었다. 규칙대로 하나는 기본에서 껐다.
- 그림자 실적 도구(M4)는 바르게 돌았다. 다만 사람이 AI인 평가 자료뿐이라, 자동 머지를 열지 판단할 실제 표본이 없다.
- 다음 마일스톤(M5, 좁은 조건의 자동 머지)은 relay-v3를 실제로 써서 실적을 쌓는 '자기 실행' 뒤에야 판단할 수 있다. 자기 실행은 사용자가 '나중'으로 정했다.

## 2. 무엇을 하려 했나

### 2.1 relay-v2는 무엇인가

- Electron 데스크톱 앱이다. 앱 안의 터미널에 Claude Code(코드를 고치는 AI 에이전트)를 띄우고, 옆 화면에서 일을 이끈다.
- 일 하나를 **Work**라 부른다. 요청 하나가 Work 하나이고, Work마다 따로 된 작업 폴더(git worktree)와 브랜치가 생긴다.
- 사람이 Work를 만들 때 업무 유형(버그 수정, 기능 추가, 리팩터링 등)을 고르고, 유형마다 정해진 단계와 승인을 거친다. 뒤에 '자율' 유형이 생겨 의도만 맞추고 나머지는 세션이 하게 했다.
- 자기 평가 도구(`app/eval`)가 있다. 같은 일을 relay와 맨 Claude Code CLI로 시키고, 사람 역할은 AI가 맡고, 숨긴 시험으로 결과가 맞았는지 본다(3.3절).
- 레포는 79 PR, 결정 로그 D1~D567이었고, 핵심 클래스 하나(`main/work.ts`의 WorkRunner)가 7,834줄까지 자랐다([v2-evidence.md](v2-evidence.md)).

### 2.2 무엇이 문제였나

사용자는 네 가지를 짚었다([v2-evidence.md](v2-evidence.md) 머리).

| # | 사용자의 지적 | 분석이 확인한 것 |
|---|---|---|
| C1 | 업무 유형을 사람이 골라야 한다 | 맞다. 고르게 한 근거는 측정이 아니라 추정이었다. 다만 유형의 값은 '고르기'가 아니라 '유형이 요구하는 증거의 모양'에 있었다(같은 18개 일에서 시험 점수 4.5 대 3.9) |
| C2 | 관문(승인 지점)이 위험과 상관없이 고정이다 | 대체로 맞다. 더 큰 구멍은 PR 전에 앱이 결과를 확인할 길이 없다는 것이었다. 앱은 시험을 돌리지 않았고, CI가 없으면 60초 뒤 통과로 봤다 |
| C3 | 의도만 명확하면 AI 자율이 낫다 | 절반만 맞다. 증거는 '같은 품질을 더 싸게'에 가깝다. 의도 정리는 요청이 모호할 때 값을 했다(요청 44: 자율 6/10, CLI 0/13). 사람 없는 완전 자동은 잰 적이 없었다 |
| C4 | 여러 Work를 거듭할 때 전체 품질을 지키는 장치가 부족하다 | 맞다. Work 사이를 잇는 기계적 통로는 팀 지식 하나였다. 위험한 쪽은 기능 회귀보다 구조의 흐름이었다. 정리 Work는 시키지 않으면 12번 중 0번 시작했다 |

분석 방법: relay-v2 `a99f6fd`(#79)의 코드·문서·평가 보고서를 여섯 영역으로 나눠 읽고, 영역마다 다른 검증자가 근거를 다시 열었다. 주장 102개 가운데 71개 확인, 30개 과장(고쳐 적음), 1개 반박이었다.

네 지적을 꿰는 사실 하나: **v2는 품질 장치와 비용을 같은 곳(단계)에 실었다.** 그래서 자율로 가려고 단계를 걷자 판정표, 독립 리뷰, 지식 확인도 같이 빠졌다. 세션은 지침이 없으면 스스로 리뷰하지 않았다(6번 중 0번).

### 2.3 relay-v3의 핵심 생각

철학([philosophy.md](philosophy.md) 0장)의 한 줄: **사람과는 '무엇이 되면 끝인지'만 맞춘다. 그 사이는 AI에게 맡긴다. 앱은 결과를 따로 재고, 품질의 바닥은 레포가 쥔다. 자율은 끝난 변경의 사실과 쌓인 실적으로만 넓힌다. 모든 장치는 끄는 조건을 단 가설이다.**

풀어 쓰면 이렇다.

1. **계약.** 작업 전에 사람과 합의하는 것은 계약 하나다. 계약은 완료조건 줄과 예시(입력 → 출력), 하지 않을 것, 사람만 아는 규칙이다. 줄의 종류(바뀜, 새로, 지킴, 없앰 등)가 어떤 증거가 필요한지 정한다. 유형 고르기는 없다.
2. **증거는 앱이 만든다.** 앱이 레포가 선언한 명령(`.relay/quality.json`)을 깨끗한 폴더에서 기준 커밋과 결과 커밋에 직접 돌린다. 세션이 "다 됐다"고 하는 말은 '주장'일 뿐이다. 증거는 커밋(SHA)에 붙고, 커밋이 바뀌면 낡는다.
3. **관문은 순수 함수다.** `gate(증거, 계약, 정책)`는 모델을 부르지 않고 결론(사람 머지, 자동 머지 후보, 계약 다시)을 낸다. 모델 판단(리뷰)과 실적은 결론을 엄격하게만 바꾼다.
4. **품질의 바닥은 레포에 산다.** 품질 기준, '나빠지지 않음'만 강제하는 래칫, 빚 장부가 레포 안에 있다. Work는 지나가도 레포는 남기 때문이다.
5. **장치는 자리를 벌어야 한다.** 리뷰, 래칫, 되먹임 같은 장치는 모두 '모델이 혼자 못 한다'는 가설이다. 장치마다 끄는 조건을 적고, 끄는 조건이 없으면 넣지 않는다. 넣을 때와 뺄 때 같은 입증 부담을 진다.
6. **자율은 실적으로만 넓힌다.** 자동 머지는 꺼진 채 시작하고, 먼저 '자동이었으면 머지했을 것'만 기록한다(그림자). 그 기록이 사람의 결정, 머지 뒤 30일의 결과와 맞는지 쌓인 뒤에만 연다.
7. **바닥(가설이 아님).** Work마다 따로 된 폴더와 브랜치, 되돌릴 수 없는 git 동작 막기, 외부 글은 자료로 감싸기, 세션이 스스로 계약을 승인하지 못함. 이것은 꺼 보는 실험의 대상이 아니다.

철학은 '더 잘한다'와 '사람 없는 자동'을 약속하지 않는다. 지금 증거가 받치는 것은 '같은 품질을 덜 무거운 절차로'까지라고 적었다.

### 3.2 결정과 장치를 적는 법

- **결정 로그.** 정한 것은 [design.md](design.md)에 V1~V54로 적었다. 결정마다 근거를 '측정' 또는 '가정'으로 단다. 사용자가 정한 것에는 ✅를 붙이고, 에이전트는 그것을 조용히 뒤집지 않는다.
- **장치 등록부.** [devices.md](devices.md)에 장치마다 가정, 붙는 사건, 비용, 지표, 끄는 조건, 최소 n, 상태(꺼짐 / 그림자 / 알림 / 관문 / 바닥)를 적는다. 평가 뒤 그 줄에 결과를 덧붙인다.
- **숫자 상한.** 앱 코어(`src/core`) 5,000줄, 파일 600줄. CI가 막는다. 상한을 올리는 것은 사용자 결정이라, M4에서는 코어가 4,999줄에 닿자 파일 하나를 다른 층으로 옮겼다(V45).

### 3.3 평가하는 법

평가 도구는 relay-v2의 것(`relay-v2/app/eval`, 설명은 relay-v2 `docs/eval.md`)에 relay-v3 쪽을 더해 썼다.

- **쪽(arm).** 같은 일을 시키는 방식 하나다. 예: `relay3`(새 앱), `relay3-noreview`(리뷰만 끔), `relay@auto`(v2 자율), `cli`(맨 Claude Code).
- **AI 사람 역할.** `claude -p` 세션 하나가 개발자를 맡는다. 화면(스크린샷, 글자)을 보고 누를 것을 고른다. 시나리오의 사실은 '처음부터 앎'과 '물으면 답함'으로 나뉜다. 물으면 답함은 에이전트가 물을 때만 말한다. 그래서 '의도를 물었는가'가 결과에 드러난다.
- **손 뗀 사람(hands-off).** 계약을 승인한 뒤 결과를 확인하지 않는 사람 역할 변형이다. 사람의 사후 교정 몫을 잰다.
- **숨긴 시험.** 작업하는 쪽이 볼 수 없는 시험으로 결과가 맞았는지 본다. 시나리오마다 정답 패치와 함정 패치로 시험이 제대로 짜였는지 확인한다(`check-scenario.mjs`).
- **봉인.** 결론을 내는 시나리오나 과제는 설계자가 보지 않는다. 숨긴 시험과 정답 파일의 sha256을 고정 때 적고, 결과를 낸 뒤 봉인을 풀 때 같은지 다시 잰다.
- **규약을 먼저 고정한다.** 묻는 것, 지표, 동등 한계 δ, 판정 규칙을 결과 전에 적고 고정한다(빌드 SHA와 함께). 차이의 95% 구간(bootstrap)이 ±δ 안이면 '같음', 밖이면 '다름', 걸치면 '모름'이다. 결과를 보고 규칙을 바꾸지 않는다.
- **판정 모델에 목적을 주지 않는다**(`--no-judge-purpose`). 무엇이 relay의 강점인지 모르게 한다.

### 4.1 M1: 확인 실행기와 관문 (11-04)

### 4.2 M2: 한 Work의 생애 (11-04~05)

- **만든 것.** Electron 앱(V13). 앱 안 터미널의 Claude Code 세션이 계약을 도구(`submit_contract`)로 내고, 사람이 승인하고, 세션이 마음대로 구현한다. 세션이 쉴 때·PR 때·[끝내기] 때 앱이 증거를 재고, 새 맥락의 읽기 전용 리뷰어가 따로 보고, 관문이 결론을 낸다. 자동 머지는 없고 그림자만 적는다. 시범 4회에서 본 것으로 끝내기 두 단계(V18), 기본 자동 조건 `small`(V19), 품질 기준 초안 제안(V20)을 더했다.
- **물은 것.** 리뷰가 값을 하나(Q1), v3가 v2 자율·CLI보다 나은 방향인가(Q2), 사람이 결과를 안 봐도 되나(Q3), '자동이었으면 머지'가 믿을 만한가(Q4).
- **답.** 결과의 질(숨긴 시험 통과)은 네 쪽이 비슷했다(88%, 87%, 91%, 87%). 그런데 새 앱은 사람 차례가 회당 25.7번으로 v2 자율(14.2)보다 11.5번 많았다. 사람이 손을 떼면 새 앱 79% → 52%, CLI 76% → 56%로 떨어졌다. 자동 조건을 채운 실행은 5번, 그중 2번만 맞았다.
- **장면.** 원인이 둘인 버그(14)에서 새 앱은 5번 중 4번 첫 원인만 담은 계약을 썼고, 계약·리뷰·관문 모두 그것을 못 잡았다. 계약을 기준으로 보는 확인은 계약이 빠뜨린 것을 보지 못한다.
- **사람 손이 많았던 까닭.** 대부분 원칙이 요구하지 않는 절차였다: 일을 Work 여러 개로 나눔(회당 약 2.5), 리뷰 지적을 손으로 옮김(약 1.8), 예시 자료를 손으로 베끼다 틀림(약 1.5), 리뷰 기다림(약 1.2), 끝내기 두 단계(1.0).
- **다음.** M3로 가지 않고 마찰부터 줄인다(M2.1). 리뷰는 남긴다. 사람이 결과를 보는 자리는 없애지 않는다. 자동 머지는 꺼 둔다.

### 4.3 M2.1: 평가에서 잰 마찰 줄이기 (11-05)

- **만든 것(V21~V31).** 한 요청은 한 Work(V21)이고, 원하면 단위마다 브랜치로 낸다(V22). 세션이 쉴 때 리뷰를 미리 돌린다(V23). 세션 몫의 실패와 리뷰 지적을 쉬는 세션에 직접 준다(V24). 열린 것이 없으면 [끝내기] 한 번(V25). 가벼운 구조 지적은 메모로(V26). 예시 자료는 앱이 쓴다(V27). 계약 제출 때 기준에서 예시를 확인(V28). 계약이 요청의 증상을 다 설명하게 하는 지침(V29). 리뷰어가 요청도 읽음(V30). 지난 평가 자료로 관문을 다시 도는 시험(V31).
- **물은 것.** 사람 손이 줄었나, 결과가 떨어지지 않았나, v2 자율과의 차이는, 잘못된 자동 판단이 있나. 결론은 설계 때 보지 않은 봉인 시나리오 셋에서만 냈다.
- **답.** 숨긴 시험 15/15(M2에 버그 고침만 더한 빌드 12/15, v2 자율 13/15). 사람 차례 12.9(17.0, 13.9)로 회당 4.1번 줄었다. v2 자율과의 차이는 가를 수 없을 만큼 줄었다. 토큰은 40% 줄었다. 잘못된 자동 판단 0(다만 조건을 채운 실행 3번). V28은 확인이 실제로 돈 제출이 18%라 끄는 조건(20% 아래)에 걸렸다. V30은 사전 리뷰 재생(0단계)에서 기준을 넘지 못해 메모로 내린 채 돌았다.
- **다음.** V28을 뺀다. M3로 갈지는 사용자와 정한다 → 사용자는 남은 마찰을 작게 고치는 M2.2를 먼저 하고 M3로 가기로 했다.

### 4.4 M2.2: 남은 마찰 (11-06)

- **만든 것(V32~V37).** V28을 지움(V32). 지킴 시험이 기준에서 불러지지 않으면 고칠 길을 붙임(V33). '예시와 시험 불일치'의 뜻을 좁히고 계약 예시는 값으로 씀(V34). [끝내기] 상자에서 세션에 넘기면 끝을 다시 걺(V35). 세션이 멈춘 뒤 기다림 20초 → 5초(V36). 끝낼 때 남은 메모를 끝난 Work에 보임(V37). 새 장치는 없다.

### 4.5 M3: Work 사이의 품질 (11-06)

- **만든 것(V38~V43).** 장치 넷. 지식 잇기(관련 지식 목록을 요청에 붙이고, 사람 규칙을 지식 파일로 남기게 하고, 형식을 확인, V38). 받아들인 나빠짐을 빚으로 기록(V40). 빚 목록을 다음 Work에 보여 '곁들일 정리'로 갚게 함(V41). 말로 적은 규칙을 실행되는 검사로 옮기게 함(규칙 승격, V42). 장치마다 켜고 끄는 스위치(V39).
- **물은 것.** 같은 레포에서 요청 15개를 차례로 한 뒤, 장치를 켠 쪽이 끈 쪽보다 뒤 일을 쉽게 하는가, 앞 일을 덜 깨뜨리는가, 사람이 같은 규칙을 덜 다시 말하는가. 쪽은 켬(`relay3`), 끔(`relay3-m2`), 맨 CLI(맥락만). 쪽마다 3회(사용자 결정). 열 끝에 사람 없는 기준 에이전트가 봉인 과제 셋을 한다.
- **답.** 가를 수 없었다. 봉인 과제 통과 0.67 대 0.78('모름'), 누적 숨긴 시험과 다시 말하기는 '같음'. 대신 켠 쪽이 Work당 입력 토큰 약 22%, 사람 차례 1.36번 많았다(보고만 하는 지표). 빚 기록은 4번(문턱 5), 규칙 승격은 0번(문턱 3)이라 재지 못했다. 곁들일 정리는 빚이 있던 Work 24개에서 계약에 넣은 것이 0개였는데, 빚 대부분이 갚을 수 없는 시험 빚이었다.
- **규칙대로 한 것(V44).** 지식 잇기는 기본을 껐다(코드와 스위치는 남김). 이 판정은 두 읽기(구간 끝이 δ에 딱 닿음, 한 값을 primary.md가 아니라 도구가 Work마다 남긴 값에서 셈)에 기댄다. 빚 기록·곁들일 정리·규칙 승격은 켬 그대로, 셋 다 증명되지 않음.
- **다음.** 사용자 결정: 곁들일 정리는 켠 채 두고(가), M3 전체는 규칙의 결과대로 두고(A) M4로.

### 4.6 M4: 그림자 실적 (11-06~07)

- **만든 것(V45~V54).** 자동 머지를 열려면 숫자가 필요한데, 그때까지의 그림자 기록은 숫자를 내지 못하고 표본이 조용히 빠졌다. 그래서 만든 것: 장부의 결론 줄에 채운 조건 전부와 판 칸(모델, effort, Claude Code 버전, 관문 판, 리뷰 프롬프트 판)을 적음(V46). 판이 바뀌면 실적을 처음부터 셈(V47). 끝난 Work까지 끝(머지, 닫힘, 버림)을 따라가고 'Update branch' 같은 같은 변경을 일치로 셈(V48). 조건별 실적 숫자와 화면·CLI(V49). 머지 뒤 30일 동안 되돌림과 귀속되는 main 실패를 봄(V50). 세션 커밋과 사람 커밋을 가르는 집합과 `Relay-Work` 트레일러(V51). 관문 5회 반복 측정(V52)과 지난 평가 자료로 실적 다시 세기(V53).
- **물은 것.** M4 장치가 끄는 조건에 걸리나. 관문이 같은 입력에서 갈리나. 판 칸이 다 채워지나. M5에 넘길 숫자는 무엇인가. 견주는 쪽은 없다.
- **답.** 관문의 결정론 입력은 같은 커밋에서 5번 모두 같았다(대상 0/10, relay-v3 커밋 0/3). 리뷰의 올림 유무도 5번 모두 같았다(0/10). 새로 돌린 30회에서 조건 `small`을 채운 8회는 모두 숨긴 시험을 통과했다(거짓 자동 0/8). 판 칸은 결론 줄 42개 모두 채워졌고, 트레일러는 세션 커밋 62개 모두에 붙었다. 그림자 실적 판정은 표본 13 < 30이라 '모름'이다. 실제 레포가 있어야 하는 조건 다섯은 '재지 않음'이다.
- **조심할 것.** 거짓 자동 0은 약한 0이다. 원인이 둘인 버그(14)의 두 실행은 계약에서 원인 하나를 빼고도 줄과 리뷰를 다 지났고, 자동 후보에서 막은 것은 '바뀐 줄 > 100' 하나뿐이었다. 그 줄의 대부분은 앱이 쓴 예시 자료 파일이었다(손으로 읽은 값).
- **다음.** 사용자 결정: M4는 '도구는 됨, 실제 실적은 자기 실행 뒤'로 닫는다. 자기 실행은 사람이 머지할 수 있을 때 따로 시작한다.

### 5.2 M5에 필요한 것

- **실제 표본.** 사람이 실제로 머지한 실적이 필요하다. 그래서 relay-v3로 relay-v3 자신을 개발하는 자기 실행(M4h)이 먼저다. 지금은 사용자 결정으로 '나중'이다(Q10 ✅). 실제 PR을 만들어야 하는 gh 다시 녹화(Q9)도 자기 실행과 함께 정한다.
- **미리 정한 숫자(Q2 ✅, m4-design 12절의 안).** 일치 ≥ 20(V3), 끝이 정해진 n ≥ 30, 일치율 ≥ 0.95, lift > 0, 30일 창이 닫힌 이 조건의 머지 ≥ 20에서 귀속 0·미정 0, 결정론 5회 갈림 0, 지금 관문 판의 재생 거짓 자동 0. M5 규약이 이것을 결과 전에 고정한다.
- **철학이 정한 조건(5장 단계 1).** 서버 쪽 브랜치 보호와 필수 검사 확인, 조건마다 하루 상한, 전체 끄기 스위치, 한 번에 되돌리는 단추.
- **시간.** 30일 창은 달력으로만 닫힌다. 빨라야 첫 머지 30일 뒤다.

### 5.3 열린 결정

1. **자기 실행을 언제 시작할까.** '재지 않음'인 다섯 조건과 'M4의 끝'의 남은 두 조건(머지된 내보내기의 30일 창이 닫힘, 첫 주간 기록)이 모두 이것을 기다린다([experiments/m4/report.md](experiments/m4/report.md) 7절 3).
2. **예시 자료 파일을 조건 `small`의 '바뀐 줄'에 셀까.** 지금은 센다. 빼면 14의 두 실행이 거짓 자동이었을 가능성이 크다. 보고의 권함은 지금처럼 세고, M5 설계 전에 '계약이 원인을 빼는' 꼴을 막을 길과 함께 따로 올리는 것이다(같은 절 2).
3. 철학 10장의 열린 결정 열넷 가운데 '정함'이 붙은 것은 1, 2, 5, 6이다.

### 5.4 알려진 한계

- **사람 역할이 AI다.** 설명서를 잘 따르고, 지치지 않고, [끝내기]를 매우 빨리 누른다. M4의 '일치'는 AI가 [끝내기]를 누른 비율이라 품질을 가르는 힘을 보여 주지 못한다.
- **n이 작다.** M2·M2.1은 시나리오마다 5회, M3는 쪽마다 3회, M4는 시나리오마다 5회다. 작은 차이는 '모름'이 되고, n=3의 '같음'은 약한 증거다.
- **시나리오가 적다.** M2.1 결론은 봉인 셋, 그중 차이는 한 시나리오(47)에서 났다. M3는 레포 하나, 요청 열 하나다.
- **M3는 장치 넷을 묶어 켰다.** 사용자가 정한 규모 때문이다. 어느 장치가 무엇을 했는지(비용 22%의 몫 포함) 가릴 수 없다. 둘은 거의 돌지 않았다.
- **한 모델 설정.** 에이전트, 사람 역할, 판정이 모두 같은 설정의 모델이다. 모델이 바뀌면 답이 바뀔 수 있다.
- **위험 시나리오가 없다.** 철학 8.2가 적은 함정 diff 묶음(E-risk)을 돌린 규약이나 보고는 문서에 없다.

## 6. 읽을 때 조심할 것

- **'좋아졌다'의 범위.** M2.1이 M2보다 나았다는 것은 봉인 셋 세 시나리오, 쪽마다 5회의 결과다. 결과의 질 차이는 원인이 둘인 47 하나에서 났다.
- **v2 자율과 '같다'가 아니다.** M2.1의 사람 차례 차이(−1.07)는 '모름'이다. '이번 횟수로는 가를 수 없다'는 뜻이다.
- **자동 머지가 안전하다는 증거는 없다.** M2의 G1은 2/5, M2.1은 3/3, M4는 8/8이지만 모두 10회 아래이거나 AI 사람 역할이다. M4의 0은 일부가 줄 수 덕일 수 있다.
- **사람 손은 실제로 무언가를 잡고 있다.** 손을 떼면 통과율이 20~27%포인트 떨어졌다(M2). 사람이 계약을 승인하고 결과를 보는 자리는 줄이지 않았다.

- **도구가 잘못 셀 뻔한 일이 여러 번 있었다.** 예: M3 맨 CLI 쪽은 평가 도구가 요청의 줄바꿈을 공백으로 바꿔 일부 실패가 도구 탓으로 보인다. M3 primary.md의 일부 비율은 분자·분모 차례가 거꾸로 찍혔다. 보고서들은 이런 것을 '참고'와 '손으로 읽은 값'으로 나눠 적었다.
- **비용은 일부만 안다.** 평가 도구는 사람 역할의 달러만 남긴다. 에이전트와 리뷰의 달러는 어느 평가에서도 재지 않았다.

| 예시 자료 | 계약 예시를 앱이 JSON 파일로 쓴 것(`.relay/examples/`). 수용 시험이 읽는다(V27) |
| 수용 시험 | 계약 예시를 확인하는 시험. 머지되면 평범한 레포 시험이 된다 |
| 증거 묶음 | 앱이 정해진 커밋에서 계산한 결과 모음(명령 결과, 줄 판정, 래칫, 신호, 리뷰 지적, diff). 세션은 쓰지 못한다 |
| 관문 | `gate(증거, 계약, 정책)`. 모델을 부르지 않는 순수 함수. 결론은 사람 머지, 자동 머지 후보, 계약 다시 |
| 품질 기준 | 레포의 `.relay/quality.json`. 명령, 사람 경로, 래칫, 자동 조건을 사람이 정한다 |
| 자동 조건 | diff에서 계산하는 술어. 기본 초안은 `small`(바뀐 줄 100 이하, 새 의존성·새 모듈 없음, 모든 줄이 시험으로 충족) |
| 래칫 | '나빠지지 않음'만 강제하는 지표 비교(시험 수, 파일 줄 수 등). 기준 ↔ 결과 |
| 빚 장부 | 레포의 `.relay/debt/`. 사람이 받아들인 나빠짐과 정리할 거리를 경로와 함께 적는다 |
| 곁들일 정리 | 이번 Work가 건드릴 곳의 빚을 계약에 넣어 함께 갚는 것(V41) |
| 규칙 승격 | 말로 적은 규칙을 lint나 스크립트 검사로 옮기는 것(V42) |
| 사람 경로 | 늘 사람에게 가는 파일(품질 기준, CI·lint 설정 등)과 레포가 적은 보호 경로 |
| 바닥 | 가설이 아니라서 꺼 보지 않는 막음(작업 폴더 격리, 되돌릴 수 없는 git 동작 막기 등) |
| 장치 | relay가 붙이는 리뷰, 래칫, 되먹임 같은 것. 모두 '모델이 혼자 못 한다'는 가설이고 끄는 조건이 있다 |
| 끄는 조건 | 장치를 뺄 때를 미리 적은 규칙. 최소 n이 찰 때까지는 쓰지 않는다 |
| 올림 / 메모 | 리뷰 지적 가운데 관문 사실이 되는 것(올림)과 [증거]에만 남는 것(메모, V26) |
| 되먹임 | 앱이 쉬는 세션에 실패와 지적을 파일 하나와 터미널 한 줄로 주는 것(V24) |
| 내보내기 | PR 열기·갱신이나 [끝내기]. 장부 줄과 머지는 이때만 생긴다(V23) |
| 그림자 | 자동이었으면 했을 결론을 적기만 하는 것. 자동 머지는 하지 않는다 |
| 장부(실적 장부) | 앱 로컬의 결론과 끝 기록. 그림자 실적을 센다 |
| 일치 / 거짓 자동 | 일치: 조건을 채운 변경을 사람이 고치지 않고 그대로 머지함. 거짓 자동: 조건을 채웠는데 숨긴 시험이 실패함 |
| G1 / G2 | 그림자 정밀도(조건을 채운 것 가운데 숨긴 시험 통과 비율) / 재현율(통과한 것 가운데 조건을 채운 비율) |
| lift | 조건을 채운 Work의 '그대로 머지' 비율과 채우지 못한 비교군의 비율의 차. 원인이 아니다 |
| 판 / 판 열쇠 | 실적을 나누는 단위. 모델, effort, Claude Code 버전, 관문 판, 리뷰 프롬프트 판이 같아야 같은 판이다(V47). '재는 판'은 평가 판(시나리오 묶음)을 뜻하기도 한다 |
| 트레일러 | 세션 커밋 메시지 끝에 붙는 `Relay-Work: <Work id>`. 사람 커밋과 가른다(V51) |
| 자기 실행 | relay-v3로 relay-v3 자신을 개발해 실제 실적을 쌓는 것(M4h). 사용자가 '나중'으로 정함 |
| 쪽 | 평가에서 같은 일을 시키는 방식 하나(arm). 예: relay3, cli |
| 회차 | 같은 쪽·시나리오를 되풀이한 한 번 |
| 사람 역할 | 평가에서 사람을 대신하는 AI 세션. 화면을 보고 행동을 고른다 |
| 손 뗀 사람 | 계약 승인 뒤 결과를 보지 않는 사람 역할 변형(hands-off) |
| 숨긴 시험 | 작업하는 쪽이 볼 수 없는 정답 확인 시험 |
| 봉인 | 결론을 내는 시나리오·과제를 설계자가 보지 않는 것. sha256으로 고정 때와 같은지 확인한다 |
| 봉인 과제 | M3에서 열 끝에 사람 없는 기준 에이전트가 각 쪽의 마지막 레포로 하는 과제 셋 |
| 규약 | 평가 전에 고정한 묻는 것·지표·판정 규칙. 고정 뒤에는 바꾸지 않는다 |
| δ / 같음·다름·모름 | 동등 한계. 차이의 95% 구간이 ±δ 안이면 같음, 밖이면 다름, 걸치면 모름 |
| 사람 차례 | 사람 역할이 화면에서 무언가 해야 했던 횟수(승인, 답, 기다림, 끝내기 등) |
| 재생 | 저장된 평가 자료로 관문이나 실적을 모델 호출 없이 다시 계산하는 것 |
