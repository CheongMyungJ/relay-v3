# M2 설계: 앱에서 한 Work의 생애

- 상태: M2a~M2c 구현함(2026-11-04). M2d(평가)는 진행 중
- 결정: V13(Electron 데스크톱), V1~V12. 철학은 [philosophy.md](philosophy.md) 3장의 생애다.
- 목표: 계약 → 자율 구현 → 증거 → 관문(그림자) → 머지를 앱에서 끝까지. 그리고 v2 자율·맨 CLI와 n≥5로 견준다(V14).

## 1. 한 Work의 생애 (앱 쪽)

| 차례 | 무엇이 일어나나 | 앱이 하는 일 | 사람이 하는 일 |
|---|---|---|---|
| 1 새 Work | 프로젝트와 요청 글. 일의 성격 제안(선택, V1)과 기준 브랜치 | Work 폴더와 worktree, 작업 브랜치(`relay/<짧은 이름>`)를 만든다. 프로젝트의 기본 브랜치에 품질 기준이 없으면 알리고 [초안 만들기]로 작업 트리에 초안을 쓴다(V20). 지식 잇기(V38)가 켜졌으면 기준의 `docs/knowledge/`에서 요청과 겹치는 항목의 제목과 경로(15개까지)를 request.md 끝에 붙이고, Work를 만들 때의 M3 스위치(프로젝트 설정 `m3`, `RELAY_M3`이 덮음, V39)를 work.json에 둔다. 빚 기록(M3b, V40)이 켜졌으면 실적 장부의 앞 기록(같은 기준 브랜치로 간 마지막 머지)과 기준을 견줘 기록 안 된 나빠짐(앱 밖에서 머지된 나빠진 래칫, 앞 기록 뒤 기준에 들어온 파일 크기 나빠짐. 기준의 `.relay/debt/`에 있으면 뺌)을 request.md 끝에 붙이고 [계약] 맨 위에 알린다. 곁들일 정리(M3c, V41)가 켜졌으면 기준의 `.relay/debt/` 목록(나이 순, 경로와 한 줄, 30개까지. 다른 진행 중 Work가 계약 tidy로 집은 항목은 '진행 중: 잡힘(<Work id>)')을 request.md 끝에 붙인다 | 요청을 쓴다. 초안을 검토해 기본 브랜치에 커밋한다 |
| 2 계약 초안 | 세션이 코드와 지식(V38: 관련 항목 목록을 보고 `docs/knowledge/`를 읽는다), 근처 빚(V41: 목록을 보고 이번 Work가 바꿀 경로의 빚을 계약의 `tidy`에 넣을 수 있다. 사람이 계약에서 받거나 뺀다. [계약]이 id마다 기준 장부의 종류·경로·까닭을 보인다, V43), 품질 기준을 읽고 묻는다. 요청 하나는 Work 하나다: 여러 부분(버그 둘, 모듈 셋)은 계약 줄의 단위(`unit`)로 묶고 범위와 함께 정한다(V21. 앱에 'Work로 나누기'는 없다) | 세션 하나를 PTY에 띄운다(3절). 질문은 Claude Code의 AskUserQuestion으로 터미널에서 | 답한다 |
| 3 계약 제출 | 세션이 `submit_contract` 도구를 부른다 | `parseContract`와 근거 확인. 틀리면 도구가 바로 오류를 돌려준다(되돌림 없음, V5·philosophy 원칙 2). 맞으면 예시 자료 초안을 worktree에 쓰고(V27. 제출 때 기준에서 돌리지는 않는다: V28을 V32에서 뺐다) 패널에 계약을 보이고(단위가 있으면 줄을 단위마다 묶고 전달 방식을 보인다, V21) 도구는 사람의 답을 기다린다. 승인하면 승인본을 쓰고, 승인된 계약의 전달 방식으로 내보내기를 정한다(one_branch는 작업 브랜치 하나, branch_per_unit은 단위 브랜치 `<작업 브랜치>--<단위>`마다, V22) | [승인], 또는 고칠 점을 쓰고 [보내기] |
| 4 자율 구현 | 세션이 마음대로 한다. 앱이 쓴 예시 자료를 바꾸지 않고 수용 시험과 함께 커밋한다(V27). 단위가 있으면 모두 작업 브랜치에 두고 단위마다 커밋을 따로 한다(앱은 검사하지 않는다, V21). branch_per_unit이면 기준 브랜치에서 단위 브랜치를 만들어 그 단위의 커밋과 예시 자료를 얹고, 작업 브랜치에도 모든 단위를 둔다(V22. 단위 브랜치의 변경이 작업 브랜치에 다 있는지는 앱이 본다). 브랜치 push, PR 열기(단위 브랜치마다)도 세션이 한다 | 훅으로 지켜본다. 되돌리기 어려운 git·gh만 막는다(바닥) | 지켜보거나 터미널에서 말한다 |
| 5 증거 | head는 작업 브랜치의 끝(`refs/heads/<브랜치>`)이다. worktree의 checkout이 아니다(V21): 세션이 다른 브랜치로 옮겨 커밋해도 재는 대상은 그대로다. 계기: 세션이 쉬는데 head가 바뀜(5초 몰아서, V36), PR 열기·갱신, [끝내기]. 같은 head의 계기가 겹치면 합치고, 같은 head·계약의 증거는 다시 재지 않는다. branch_per_unit이면 작업 브랜치를 계약 전체로 결정론만 재고(통합 증거), 단위 브랜치마다 계약의 조각으로 잰다(내보내기). 선언한 단위 브랜치가 없으면 '단위 브랜치 없음'이다(V22) | 엔진 `check`를 앱 밖 자식 프로세스로 돌린다. 패널에 '결론을 정한 사실 한 줄'과 펼침(branch_per_unit은 통합 증거 칸 하나와 내보내기마다 칸 하나). 곁들일 정리(V41)가 켜졌으면 펼침의 '빚'에 정리 몫과 상한, 갚은 빚, 못 갚은 빚, 건드린 곳의 빚(알림, 관문 사실이 아님). 규칙 승격(V42)이 켜졌으면 펼침의 '지식'에 말로만 남은 규칙(알림)과, 기준에서 승격된 규칙의 허용 목록이 늘었으면 그 항목(관문의 사람 머지 사실 '규칙의 허용 목록이 늚'). 곁들일 정리도 켜졌으면 rule_violation 빚을 허용 목록과 빠른 명령으로 가른다 | 본다. 건드린 곳의 빚은 끝내기 전에 세션에게 말할 수 있다 |
| 6 리뷰 (V4, V23, V30) | 세션이 쉬고 증거가 리뷰 준비(명령 pass, 못 미침·증거 없음 줄 없음)인 head(미리 리뷰, 내보내기마다 4번까지), 내보내기 후보(PR 열기·갱신, [끝내기]). 단위 브랜치로 내보내면(V22) 단위 브랜치마다 리뷰하고(리뷰어는 계약 전체와 그 내보내기가 채울 줄을 받는다) Work 브랜치(통합 증거)는 리뷰하지 않는다. 내보내기는 같은 head·계약의 끝난 리뷰를 다시 쓴다 | 새 맥락의 읽기 전용 `claude -p`로 리뷰. 리뷰어는 요청(request.md)을 인용한 자료로 받는다(V30: 요청을 보지 않은 끝난 리뷰는 사람 머지). 지적은 증거 묶음에. 관문에는 올림만 들어간다(V26: 구조는 medium 이상, 다른 갈래는 심각도와 상관없이. 나머지는 메모). 도는 사이 head나 계약이 바뀌면 멈추고 버린다. 세션이 쉬면 세션 몫의 사실(결정론 실패, 올림 가운데 예시와 시험 불일치·보안·구조)을 되먹임 파일과 터미널 한 줄로 준다(V24: 사람이 60초 안에 입력했거나 입력 칸에 글을 쓰다 두었거나, 사람 몫의 올림을 사람이 아직 넘기지 않았거나, [끝내기]가 걸렸으면 보내지 않음, Work마다 3라운드). 계약 밖 변경, 요청과 어긋남(request_gap), 메모, 바닥 신호는 사람에게만 | 본다. 사람 몫의 지적은 [세션에 넘기기] |
| 7 관문 | 증거와 리뷰가 다 모임 | `gate()`(내보내기마다). 내보내기 계기에서만 결론과 그림자를 실적 장부에 남기고 정책 머지를 한다(V23). 단위 브랜치의 내보내기는 같은 때의 통합 증거에 열린 것이 없고(단위 브랜치의 커밋이 작업 브랜치에 다 있지 않으면 그것도 열린 것) 작업 브랜치 전체 diff도 같은 조건을 채워야 자동 조건을 채운 것이다(V22) | — |

## 2. 프로세스와 모듈

```
Electron main
  ├─ store        $RELAY_HOME/projects.json, works/<id>/{work.json, request.md, contract.json, events.jsonl}
  ├─ sessions     PTY(node-pty)에서 claude 실행. 화면은 렌더러 xterm으로 흘려보냄
  ├─ hooks        127.0.0.1 HTTP. UserPromptSubmit·Stop·PreToolUse·PostToolUse·SessionEnd
  ├─ control      relay MCP 브리지가 부르는 곳: submit_contract, request_contract_change, relay_check
  ├─ evidence     계기를 받아 엔진 check를 자식 프로세스(node src/cli/main.ts check --json)로 돌림. 한 Work에 하나씩
  ├─ review       claude -p, 읽기 도구만, --json-schema(지적 목록)
  ├─ gate·ledger  core.gate, 실적 장부 $RELAY_HOME/ledger.jsonl
  ├─ record       끝까지 따라가기(M4b): 끝난 Work의 PR·PR 없이 끝남. 앱 시작, 새 Work, 6시간마다. 거울 $RELAY_HOME/mirror
  └─ gh           PR 찾기·읽기·머지 (gh CLI)
Renderer (React)
  사이드바(프로젝트 → Work) │ 터미널(xterm) │ 패널: [계약] [증거] [변경] [빚]
relay MCP 브리지 (Electron을 Node로: ELECTRON_RUN_AS_NODE)  stdio MCP ↔ control HTTP
```

- 층: `src/main`(조립, Electron), `src/renderer`, `src/preload`. main은 engine·adapters·core를 쓴다. core·adapters·engine은 Electron을 모른다(M1 층 규칙 그대로).
- 상한: 파일 600줄. v2의 WorkRunner처럼 한 클래스에 모으지 않는다. Work의 상태 기계는 순수 함수로 `src/core/work.ts`(M2에서 추가).

## 3. 세션 실행

```
claude --session-id <uuid>
       --settings <works/<id>/settings.json>      훅(HTTP), 자동 메모리 끔
       --append-system-prompt-file <works/<id>/instructions.md>
       --mcp-config <works/<id>/mcp.json>
       --dangerously-skip-permissions            (v2 D17과 같음: 권한 확인 대신 바닥의 막기)
       "<첫 프롬프트: request.md 경로와 할 일>"
```

- `instructions.md`(v3 지침, 사실만): 계약을 먼저 쓰고 `submit_contract`로 제출(그 전에 코드를 읽고 돌려 보고 시험을 쓰고 커밋해도 되며, 승인 전에는 시험 밖을 바꾸지 않음), 계약이 요청을 설명한다는 것(V29: 틀린 동작을 알리는 요청이면 알린 증상마다 원인을 근거에, 설명하지 못한 증상은 더 찾거나 묻기, 이름 붙인 대상마다 끝까지 가는 줄과 예시, 증상 곁에서 바꾸지 않는 것은 지킴 줄, 요청 영역의 동작을 비목표로 두기 전에 묻기, 승인 뒤 다른 원인을 찾으면 계약 바꾸기), 사람만 아는 사실은 묻기(질문 방식은 결정마다 확인이 첫 기본값, philosophy 원칙 1), 승인 뒤에는 방식이 자유, 예시의 입력과 출력은 시험이 그대로 쓸 수 있는 JSON 값으로 쓰고 글로만 쓸 수 있는 것은 note에 둔다는 것(V34), 예시 자료 위치와 시험 이름의 `[<계약 id>:C1.1]` 태그(V11), 바뀜·지킴 시험은 기준에서도 돌아 지킴 시험은 기준에 있는 것만 쓴다는 것(V28에서 더함. 제출 때 기준 확인의 사실은 V32에서 뺐다), 한 요청은 한 Work이고 여러 부분은 줄의 단위로 묶어 Work 브랜치에 단위마다 커밋한다는 것과 증거는 Work 브랜치의 끝에서 잰다는 것(V21), `relay_check`로 증거를 당겨 볼 수 있음, 쉬는 동안 relay가 세션 몫의 사실과 지적(주장)을 파일과 한 줄로 줄 수 있음과 사람의 답은 AskUserQuestion으로 물음(V24), 막히는 동작 목록, 쓴 것을 끝에 터미널에 말하기. 리뷰·시험 '하라'는 지시는 넣지 않는다(증거 의무는 앱이 잰다).
- 재개: 앱이 꺼지거나 세션이 끝나면 `--resume <session-id>`로 같은 대화를 연다. 기다리던 `submit_contract`는 다시 부르게 안내한다.
- 바닥의 막기(PreToolUse): v2 `core/git-guard.ts`를 옮긴다(지킬 브랜치·기준 브랜치 push, 강제 push, 원격 삭제, `gh pr merge`, `gh api` 머지). 모든 세션에 같은 두께.
- PR 코멘트·이슈 같은 바깥 글은 v2 D566처럼 인용 파일로만 두고, 쉬는 세션에 한 줄. M2에서는 넣지 않고 M3에서 장치로 등록한다(증거 되먹임과 같은 장치군).

## 6. 평가 (M2-eval, V14)

v2 평가 도구(`relay-v2/app/eval`)에 v3 쪽(`relay3`)을 더한다. 화면이 다르므로 사람 역할의 조작은 새 driver다. 시나리오·숨긴 시험·판정·보고서는 그대로 쓴다.

- 시나리오: 07, 08, 10, 14, 19, 40, 43, 44, 45. n=5.
