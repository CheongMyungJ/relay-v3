# relay-v2 사실 지도

- 대상: relay-v2 `a99f6fd`(#79)의 코드, docs/, skills/, app/eval/reports/
- 방법: 여섯 영역(유형·파이프라인, 게이팅·안전, 자율, 여러 Work의 품질, 평가, 레포 자체)으로 나눠 읽고, 영역마다 다른 검증자가 근거를 다시 열어 판정했다. 주장 102개 중 71개 확인, 30개 과장(아래에는 고친 내용으로 적음), 1개 반박.
- 쓰임: [philosophy.md](philosophy.md)의 1장 진단과 원칙의 근거. 결정 번호(Dnnn)와 보고서 이름은 relay-v2 레포 기준이다.

사용자의 문제 제기:
- C1 업무 유형을 사람이 골라야 한다.
- C2 게이팅이 유형·난이도·위험도와 상관없이 고정이다. 모델이 발전할수록 절차 강제는 성능 상한이 되고, 위험 낮은 일은 완전 자동화를 노려볼 수 있는데 구조가 막는다.
- C3 의도 정리만 명확하면 이후는 AI가 자율로 하는 편이 성능이 좋다는 증거가 많았다.
- C4 한 Work를 잘하게 하는 장치는 있지만, 여러 Work를 거듭할 때 소프트웨어 전체 품질을 꾸준히 유지시키는 장치가 부족하다.

## C1 유형 선택

- 맞다. 새 Work 창에서 사람이 고르고(기본값 없음), createWork 때 work.json에 박히며 바꿀 수 없다(D236, D423). relay MCP의 start_work도 type 필수.
- 사람이 고르게 한 근거(D236)는 측정이 아니라 "크기 분류처럼 흔들릴 수 있다"는 추정이다. 반대 자료: 일반 유형으로 시작한 의도 정리가 18회 중 17회 더 맞는 유형을 알렸다(cross-general 평가). 다만 유형이 분명한 시나리오였다.
- 유형이 의도보다 먼저 정해져야 하는 것은 구조 때문: 의도 초안의 기본 완료조건, 확인 방법 강제, 브랜치 접두사가 유형에서 나온다(D507, D509, D511).
- **유형의 값은 '고르는 일'이 아니라 '유형이 요구하는 증거의 모양'에 있었다.** 같은 18개 일을 전용 유형 vs 일반 유형: 숨긴 시험 18/18 동일, correctness 4.9 동일, 그러나 tests 점수 4.5 대 3.9, 결과 선호 전용 7 : 일반 1 : 비김 10. 차이는 버그(재현 시험)와 리팩터링(안전망)에서 컸다.
- 유형별 intake.md에는 "일의 종류마다 무엇을 물을지"라는 지식이 들어 있다(사람 추정, 바뀌는/없애는 동작 표시, 리팩터링에 섞인 동작 변경).
- 유형이 '강제'한다는 절차(재현 먼저, 안전망 먼저 커밋)는 앱의 결정론적 검사가 아니다. 산출물은 파일 존재만 검사(빈 fix.md도 통과). 프롬프트·같은 세션의 판정·LLM 리뷰가 지킨다.
- D506 뒤 유형은 데이터(폴더·칸·설정)로 정의되어 앱 코드에 유형 이름 분기 0. 비싼 것은 패러다임이 다른 auto(분기 14+17곳).

## C2 게이팅

- 대체로 맞다. 기본 유형의 실제 사람 관문은 의도 승인 + 마무리(Work 완료) 둘(기능 추가는 design 수동이라 셋). approvalMode(config, settings, node, engine, step)에 위험·크기 입력이 없고 completesWork면 무조건 manual(approval.ts:98-111). '위험도·난이도' 개념은 코드에 없다. 단계별 자동 승인 기본값(fix 등 켬)은 새 파이프라인에서 대부분 죽은 설정(D498).
- 자동 승인 조건은 증거가 아니라 에이전트 자기 보고(handoff의 open_questions, intent_deviation)와 세션 상태(D7: "앱이 결정론적으로 확인하는 검사 단계가 없으므로").
- **PR 전에는 결정론적 증거원이 없다.** 앱은 시험을 돌리지 않고(D7, D536), intent에서 테스트 명령도 뺐다(D503, D505), project.json에 품질 기준을 둘 자리가 없다(allowed_bots, merge_method, issue_log, submodules, branch_rule뿐). 증거로 판정하는 유일한 관문은 PR 머지 게이트(CI 통과, 충돌 없음, 항목 처리, head 일치, 60초 대기, pr.ts:823-880). CI가 없으면 60초 뒤 통과로 본다.
- 사람이 고르는 다이얼은 있다: Work 설정의 자동 승인 덮어쓰기(D72 "버그마다 맡기는 정도가 다를 수 있음"), code_review 끄기(D497), 진행 방식 묶음 꼼꼼히/기본/맡기기(D529), 이 단계 끝나면 멈춤(D119). 신호에서 자동으로 정해지는 것은 없다.
- **'동작 단위' 위험 축은 이미 있다:** 되돌릴 수 없는 외부 동작일수록 관문이 세다(D204 답글 게시, D518 머지·지우기는 사람, D558 지킬 브랜치 push·강제 push·원격 브랜치 삭제·gh pr merge 차단). 위험 기반 관문은 이 축을 '일 단위'로 넓히는 것으로 볼 수 있다.
- **S/M/L 크기별 경로를 해 봤다(D147~D151).** 같은 요청 08에서 L 3·M 1·S 1로 흔들렸고 결과는 같았다. D227로 없앴다. 단, S/M/L은 가운데 단계 수만 바꿨고 사람 관문(의도 승인, 리뷰, verify)은 모든 크기에 있었다(S도 승인 4번). 즉 "위험 낮으면 사람 관문을 뺀다"는 실험은 한 적 없다. 흔들림 일부는 특정 기준("환경에 달린 버그는 L") 탓. n=5. 교훈: **요청을 보고 미리 예측한 분류에 경로를 묶으면 흔들린다.**
- 완전 자동화의 통로는 일부 있다: relay MCP driver=caller면 바깥 에이전트가 의도 승인·마무리·전달까지(머지 제외). questions=recommend면 추천안으로 자동 답. 그러나 D520은 앱 안의 세션이 relay MCP로 스스로 승인하는 것을 일부러 막았다. 자율 Work는 handoff가 없어 MCP로 끝낼 길이 없다(PR 머지나 포기로만 끝남).
- 상한 있는 자동 루프의 원형: PR 대응 자동 시작·자동 승인, 사람 손 없는 라운드 상한 3(D171), 외부 글은 데이터로 감쌈·작성자 거르기(D160, D566).
- 형식 되돌림(Stop 훅으로 산출물 형식 강제)은 측정된 비용이 컸다: 단계 pty 로그의 18%에 'Stop hook error', 자식 셋이 다섯 번 되돌려짐. 이것을 없애자 시간·토큰·차례가 절반 안팎.
- 안전 차단은 샌드박스가 아니라 명령 문자열 검사(D91, 실수 방지). 스크립트·변수로 만든 명령, gh api graphql은 못 막는다. 곁·기본 세션은 push·gh를 막지 않는다. 유형마다 보호 두께가 다르다(D558 훅은 orchestrate만, guided는 deny 규칙만).
- 핵심 관문 결정(D7, D15, D17, D152, D498, D518)은 사용자 결정(✅). 바꾸면 철학 재정의다.

## C3 의도 뒤 자율

- 증거는 "더 잘한다"보다 **"같은 품질을 더 싸게"**에 가깝다. 앞 설계 자율 vs 전용 유형(01-07, 39-42): 숨긴 시험 8/10 vs 9/10, 결과 선호 자율 3 : 전용 4 : 비김 3, 대신 시간 6.3 vs 9.9분, 토큰 1129천 vs 1787천, burden 8:1.
- 단계를 6→3으로 줄인 M13 뒤에도 숨긴 시험 38/42 → 41/42, 시간 6.1→3.8분. "품질은 산출물이 만들었고, 비용은 고정된 경로가 만들었다"(autonomous-work.md 1.2).
- 세션 주도 자율(D557 뒤) vs 맨 CLI: 숨긴 시험 대부분 동일. 갈린 곳은 **크고 세부가 많은 대충 쓴 요청 44뿐**(자율·결정마다 확인 6/10, 초안 우선 1/5, CLI 0/13). 작은 요청 45·46·10은 자율 9/9, CLI 17/18. 한 배치 전체로는 자율 11/15, CLI 12/15. 요청이 사실상 명세인 39-42에서는 CLI도 9/10.
- 그래서 증거에 맞는 말은 **"요청이 모호할 때 의도 정리가 값을 한다"**. 대가는 사람 차례(자율 12~16 vs CLI 3.5~5). burden은 모든 짝에서 CLI(45:0). 결과 선호(30:12:3), confidence(34:6:5)는 자율.
- **"의도만 명확하면"이 자주 무너졌다:** (1) 의도 정리가 틀린 동작을 비목표로 숨김(07, D550로 고침), (2) 사람만 아는 반올림 규칙을 안 물음(42#2, 43#1), (3) 질문이 짚지 않은 세부 누락(44 코드 블록 class — 사람은 물은 것만 답함. 이건 사람 역할 프롬프트가 만든 행동이기도 함), (4) **의도에 있던 세부를 구현이 놓침**(44 cron 오류 필드명), (5) 조사 실패(14 두 번째 원인), (6) 승인 뒤 사람이 diff를 읽고 오류를 짚어 통과가 된 경우가 여러 번(d564 44 #2·#3·#4 round). 즉 지금 자율의 숨긴 시험 통과에는 사람의 사후 교정 몫이 들어 있고, **사람 없는 완전 자동의 성능은 잰 적이 없다.**
- 자율로 오며 결과 쪽 품질 장치가 모두 빠졌다: 판정표, verification.md, pr.md, plan.md 관문(G4 시험 더함, G5 시험 먼저 커밋), 독립 리뷰(D557, D562). **세션은 지침이 없으면 스스로 리뷰하지 않았다(6회 중 0회).** 앱 리뷰를 없앤 뒤 결과 선호 5:1 → 2:2:2(n=2라 편차일 수 있음). 이후 rough 평가에서 결과 선호는 다시 자율 11:3:1, 7:3.
- **결과 하네스(G1~G7)를 실제로 만들었다가 걷어냈다.** autonomous-work.md 3.1 "과정 하네스에서 결과 하네스로", 목표 "어떤 방식을 골랐든 결과의 품질은 앱이 같은 관문으로 검사한다". 걷어낸 까닭은 품질 가치가 아니라 (a) Stop 되돌림이라는 실행 방식의 비용·경합, (b) 자식 결과를 PR로 낼 길이 없었음(D17), (c) Claude Code가 이미 할 줄 앎, (d) 사람의 바람. G4·G5의 품질 효과는 따로 잰 적 없음.
- 자율 설계 35개 결정이 이틀(11-02~03)에 나왔고 그중 다수가 이틀 안에 뒤집혔다. 근거는 대부분 시나리오당 2회. 모든 평가의 에이전트·사람 역할·판정이 sonnet(effort medium). **"모델이 좋아질수록"은 외삽**.
- relay가 CLI를 이긴 까닭을 문서끼리 다르게 귀속했다: D559 "독립 리뷰와 판정", D557/session-driven "의도 정리", eval-findings 7절 "결과 선호 27:2의 대부분은 회귀 시험". 원 평가가 직접 보인 것은 열린 질문(08: 5/5 대 0/5)과 판정표·diff의 확신(confidence 33:0), 회귀 시험(tests 4.6 대 3.0). → 어느 장치를 남길지는 이야기 말고 뺀 변형(ablation)으로 재야 한다.
- 자율의 범위·커밋 위생은 CLI보다 낫다: 커밋된 비율 100% vs 50~87%, 기대 밖 파일 0 vs 3.2. Work마다 worktree·브랜치를 주는 구조 자체가 품질에 값을 한다.
- 자율은 버그·기능 시나리오로만 평가. 리팩터링·설계 문서·일반·여러 Work·PR 대응은 자율로 돌린 적 없다.
- 자율의 방식 선택은 토큰을 아끼는 쪽(자식 세션 대부분 안 씀)이었고 대체로 옳았다(강제로 나누면 토큰 4배). 사람의 '어떻게' 요청을 무시한 사례도 있다(앞 설계 43#2).
- 이중 구조: 자율(sessionDriven)과 고정 유형이 push 정책(D17 vs D558), 리뷰(D495 vs D562), PR(D152 vs D565), 자식(자율·Claude만)에서 갈린다. 자율을 다른 유형으로 넓히는 건 위험하다며 미뤘다.

## C4 여러 Work에 걸친 품질

- **Work 사이를 기계적으로 잇는 통로는 사실상 팀 지식(docs/knowledge) 하나.** 결정 로그·기각 목록·handoff는 Work 안에서만. 이슈 기록은 내보내기 전용(D349). 브랜치 쌓기(D428)는 git 수준. Work 초안(D404, D420)은 '다시 하기'에만.
- 지식 실험 hold-out: 사람이 규칙을 다시 말하는 횟수 PM1 −1.80 [−2.40, −1.20](효과 있음). 숨긴 시험 PM2 −0.10(한도에 딱 걸쳐 통과, 개발용은 천장). **지식은 '기억'을 이었지 '코드 품질'을 올린다는 증거는 없다.** 누적 장치가 새 부채를 만들기도 함: 옛 규칙 파일 대신 새 파일(h1 2/5), 코드 상태를 규칙처럼 적어 팀원 Work가 숨긴 시험 깸(h2 #2), "이번엔 손대지 말라"가 규칙으로 굳음(27 k8 3/5), 검토 호출이 앞 Work의 사람 규칙을 지움(E13). 고친 뒤 개발용에서 0으로 줄였으나 hold-out 재확인 없음.
- **'나중에 정리할 곳'(D437)은 아무 데도 이어지지 않는다.** 레포 밖 verification.md에만 남고, 파싱·표시·주입 없음. PR 템플릿에도 없음. 리팩터링 Work를 만드는 길은 9절 후보.
- **유지보수 Work는 사람이 끌어와야만 생긴다.** 정리하라는 말이 없으면 12회 중 0회 시작. 사이드바 알림은 효과 없어 버림(D395). 실제로 풀린 낡은 지식은 모두 일상 버그 Work의 리뷰·검증이 곁들여 고친 것(비율은 2/18, 4/18로 낮음).
- 결정론적 탐지기는 값을 했다: 지식 정리 후보(같은 anchor, 사라진 anchor, 없는 경로) 해결률 87.5% vs 에이전트만 66.7%. 지식 rule의 '아직 따르지 않는 곳'은 사람이 정한 규칙 한정의 기계 확인 부채 장부(D296).
- 구조 일관성 장치(D432 구조 맞춤·재사용, D436 리뷰의 구조·중복·유지보수성, 지식 rule 위반은 차단)는 **프롬프트 문구이고 평가한 적 없으며, 자율에서는 독립 리뷰와 함께 꺼졌다.**
- 앱에 코드베이스 건강 지표, 커버리지, 불안정 시험 장부, 복잡도 추세, 품질 래칫, 아키텍처 규칙의 기계 검사 계층이 없다. 단 relay-v2 자신은 ESLint no-restricted-imports로 core 경계를 CI에서 강제한다(개발 관행).
- **레포 시험 스위트가 사실상의 기능 회귀 래칫이다.** 비자율 유형은 Work마다 시험을 더하고 다음 Work가 다 돌린다. scale 실험 F1에서 뒤 조각이 앞 조각을 깬 경우 0(레포 테스트 명령이 앞 조각 시험을 돌려서). → **C4의 실제 위험은 기능 회귀보다 구조·유지보수성의 흐름**이고, 이것을 재는 장치·평가가 없다. 자율 유형에는 시험 요구가 없다.
- 자율에서 지식: 문서(D557)는 '지식 남기기 없음'이라 했지만 코드상 orchestrate가 마지막 단계라 context.md에 지식 남기기 지시가 들어가고, 실제로 실행당 지식 파일 0.8~2.8개를 썼다. 형식 확인·뜻 검토는 handoff가 없어 안 돈다. **검사받지 않은 지식이 쌓인다.** 자식 세션은 지식·결정 로그·이슈 기록을 받지 않는다.
- 감시 세션과 주기적 모델 호출을 두지 않는 원칙(D153, D395), CLAUDE.md·AGENTS.md를 건드리지 않는 원칙(D290) 때문에 relay가 레포의 상시 규칙이나 정기 점검을 쥘 자리가 없다.

## 평가 체계

- 평가 단위는 '요청 하나, relay vs 맨 CLI'. 시나리오 레포는 JS 9~2,569줄, Work 최대 3개. 코드 품질 판정은 diff 하나에 "읽기 쉽고 올바른가" 한 줄. 복잡도·중복·커버리지·유지보수성 지표 없음. **여러 Work에 걸친 품질은 지금 도구로 증명도 반증도 못 한다.**
- 숨긴 시험이 대부분 천장. 숨긴 시험이 구조 부채를 못 본 직접 사례(27 k8에서 팀원이 옛 코드를 우회했는데 PM2 1.00).
- Work 단위 판정은 다음 Work를 위한 투자(지식 파일)를 범위 밖 변경으로 깎았다(scope 2.8 vs 4.5).
- 강점: 숨긴 시험, 함정 패치 검증(check-scenario), 사람만 열쇠를 가진 봉인 hold-out, 결과 전에 고정한 판정 규칙, bootstrap 구간, 측정 로직의 단위 시험. 측정 오류가 결론을 뒤집을 뻔한 일이 여러 번(E1, worktree만 본 자율 40, 빌드 누락).
- 약점: n=1~5, 사람 역할·판정 모두 Claude sonnet, 사람 역할은 매번 처음 쓰는 사람(신뢰가 쌓이는 장기 사용을 못 잼), 위험(되돌리기 어려움, 보안, 데이터 이전) 시나리오 0, PR 리뷰·CI·실제 머지 충돌 없음, 자율 시리즈는 규약·hold-out 없이 결정을 바로 고침, 사람 역할 비용이 CLI의 6~10배(지식 실험 하나 $705, 46시간).
- knowledge-quality.mjs는 모든 Work 뒤 레포의 지식 상태를 정답과 견주는 '레포 상태 평가'의 원형. 코드 구조로 넓히면 장기 평가의 뼈대.

## relay-v2 레포 자체(여러 Work를 거듭한 사례)

- 79 PR. 품질을 지킨 장치: 시험 층 규칙("맞는 첫 층, 가장 낮은 층에서 한 번"), 계약 시험과 녹화본, ✅ 결정 로그(D1~D567, 560행, 409 사용자 결정), skills/check.mjs(결정과 스킬 글 대조 정규식 약 250개), push 전 명령, npm run shot·화면 확인 규칙, ESLint 경계 규칙, 봉인 hold-out 실험. **거의 모두 개발 관행에만 있고 제품 기능이 아니다.**
- 누적 복잡도: main/work.ts의 WorkRunner 클래스 하나가 7,834줄(메서드 약 281개; MVP 2,170 → 10-01 4,184 → 11-03 7,834). core/machine.ts 3,840줄. 결정 93개가 뒤 결정으로 바뀌거나 없어짐. D 번호 참조가 src 3,942곳. 옛 Work(LEGACY_PIPELINES) 분기, 안내형/세션형 분기, 'auto'가 자동 승인과 자율 유형 두 뜻. 크기·복잡도 상한과 추세 장치 없음.
- 사람이 손으로 하는 확인(감사 2단계, [실기], checks.md M41 이후)은 멈췄다. 자동화된 것(CI 결정적 시험)과 AI가 돌리는 평가만 꾸준했다. 가장 꾸준하고 무거운 품질 장치는 AI 평가·실험(보고서 32개, 11-02~03에만 17개).

## v2에서 지켜야 할 것 (여러 영역 공통)

1. 사람만 아는 규칙을 끌어내는 의도 정리(08 5/5 대 0/5, 44 6/10 대 0/13). 다만 깊이는 모호함에 맞춘다(작은 요청에선 효과 없음).
2. 요청 옆의 틀린 동작은 혼자 비목표로 돌리지 않고 묻는다(D550).
3. 일의 성질별 증거: 재현 시험(수정 전 실패·후 통과), 바꾸기 전 안전망, 새 동작 시험. 단계 순서가 아니라 요구하는 증거로.
4. 완료조건마다 실행 근거가 있는 판정표와 전체 diff(확신 33:0의 원천).
5. 되돌리기 어려운 동작만 결정론적으로 막고, 막는 축은 '되돌릴 수 있는가'.
6. 증거 기반 머지 게이트(CI, 충돌, head 일치)를 자동 관문의 틀로.
7. 회로 차단기 달린 상한 있는 자율(라운드 상한, 취소, 백그라운드 작업 중 판정 안 함).
8. 누가 승인했는지(by: human/ai/caller)와 무엇을 건너뛰었는지 기록 — 신뢰를 데이터로 맞추는 바탕.
9. 외부 글은 데이터로 감싸고 작성자를 거른다.
10. 형식 되돌림으로 과정을 강제하지 않는다(비용과 경합).
11. 예측 분류(크기·유형)에 경로를 묶지 않는다.
12. Work마다 worktree·브랜치 격리(범위·커밋 위생).
13. 지식 형식(규칙/아직 따르지 않는 곳/아직 정하지 않은 것/바뀐 이력), 한 Work의 범위 지시는 규칙이 아님, 싼 결정론적 탐지기.
14. 사람이 시작해야 하는 유지보수는 쓰이지 않는다 → 일상 흐름이나 정해진 계기에 끼운다.
15. 평가 방법: 숨긴 시험, 함정 패치, 봉인 hold-out, 결과 전 고정 규칙, 측정 도구 시험.
16. 정의를 코드 분기가 아니라 데이터로(유형 폴더). Work는 시작 때 복사한 정의로 끝까지.
