# relay-v3 설계

- 상태: M1 진행 중
- 철학과 근거: [philosophy.md](philosophy.md). 이 문서에는 정한 것과 모듈의 약속만 적는다.
- 장치 등록부: [devices.md](devices.md)

## 0. 이 문서를 고치는 규칙

1. **넣기와 빼기에 같은 입증 부담.** 결정마다 근거를 '측정' 또는 '가정'으로 적는다. 장치를 넣으면 [devices.md](devices.md)에 끄는 조건과 함께 올린다.
2. **사용자 결정(✅)은 사용자와 다시 정한다.** 에이전트가 조용히 뒤집지 않는다.
3. **숫자 상한.** 앱 코어(`src/core`) 5,000줄, 파일 600줄. CI(`scripts/limits.mjs`)가 막는다.
4. v2 결정은 `v2 D236`처럼 앞에 `v2`를 붙여 쓴다. v3 결정은 `V` 번호다.

## 2. 품질 기준 (`.relay/quality.json`)

사람이 소유하고 PR로 바꾼다. `relay init`이 package.json과 CI 설정을 읽어 초안을 쓴다.

```json
{
  "version": 1,
  "setup": { "run": "npm ci", "inputs": ["package-lock.json"], "keep": ["node_modules"] },
  "commands": {
    "fast": [
      { "id": "typecheck", "run": "npm run typecheck" },
      { "id": "lint", "run": "npm run lint" }
    ],
    "acceptance": { "id": "test", "run": "node --test --test-reporter=junit --test-reporter-destination=.relay-out/junit.xml", "junit": ".relay-out/junit.xml" },
    "full": { "ci_checks": ["ci"] }
  },
  "human_paths": ["migrations/**", "src/auth/**"],
  "guard_paths": [],
  "public_api": ["src/index.ts"],
  "test_globs": ["**/*.test.*", "**/*.spec.*", "test/**", "tests/**"],
  "examples_dir": ".relay/examples",
  "ratchets": [
    { "id": "tests", "kind": "test_count" },
    { "id": "file-size", "kind": "file_lines", "max": 600 }
  ],
  "rules": [],
  "auto": [
    { "id": "small", "max_changed_lines": 50, "no_new_dependencies": true, "no_new_modules": true, "require_all_lines_tested": true }
  ]
}
```

- `guard_paths`는 기본 목록(`.relay/quality.json`, CI 설정, lint·tsconfig·시험 러너 설정, CODEOWNERS)에 더한다. 빼지는 못한다.
- 초안(`relay init`, 앱의 [초안 만들기])의 `auto`는 늘 `small`(바뀐 줄 100 이하, 새 의존성·새 모듈 없음, 모든 줄이 시험으로 충족) 하나다(V19). 위 예시의 50은 사람이 좁힌 값이다.
- `.relay/debt/`는 사람 경로가 아니다. 앱이 형식과 anchor만 본다.
- `docs/knowledge/`(V38)도 사람 경로가 아니다. 지식 잇기가 켜졌으면 앱이 바뀐 항목의 형식과 anchor, 아직 따르지 않는 곳을 본다.
- `rules`(V42)는 지식 규칙에서 승격된 검사의 이름이다. 규칙 항목의 `check:`가 여기 있으면 승격된 규칙이고, 그 항목의 `## 아직 규칙을 따르지 않는 곳`은 검사의 허용 목록이라 줄어들기만 한다(늘면 사람 머지). 검사 자체는 레포의 lint 설정이나 빠른 명령이 돌리는 스크립트에 둔다.

## 3. 계약

Work마다 앱 저장소(`$RELAY_HOME/works/<id>/contract.json`)에 둔다. 승인된 예시는 앱이 계약에서 레포의 `examples_dir/<계약 id>.json`으로 쓰고 세션이 시험과 함께 커밋한다(V27). 수용 시험은 그 파일에서 예시를 읽는다.

- 줄: `id`(C1…), `kind`(change 바뀜 | new 새로 | keep 지킴 | remove 없앰 | observe 문서·화면 | human 사람), `text`, `grounds`(code path:line | request 인용 | knowledge id | guess), `examples`(예시 id), `check`(test | observe | human), `unit`(선택. 요청 안의 부분, V21).
- 근거 확인: code는 그 path:line이 head에 있는지(이름을 주면 그 줄에 있는지), request는 요청 글에 그 구절이 그대로 있는지, knowledge는 그 id(항목 경로, 앞의 `docs/knowledge/`와 끝의 `.md`는 없어도 됨)의 항목이 head에 있는지(지식 잇기가 켜졌을 때, V38). 확인되지 않으면 guess로 내린다.
- `hint`: 사람이 제안한 일의 성격(V1). `tidy`: 곁들일 정리로 받은 빚 id. `delivery`: 단위의 전달 방식(선택, 기본 `one_branch`. `branch_per_unit`이면 단위마다 브랜치 `<Work 브랜치>--<단위>`로 내보낸다, V21·V22).

## 6. 시험의 층

v2의 규칙을 잇는다. 맞는 첫 층에, 한 동작은 가장 낮은 층에서 한 번만 자세히.

1. 외부 없이 되면 [단위] `test/unit/`
2. 실제 git·파일·프로세스를 보면 [어댑터] `test/adapters/`
3. 여러 모듈의 시나리오면 [흐름] `test/flow/` (실제 git 임시 레포, 가짜 명령)
4. 실제 모델이 필요하면 [실제] `test/claude/` (M2부터)

## 7. 알려진 한계 (M1)

- `relay check`는 커밋을 본다. 작업 트리의 커밋하지 않은 변경은 증거에 들어가지 않는다.
- 명령이 `setsid`로 새 세션을 만들어 떨어져 나간 자손 프로세스와 Windows의 일부 자손은 시간 초과 때 끝내지 못할 수 있다. worktree 잠금이 다음 check가 그 worktree를 건드리는 것은 막는다.
- 지식 근거(knowledge)는 M1에 지식 저장소가 없어 늘 '확인하지 못함'이었다. M3a(V38)부터 지식 잇기가 켜졌으면 항목이 head에 있는지 본다(꺼졌으면 '지식 잇기가 꺼져 있어 확인하지 못함').
- 서버 보호와 실적은 M1에서 읽지 않는다(gate의 server는 null, track_record_ok는 빈 값). 리뷰도 없으므로 결론은 늘 사람 머지다(V15).
