- 상태: 제안. 사용자가 검토하기 전이다.
- 작성일: 2026-11-04
- 근거: relay-v2 `a99f6fd`(#79)의 코드·문서·평가 보고서. 여섯 영역으로 나눠 읽고, 영역마다 다른 검증자가 근거를 다시 열어 확인했다(주장 102개 중 71개 확인, 30개는 고쳐 적음, 1개 반박). 정리한 사실은 [v2-evidence.md](v2-evidence.md)에 있다. 외부 선례는 부록 B에 있다.

> **한눈에**
>
> - **없어지는 것:** 유형 고르기, 유형별 단계 파이프라인, 단계마다 승인, 형식 되돌림(Stop 훅).
> - **남는 것:** 사람과 맞추는 의도(v3에서는 '계약') 승인, 머지. v3.0에서 사람 관문은 v2 자율과 같은 둘이다.
> - **새로 생기는 것:** 앱이 레포 명령을 직접 돌려 증거를 만든다. 레포에 품질 기준과 빚 장부가 생긴다. 평가를 생성과 떼어 늘 돌린다. 자동 머지는 먼저 '했을 것'만 기록한다.
> - **약속하지 않는 것:** '더 잘한다'와 사람 없는 자동. 지금 증거가 받치는 것은 '같은 품질을 덜 무거운 절차로'까지다.
> - **틀렸다고 볼 조건:** 8.4에 결과를 보기 전에 적어 둔다. 걸리면 그 장치를 뺀다.

## 0. 한 줄로, 그리고 핵심 믿음

**한 줄로.** 사람과는 '무엇이 되면 끝인지'만 맞춘다. 그 사이는 AI에게 맡긴다. 앱은 결과를 따로 재고, 품질의 바닥은 레포가 쥔다. 자율은 끝난 변경의 사실과 쌓인 실적으로만 넓힌다. 모든 장치는 끄는 조건을 단 가설이다.

**핵심 믿음**

1. **v2는 품질 장치와 비용을 같은 곳(단계)에 실었다.** 그래서 단계를 걷으면 품질 장치도 같이 빠졌다(D557, D562). v3는 둘을 떼어 놓는다. 절차는 세션에 맡기고, 결과에 대한 요구는 레포와 앱이 쥔다.
2. **증거는 앱이 실행한다. 무엇을 볼지는 계약의 예시가 정한다.** 세션의 말은 '주장'이다. 판정을 세션의 자기 보고에 기대지 않는다.
3. **Work는 지나가고 레포는 남는다.** 여러 Work를 거듭해도 품질을 지키려면 기준과 빚이 레포 안에 살아야 한다.
4. **위험은 요청을 보고 맞히지 않는다.** 끝난 diff의 사실과 '되돌릴 수 있는가'로 계산한다.
5. **하네스는 줄어들도록 만든다.** 장치를 넣을 때와 뺄 때 같은 입증 부담을 진다. 되돌릴 수 없는 동작을 막는 바닥만은 예외다.

v2에서 relay가 CLI보다 낫다고 판정된 몫은 대부분 **회귀 시험을 더한 것**과 **판정표·diff가 준 확신**에서 나왔다. 기능 정답(숨긴 시험)은 거의 모든 쪽이 천장이었다. 그래서 무엇이 정답을 만들었는지는 아직 가르지 못했다. v3가 처음 할 일은 이것을 재는 것이다(11장 M0).

## 1. relay-v2와 견준 진단

네 문제를 꿰는 사실이 하나 있다. **v2는 '단계'에 품질과 비용을 함께 실었다.** C1~C3는 그 경로의 비용을 짚었다. C4는 경로를 걷을 때 같이 빠진 빈자리를 짚었다. 그래서 지금 v2에서는 **C3를 따를수록 C4가 약해진다.** 자율 유형이 판정표, 독립 리뷰, 지식 확인을 모두 걷어 냈기 때문이다. 네 지적은 방향이 맞다. 다만 숫자가 받치는 범위는 사용자의 말보다 좁다.

### C1. 업무 유형을 사람이 고른다 — 맞다. 다만 유형의 값은 다른 데 있었다

**맞는 것**
- 새 Work 창에서 사람이 고르고, 기본값이 없다. 만들 때 `work.json`에 박혀 바꿀 수 없다(D236 ✅, D423 ✅). relay MCP의 `start_work`도 `type`이 필수다.
- 사람이 고르게 한 근거(D236)는 측정이 아니다. '크기 분류처럼 흔들릴 수 있다'는 추정이었다. 반대로 일반 유형으로 시작한 의도 정리는 18회 중 17회 더 맞는 유형을 알렸다(D319의 근거). 다만 유형이 분명한 시나리오였다.
- 유형이 의도보다 먼저 정해지는 것은 구조 때문이다. 기본 완료조건, 확인 방법, 브랜치 접두사가 유형에서 나온다(D507, D509, D511).

**다른 것**
- 유형이 쓸모없지는 않았다. 같은 18개 일을 전용 유형과 일반 유형으로 견주면 숨긴 시험(18/18)과 correctness(4.9)는 같았다. 그러나 tests 점수는 4.5 대 3.9, 결과 선호는 전용 7 : 일반 1 : 비김 10이었다. tests 차이는 버그 10(5.0 대 3.7), 리팩터링 19(4.3 대 3.3), 기능 15(5.0 대 4.0)에서 컸다. 시나리오마다 n=3이다.
- 그러니 문제는 '고르는 일'이 아니다. **유형이 하던 일(요구하는 증거의 모양, 일의 종류별로 물을 것)이 '고르기'와 '고정 경로'에 묶여 있던 것**이 문제다.

**놓친 것**
- 유형의 '강제'는 결정론적 검사가 아니었다. 산출물은 파일이 있는지만 봤다(빈 `fix.md`도 통과, validate.ts:816). 프롬프트와 LLM 리뷰가 지켰다.
- 자율 유형에는 시험 요구가 아예 없다. 유형을 그냥 없애면 증거의 모양도 함께 사라진다.
- 비싼 것은 유형이 아니었다. D506 뒤 유형은 데이터라서 앱 코드에 bugfix·feature 같은 이름 분기가 없다. 비싼 것은 패러다임이 다른 자율이었다(`'auto'` 비교 14곳, work.ts의 sessionDriven·pushesItself 16곳).

### C2. 게이팅이 위험과 상관없이 고정이다 — 대체로 맞다. 막는 것은 '증거의 부재'다

**맞는 것**
- 관문 판정 함수에 위험이나 크기 입력이 없다. 마지막 단계면 무조건 수동이다(approval.ts:98-111, D498 ✅). 위험도·난이도라는 개념이 코드에 없다.
- 실제 사람 관문은 의도 승인과 Work 완료 둘이다(기능 추가는 설계가 기본 수동이라 셋). 단계별 자동 승인 기본값은 새 파이프라인에서 대부분 쓰이지 않는다(D498).
- 자동 승인 조건은 증거가 아니라 에이전트의 자기 보고다. handoff의 `open_questions`, `intent_deviation`과 세션 상태다(D7 ✅).
- 고정 관문이 부담의 바닥이었다. burden은 첫 평가 40짝 모두 CLI가 앞섰고(R1), 세션 자율 대 CLI도 모든 짝에서 CLI였다(45:0).

**다른 것**
- '절차 강제가 성능의 상한'은 잰 적이 없다. v2 숫자에서 강제의 대가는 품질이 아니라 부담이었다. 단계를 6개에서 3개로 줄인 M13 뒤에도 숨긴 시험은 38/42에서 41/42였다.
- 강도 다이얼은 있다. 다만 사람이 고른다. Work별 자동 승인 덮어쓰기(D72), 코드 리뷰 끄기(D497), 꼼꼼히/기본/맡기기 묶음(D529), 이 단계 끝나면 멈춤(D119)이고, 진행 중에도 바뀐다(D73).
- 관문이 줄 때의 반대 신호도 있다. M13 뒤 AI 사람 역할의 불편 42개 중 34개가 '자동 승인으로 지나가 산출물을 볼 틈이 없었다'였다.
- **동작 단위의 위험 축은 이미 있다.** 되돌릴 수 없는 동작일수록 관문이 세다. 답글 게시(D204), 머지와 지우기는 사람(D518 ✅), 지킬 브랜치 push·강제 push·원격 삭제·`gh pr merge` 차단(D558)이 그렇다. v3의 위험 비례는 이 축을 '일 단위'로 넓히는 것이다.

**놓친 것**
- **예측 분류로 경로를 고르는 방식은 이미 해 봤다(S/M/L, D147~D151).** 같은 요청 08에서 L 3·M 1·S 1로 흔들려 D227로 없앴다(n=5). 다만 S/M/L은 가운데 단계 수만 바꿨고 S도 승인이 4번이었다. '위험이 낮으면 사람을 뺀다'는 반증된 것이 아니라 해 본 적이 없다. 교훈은 '요청을 보고 미리 매긴 분류에 경로를 묶지 말라'다.
- **사람을 빼려면 그 자리를 채울 증거가 있어야 하는데, PR 전에는 결정론적 증거원이 없다.** 앱은 시험을 돌리지 않는다(D7 ✅, D536). 의도에서 시험 명령을 뺐다(D503, D505). `project.json`에는 품질 기준을 둘 칸이 없다. 증거로 판정하는 관문은 PR 머지 게이트(pr.ts:823-880) 하나이고, 그마저 체크가 없으면 60초 뒤 통과다(D176 ✅).
- 완전 자동의 통로는 일부 있다. relay MCP에서 `driver=caller`면 바깥 에이전트가 의도 승인부터 전달까지 한다(머지 빼고). 반면 앱 안 세션이 스스로 승인하는 것은 일부러 막았다(D520 ✅). 자율 Work는 handoff가 없어 MCP로 끝낼 길도 없다.
- 안전 차단은 샌드박스가 아니라 명령 문자열 검사다(D91). 스크립트로 만든 명령이나 `gh api graphql`은 못 막는다. 보호 두께도 유형마다 다르다(D558 훅은 자율 진행 task에만 붙는다).

### C3. 의도만 명확하면 자율이 낫다 — 절반만 맞다. '같은 품질을 덜 무겁게'다

**맞는 것**
- v2 전용 유형과 견주면 자율은 같은 품질을 더 싸게 냈다(D557 전 설계). 숨긴 시험 8/10 대 9/10, 결과 선호 자율 3 : 전용 4 : 비김 3, 시간 6.3분 대 9.9분, 입력 토큰 1,129천 대 1,787천, burden 8:1.
- 형식 되돌림과 마무리 단계를 걷자 07·40의 시간·토큰은 절반 안팎이 됐다. 세션의 방식 선택도 대체로 옳았다. 자식 세션을 대부분 쓰지 않았고, 강제로 나누면 토큰이 4배였다.
- Work마다 worktree와 브랜치를 준 구조가 값을 했다. 커밋된 비율 100% 대 CLI 50~87%, 기대 밖 파일 0 대 3.2.

**다른 것**
- 맨 CLI와 견주면 이야기가 다르다. 숨긴 시험은 대부분 같았다(한 배치 전체로 자율 11/15, CLI 12/15). 사람 차례는 12~16 대 3.5~5, 시간은 1.3~2배로 늘 더 비쌌다. 결과 선호(30:12:3)와 confidence(34:6:5)는 자율 쪽이다.
- 숨긴 시험이 갈린 곳은 **크고 세부가 많은 대충 쓴 요청(44) 하나**다. 결정마다 확인 6/10, 초안 우선 1/5, CLI 0/13. 작은 요청(45·46·10)은 9/9 대 17/18, 명세 같은 요청(39~42)은 CLI도 9/10이었다. 증거에 맞는 말은 '의도가 명확하면 자율이 낫다'가 아니라 **'요청이 모호할 때 의도 정리가 값을 한다'**다.
- 이 44의 차이에도 평가 설계가 섞여 있다. 사람 역할은 세부를 '물으면 답하는' 지식으로만 갖는다. 08의 5/5 대 0/5는 '물었는가'를 센 것이고, CLI는 묻지 않고도 숨긴 시험을 통과했다(E7).

**놓친 것**
- **'의도만 명확하면'이 여러 번 무너졌다.** (1) 의도 정리가 틀린 동작을 비목표로 숨겼다(07, D550로 고침). (2) 사람만 아는 반올림 규칙을 묻지 않았다(42#2, 43#1). (3) 질문이 짚지 않은 세부가 빠졌다(44 코드 블록 class). (4) **의도에 있던 세부를 구현이 놓쳤다**(44 cron 오류의 필드 이름). (5) 원인을 하나만 찾았다(14). (6) 승인 뒤 사람이 diff를 읽고 짚어 통과한 회차가 여럿이다(44 round).
- 그러니 지금 자율의 통과에는 사람의 사후 교정 몫이 들어 있다. **사람 없는 완전 자동은 잰 적이 없다.**
- 결과 쪽 품질 장치가 경로와 함께 빠졌다. 세션은 지침이 없으면 스스로 리뷰하지 않았다(0/6). 리뷰를 없앤 효과는 아직 모른다(5:1 → 2:2:2 → 뒤 빌드에서 11:3:1, 7:3, n이 작다).
- **v2는 결과 하네스(G1~G7, '어떤 방식이든 결과는 같은 관문으로')를 만들었다가 걷었다.** D557이 든 까닭은 다섯이다. 자식 결과를 PR로 낼 길이 없었다(D17, D556). 경합이 있었다(43). 형식 되돌림 비용이 컸다(40에서 다섯 번). Claude Code가 이미 할 줄 안다. 사람이 '세션이 하고 앱은 보는' 방식을 바랐다. G4·G5의 품질 효과는 따로 잰 적이 없다.
- relay가 CLI를 이긴 까닭을 문서끼리 다르게 적었다. D559는 독립 리뷰, D557은 의도 정리, eval-findings 7절은 회귀 시험이다. 어느 장치를 남길지는 이야기 말고 뺀 변형으로 재야 한다.
- 모든 증거가 sonnet(effort medium) 에이전트, AI 사람 역할, AI 판정, 시나리오당 n=1~5다. 자율 결정 35개가 이틀에 나왔고 다수가 그 안에 뒤집혔다. '모델이 발전하면'은 아직 외삽이다.

### C4. 여러 Work에 걸친 품질 장치가 부족하다 — 맞다. 위험한 쪽은 기능보다 구조다

**맞는 것**
- Work 사이를 기계로 잇는 통로는 팀 지식(docs/knowledge) 하나다. 결정 로그와 handoff는 Work 안에서만 산다. 이슈 기록은 내보내기만 한다(D349).
- 지식은 '기억'을 이었다. 사람이 규칙을 다시 말한 횟수는 −1.80 [−2.40, −1.20]이었다. 코드 품질을 올린 증거는 없다(숨긴 시험 −0.10, 한도에 걸침).
- '나중에 정리할 곳'(D437)은 레포 밖 `verification.md`에만 남고, 아무 데도 이어지지 않는다.
- 유지보수 Work는 사람이 끌어와야 생긴다. 시키지 않으면 12회 중 0회였다. 사이드바 알림은 효과가 없어 버렸다(D395).
- 구조 장치(D432 구조 맞춤, D436 리뷰의 구조·중복)는 평가한 적 없는 프롬프트 문구였다. 자율에서는 리뷰와 함께 꺼졌다. 앱에 건강 지표, 래칫, 구조 규칙 검사가 없다.
- 자율에서는 검사받지 않은 지식이 실행당 0.8~2.8개씩 쌓인다. 문서(D557)는 '지식 남기기 없음'이라 했지만 코드는 지시를 넣는다.

**다른 것**
- v2에는 레포 안에 둘 자리가 이미 있다. `.relay/types/`(D450 ✅)와 docs/knowledge다. 빠진 것은 자리가 아니라 **유형과 상관없이 늘 도는 품질 관문**이다.
- 작은 규모에서 기능 회귀는 막혔다. 시험을 더하는 유형에서는 레포 시험 스위트가 사실상의 래칫이었다(scale F1, Work 셋, 뒤 조각이 앞 조각을 깬 일 0). 빈틈은 구조와 유지보수성의 흐름이다.
- 그렇다고 '품질이 떨어진다'가 보인 것도 아니다. 평가 레포는 9~2,569줄, Work는 최대 3개라서 증명도 반증도 못 한다. 근거는 두 사례다. 27 k8에서 팀원이 옛 코드를 우회했는데도 숨긴 시험이 1.00이었다. relay-v2 자신의 `work.ts`는 2,170줄(MVP)에서 7,834줄이 됐다(WorkRunner 클래스 약 7,030줄, 메서드 281개).

**놓친 것**
- 누적 장치가 스스로 부채를 만들었다. 옛 규칙 파일 대신 새 파일을 만들었다(h1 2/5). 코드 상태를 규칙처럼 적어 팀원 Work가 숨긴 시험을 깼다(h2 #2). '이번엔 손대지 말라'가 규칙으로 굳었다(27 k8 3/5). 검토 호출이 앞 Work의 사람 규칙을 지웠다(E13). 장치를 더하면 이 일도 같이 는다.
- 싼 결정론적 탐지기가 에이전트보다 나았다(지식 정리 후보 해결률 87.5% 대 66.7%).
- Work 단위 판정은 다음 Work를 위한 투자를 범위 밖 변경으로 깎았다(scope 2.8 대 4.5). 평가 단위가 Work 하나인 한 C4는 보이지 않는다.
- relay-v2 레포를 꾸준히 지킨 것은 손으로 하는 확인이 아니었다(감사 2단계, [실기], checks.md는 멈춤). 자동화된 것(CI의 결정적 시험, ESLint 경계 규칙)과 AI가 돌리는 평가였다. 모두 개발 관행이고 제품 기능이 아니다.

## 2. v3 철학: 다섯 원칙과 하나의 바닥

### 원칙 1. 사람과는 계약만 맞춘다

**무엇인가**
- 작업 전에 사람과 합의하는 것은 **계약** 하나다. 계약은 완료조건 줄, 비목표, 사람만 아는 규칙이다. 줄마다 종류, 예시(입력 → 출력, 오류), 확인 방법, 근거를 적는다.
- **증거의 모양은 유형이 아니라 줄의 종류가 정한다.**
  - 바뀜: 결과에서 통과하고, 기준 커밋에서 단언이 실패하는 시험.
  - 새로: 결과에서 통과하는 새 동작 시험.
  - 지킴: 기준과 결과 모두에서 통과하는 안전망.
  - 없앰: 쓰는 곳이 없음을 보인다.
  - 문서·화면·사람: 관찰하거나 사람이 확인한다.
  - 버그, 기능, 리팩터링은 이 줄들을 섞은 것이다. 유형별 intake.md의 지식(사람 추정, 바뀜·없앰 표시, 리팩터링에 섞인 동작 변경)은 줄 종류별 질문 단서로 옮긴다.
- **묻는 깊이는 앱이 확인하지 못한 근거가 정한다(목표 방식. 첫 기본값은 아래 '왜'대로 결정마다 확인).** 세션은 줄마다 근거를 댄다. '코드'면 있는 path:line과 이름, '요청'이면 요청 글의 구절 인용, '지식'이면 항목 id다. 앱이 확인하지 못한 근거는 '추정'으로 내린다. 확인 방법·예시가 빈 줄, 추정 줄, 요청 옆의 틀린 동작(D550)이 질문이 된다. 레포가 이미 답한 것은 묻지 않는다.
- 승인 뒤의 과정은 모두 세션 몫이다. 계획, 나누기, 서브에이전트, 커밋 순서, push, PR이 다 그렇다.

**왜**
- 유형의 값은 증거 모양에 있었다(tests 4.5 대 3.9). v2는 그것을 프롬프트로만 지켰다. v3는 앱이 실행해 본다(원칙 2).
- 의도 정리가 숨긴 시험을 가른 곳은 44뿐이다. 작은 요청과 명세 같은 요청에서는 값이 없었고 사람 차례만 늘었다(confirm-each 배치 12.3 대 4.9, burden 15:0).
- 같은 배치에서 견주면 결정마다 확인 3/5, 초안 우선 1/5였다. 자료의 방향은 '많이 묻기' 쪽이다. 그래서 **첫 기본값은 v2의 결정마다 확인(D563)으로 둔다.** 근거 확인 방식은 M2에서 견줘 44의 이득을 잃지 않을 때만 기본으로 올린다.
- 선례: Claude Code best practices [1차]는 계획의 깊이를 변경 크기와 불확실성에 맞춘다.

**하지 않는 것**
- 유형 선택 화면, 유형별 파이프라인, 의도보다 먼저 정해지는 기본 완료조건과 브랜치 접두사.
- 크기·위험 분류로 질문 깊이를 정하기. 승인 뒤의 단계별 승인.
- 의도 정리가 요청을 여러 Work로 쪼개기(D551).

**알려진 맹점**
- 줄의 종류는 사람이 승인한 LLM 분류다. 같은 요청에서 얼마나 흔들리는지 잰 적이 없다(8.2에서 잰다).
- 세션이 사람만 아는 규칙을 코드에서 그럴듯하게 짚으면 '코드' 근거로 통과할 수 있다(42#2류). 추정이 놓친 사람 규칙의 비율을 함께 잰다.

### 원칙 2. 증거는 앱이 실행하고, 평가는 생성과 뗀다

**무엇인가**
- 앱이 레포가 선언한 명령(`.relay/quality.json`)을 직접 돌린다. 깨끗한 worktree에서 기준 SHA와 결과 SHA에 돌리고, 기준 결과는 SHA마다 캐시한다(main의 CI 결과가 있으면 그것을 쓴다).
- 결과는 SHA에 붙는다. head가 바뀌면 '낡음'이 된다. 계기는 셋이다. 세션이 쉬는데 head가 바뀌었을 때(몰아서 한 번), PR이 열리거나 갱신될 때, 사람이 [끝]을 누를 때. push했는지에 달리지 않는다. 세션은 `relay check`로 같은 확인을 당겨 볼 수 있지만 결과를 쓸 수는 없다.
- **승인된 예시는 데이터 파일로 커밋한다**(예: 시험 고정 자료 JSON). 수용 시험은 예시를 그 파일에서 읽는다. 앱은 예시 id마다 읽는 시험이 있는지, 통과하는지를 결정론으로 본다. 이 꼴이 맞지 않는 코드(화면 등)는 관찰·리뷰로 본다.
- **흔들리는 시험 규칙.** 실패하면 한 번 다시 돌린다. 기준에서도 실패하면 '원래 실패'다. 결과가 뒤집히면 '불안정'으로 적고 통과로도 실패로도 세지 않는다. 불안정 목록은 레포에 둔다.
- **평가는 생성과 뗀다.** 내보내기 후보마다 앱이 새 맥락의 읽기 전용 리뷰어를 띄운다. 리뷰어는 계약, 예시와 수용 시험, diff, 래칫 차이를 본다. 예시가 시험으로 제대로 옮겨졌는지, 시험이 못 보는 구조와 경계값을 본다. 지적은 증거 묶음에 붙고 막는 힘이 없다. 관문에는 정해진 몇 가지 올림 사유(예시와 시험 불일치, 보안, 계약 밖 변경)로만 들어간다.
- 결과는 쉬는 세션에 파일 하나와 터미널 한 줄로 준다. 사람이 최근에 입력했으면 넣지 않고 상태 줄에만 보인다. 라운드 상한은 3이다. 이 되먹임도 장치로 등록하고 라운드당 토큰·시간을 잰다.
- 세션이 PR 본문에 쓴 설명은 '주장' 칸에 따로 보인다. 증거가 없으면 '없음'이다. 통과로 보지 않는다.

**왜**
- PR 전에 결정론적 증거원이 없던 것이 v2 자율의 가장 큰 구멍이었다. D536이 시험을 돌리지 않은 까닭은 '레포마다 명령을 알아야 해서'였다. 레포가 명령을 선언하면 그 까닭은 사라진다.
- 결과 하네스를 버린 까닭 가운데 v3가 직접 푸는 것은 둘이다. Stop 되돌림을 쓰지 않고(형식 비용), 정해진 SHA에서 따로 재서 턴과 부딪치지 않는다(경합). 나머지 셋(PR 길, Claude Code가 이미 함, 사람의 바람)은 세션이 push·PR을 하는 v2 자율의 방식을 이어서 푼다.
- 앱 리뷰는 push에 달려 있어 6번 중 4번만 돌았다. 한 번은 [Work 완료] 3초 뒤에 끝났다. 계기를 push에서 떼면 이 빈틈이 사라진다.
- 세션은 지침 없이 스스로 리뷰하지 않았다(0/6). 앱 리뷰가 낸 유일한 차단은 틀린 지적이었다. 그래서 늘 돌리되 막는 힘은 주지 않는다. LLM 지식 검토가 옳은 사람 규칙을 지운 일(E13)도 모델 판단에 '내리는 힘'을 주면 안 되는 근거다.
- 44의 cron 실패처럼 의도 세부를 구현이 놓치면, 같은 세션이 쓴 시험도 같은 세부를 놓친다. 예시를 데이터로 두면 '예시 → 시험'의 연결을 앱이 지킨다.
- 선례: METR(2026-03) [1차]는 SWE-bench 시험을 통과한 PR의 약 절반을 관리자가 머지하지 않았을 것이라 봤다. 'Harness design' 글 [2차]은 자기 평가가 관대해서 평가자를 나눴다.

**하지 않는 것**
- Stop 훅 되돌림. 필수 산출물(handoff, plan.md, verification.md). 파일이 있는지로 품질 판정하기.
- 자기 보고로 자동 승인하기(D7). 커밋 순서 같은 과정 검사. push에 달린 검사.
- 리뷰를 세션 재량에 맡기기(D562). 리뷰가 머지를 막기. 리뷰의 '문제 없음'을 자동 머지의 충분조건으로 쓰기.
- 단계마다 새 세션 띄우기.

**알려진 맹점**
- 계약 줄이 모두 통과해도 계약이 빠뜨린 원인은 못 본다(14 #1: 판정표가 모두 '충족'이었는데 두 번째 원인을 놓침). 원인이 둘인 버그를 평가 묶음에 넣는다(8.2).

### 원칙 3. 품질의 바닥은 레포에 산다

**무엇인가**
- 레포가 품질 기준(`.relay/quality.json`)과 빚 장부(`.relay/debt/`)를 갖고, 사람이 PR로 바꾼다. 모든 Work는 방식과 상관없이 같은 기준으로 잰다.
- **강제는 '나빠지지 않음' 하나다(래칫).** 옛 빚을 갚으라고 하지 않는다. 첫 지표는 셋이다. 시험 수, lint·타입 오류 수, 파일 크기 상한. 기준선은 merge-base SHA에서 잰 값을 캐시한다(나란히 도는 Work가 파일에서 부딪치지 않게).
- **사람이 나빠진 채로 머지하면, 앱이 그 나빠짐을 빚 항목으로 기록한다.** anchor는 파일과 지표, 출처는 그 PR이다. 그래서 '사람이 받아들인 작은 나빠짐'이 새 바닥으로 조용히 굳지 않는다. 지표마다 고정점(v3를 처음 등록한 SHA)부터의 누적 추세도 보인다.
- **빚은 다음 Work에 저절로 닿는다.** 리뷰의 '나중에 정리할 곳'과 받아들인 나빠짐은 anchor(경로·이름)와 함께 장부에 간다. 그 경로를 건드리는 Work의 계약 초안에 '곁들일 정리' 후보로 뜬다. 사람이 계약에서 받거나 뺀다. 몫에는 상한(바꾼 파일 안, diff +N줄)을 둔다.
- **구조 변경 신호.** 새 디렉터리, 새 모듈, 새 외부 의존성, 새 공개 이름이 생긴 diff는 늘 사람에게 간다. 구조 흐름은 결정론으로 다 못 재기 때문에, 구조가 바뀌는 순간만큼은 사람이 본다.
- **기계로 볼 수 있는 규칙은 검사로 승격한다.** 사람이 정한 규칙(지식 rule)은 레포의 lint 설정이나 스크립트로 옮긴다. 옮길 수 없으면 '말로만'이라 적는다. 규칙의 '아직 따르지 않는 곳'(D296)은 그 검사의 허용 목록이 되고, 줄어들기만 한다.
- 수용 시험은 머지되면 평범한 레포 시험이 된다. 다음 Work부터 회귀 래칫이다.
- **시험이 없는 레포.** 줄의 확인이 기본으로 '관찰·사람'이 되고, 증거 묶음에 '없음'이 드러나게 보인다. 처음 등록할 때 앱이 '시험 틀 세우기'를 첫 빚 항목으로 제안한다. 첫 수용 시험이 들어온 뒤부터 회귀 래칫이 생긴다. 이런 레포는 늘 사람이 머지한다.

**왜**
- v2에서는 품질 장치가 마무리 단계에 붙어 있어서 경로와 함께 사라졌다. 레포에 두면 절차를 바꿔도 남는다.
- 지식은 기억만 이었다(숨긴 시험 −0.10). 반면 relay-v2 자신의 ESLint 경계 규칙은 PR마다 돌아 core 경계를 지켰다. 크기 상한은 없어서 `work.ts`가 자랐다. 말로 적은 규칙과 실행되는 검사의 차이다.
- '나중에 정리할 곳'은 아무 데도 이어지지 않았다. 사람이 시작해야 하는 정리는 0/12였다. 풀린 낡은 지식은 일상 Work가 곁들여 고친 것뿐이었다(2/18, 4/18로 낮음). '일상 Work에 끼우면 돈다'는 아직 잰 적 없는 가설이다. 그래서 이 장치도 등록부에 올리고 잰다.
- 선례: Betterer [1차]는 나빠지지 않음만 강제한다. fitness function [1차]은 원칙을 실행되는 검사로 둔다. Google 리뷰 기준 [1차]은 code health가 나아지는 방향이면 승인한다. Tricorder [1차]는 '쓸모없음' 비율이 높은 분석기를 끈다.

**하지 않는 것**
- 구조 품질을 프롬프트 문구로만 지키기. 옛 빚을 한꺼번에 갚으라고 요구하기.
- 지표로 사람의 머지를 막기. 건드리지 않은 곳을 지적하기.
- Work 사이 정보를 레포 밖에만 두기. 사람이 시작해야 하는 정리 Work와 그 알림.
- 앱이 CLAUDE.md를 고치기(D290을 지킨다).

**알려진 맹점**
- v3.0의 결정론 래칫 가운데 구조를 직접 겨누는 것은 파일 크기 상한 하나다. 27 k8 같은 일(옛 코드를 우회한 병렬 구현)은 셋을 모두 지나간다. v3.0에서 구조 흐름은 구조 변경 신호, 리뷰, 장기 평가로만 본다. 중복 탐지(언어와 상관없는 토큰 복제 탐지)는 첫 번째로 더할 후보다.
- 지표 게이밍(억지로 파일 쪼개기, 뜻 없는 시험 더하기)이 생길 수 있다. 리뷰어가 래칫 차이를 함께 보고, 기준을 바꾸는 diff는 사람 경로로 간다. 장기 평가의 주지표는 래칫이 겨누지 않는 것에서 고른다(8.2).

### 원칙 4. 자율은 끝난 변경의 사실과 실적으로 넓힌다

**무엇인가**
- 관문은 `gate(증거, 정책)`라는 순수 함수다. 모델을 부르지 않는다. 결론은 셋이다. **사람 머지**(기본), **자동 머지 후보**, **계약 다시**.
- 입력은 결정론적 사실이다. 계약 줄 판정, 명령 결과, 래칫 차이, 시험 약화(시험 파일 삭제, skip·only 추가, 시험 수 감소), 사람 경로를 건드렸는지, '사람' 줄이 있는지, 서버 쪽 브랜치 보호 상태, 정책의 자동 조건. 리뷰는 올림 사유로만 들어오고 결론을 엄격하게만 바꾼다(합치는 규칙은 max).
- **사람 경로** = 지킴 파일(`.relay/quality.json`과 정책, CI·lint·tsconfig, CODEOWNERS) + 레포가 적은 보호 경로(마이그레이션, 인증, 결제, 공개 API 등). 둘 다 늘 사람에게 간다. 빚 장부(`.relay/debt/`)는 사람 경로가 아니다. 앱이 형식과 anchor만 본다.
- **자동 조건은 diff에서 계산하는 술어로만 정의한다.** 예: '사람 경로 밖, 계약 줄이 모두 시험으로 확인됨, 새 의존성·새 모듈 없음, +N줄 이하'. 술어는 `quality.json`에 둔다. 사람이 요청한 Work도 술어를 채우면 후보가 된다.
- **자동 머지는 꺼진 채 시작한다.** 먼저 그림자로 '자동이었으면 머지했을 것'만 적는다. 이것을 사람의 결정, 그리고 머지 뒤 30일의 결과(되돌림, 머지 뒤 main 실패)와 맞대 본다.
- 넓히는 길은 하나다. 미리 적은 기준을 넘으면 앱이 정책 PR을 제안하고, 사람이 승인한다. 좁히는 것은 자동이다. **그 커밋에 귀속되는** 되돌림이나 main 실패가 하나 나면 그 조건의 자동이 꺼진다(바로 앞 커밋은 통과하고 그 커밋은 다시 돌려도 실패할 때).
- **모델이 바뀌면 다시 잰다.** 장부의 사건마다 모델, effort, Claude Code 버전, relay 버전을 적는다. 하나라도 바뀌면 열린 조건을 그림자로 되돌린다. 재생 평가를 지나거나 새 실적이 K건 쌓인 뒤에만 다시 연다.
- 시작 전의 예측은 질문 깊이에만 쓰고 관문에는 쓰지 않는다. 한 Work 안에서 결론은 엄격한 쪽으로만 간다. 느슨하게 하는 길은 사람이 승인한 정책 PR뿐이다.

**왜**
- S/M/L은 요청을 보고 미리 예측해 경로 전체를 묶었다가 흔들렸다. 반대로 동작 단위로 '되돌릴 수 있는가'를 본 관문(D204, D518, D558)은 결정론이라 흔들리지 않았다.
- 사람 없는 완전 자동의 품질은 잰 적이 없다. **실적으로 넓힌다는 기제도 v2에서 잰 적이 없는 가설이다.** 평가의 사람 역할은 매번 처음 쓰는 사람이었다. 그래서 그림자부터 시작한다.
- 누가 승인했는지(by: human/ai/caller, D522)와 건너뛴 것(D497)의 기록이 장부의 씨앗이다.
- 정책 표면은 작게 둔다. v2의 단계×유형 자동 승인 표는 대부분 죽은 설정이 됐다(D498). 위험 신호는 함정 diff 평가에서 값이 보일 때만 하나씩 더한다.
- 선례: Meta Diff Risk Score [논문 1차]는 작업 유형이 아니라 실제 diff로 게이팅하고, 정책을 '막은 비율 대비 잡은 사고 비율'로 잰다. Renovate·Dependabot [1차]은 계산되는 속성으로 자동과 수동을 가르고 자동도 필수 검사를 거친다. 'Measuring AI agent autonomy' [2차]에서는 사용자가 숙련될수록 세션 전체 자동 승인과 개입이 함께 늘었다. Lee & See [1차 초록]는 실제 신뢰성에 맞춘 신뢰를 말한다.

**하지 않는 것**
- LLM이 매기는 위험·크기 등급. 요청 글로 경로를 고르기. 에이전트가 '위험 낮음'이라 적은 글로 관문을 낮추기.
- '모델이 좋아졌으니' 넓히기. 옛 모델의 실적으로 폭을 유지하기.
- 실적 없이 자동 머지하기. 레포 전체에 한꺼번에 자율을 주기.
- 사람 교정률이 준 것을 품질 향상으로 읽기(사람이 덜 보면 교정도 덜 보인다).
- 앱 안 세션의 자기 승인(D520을 지킨다).

### 원칙 5. 장치는 가설이고, 단순함도 래칫이다

**무엇인가**
- relay가 붙이는 장치(질문, 증거 의무, 리뷰, 래칫, 장부, 관문, 되먹임)는 모두 '모델이 혼자 못 한다'는 가설이다. 장치마다 한 줄을 적는다. 가정, 붙는 사건, 비용, 지표, 끄는 조건, 최소 n, 상태(꺼짐 / 그림자 / 알림 / 관문). **끄는 조건이 없으면 들어오지 못한다.** 등록부는 relay-v3 레포의 `docs/devices.md`로 시작한다.
- 장치는 하나씩 넣고 하나씩 뺀다. 묶어서 걷지 않는다. 결정 로그의 근거에는 '측정' 또는 '가정'을 붙인다.
- **생애는 하나다.** 모드, 유형, 파이프라인, 옛 길 호환이 없다.
- **숫자로 상한을 건다.** relay-v3 자신에 첫날부터 CI로 건다. 앱 코어 5,000줄 이하, 파일 600줄 이하, 의존 방향 규칙. v3.0에서 사람이 새로 배울 낱말은 부록 A에 있는 것뿐이다(열 개 이하).
- 마일스톤마다 '빼는 이유'를 심사한다. 꺼진 채 심사를 두 번 지난 장치는 코드에서 지운다.

**왜**
- v2의 설계 규칙 0.2는 '추가에는 이유'만 물었다. 결정 560행 중 93행이 뒤에서 바뀌었다.
- D559(리뷰 넣기)는 평가를 근거로 들었지만 귀인이 틀렸다. D562(리뷰 빼기)는 n=2 평가와 사람의 가정을 함께 근거로 했다. 둘 다 뺀 변형 없이 정했다.
- D557은 판정표, verification.md, 지식 확인, plan.md 관문을 한꺼번에 걷었다. 그래서 무엇이 값을 했는지 가를 수 없게 됐다.
- 반대로 결과 전에 규칙을 고정하고 hold-out을 봉인한 실험은 버릴 것을 실제로 버렸다(D395).
- 이중 모드 탓에 문서와 코드가 어긋났다(D557의 '지식 남기기 없음'과 context.ts). 자율을 다른 유형으로 넓히는 일도 '앱이 쥔 것이 많아 위험하다'며 미뤘다.
- 선례: 'Harness design' 글 [2차]은 장치마다 가정을 적고 새 모델에서 하나씩 꺼 보라고 한다. mini-swe-agent [1차]는 bash만 쓰는 작은 에이전트로 높은 점수를 냈다.

**하지 않는 것**
- 끄는 조건 없는 영구 장치. '필요해 보인다'만으로 넣기. '모델이 좋아지면 필요 없다'만으로 빼기.
- n=2로 기본값 바꾸기. 이중 모드. 거대한 runner 클래스. 기능마다 다는 설정 손잡이.

### 바닥 (가설이 아니다)

다음은 등록부 밖이다. 꺼 보는 실험의 대상이 아니다.

- Work마다 worktree와 브랜치를 따로 준다.
- 지킬 브랜치 push, 강제 push, 원격 브랜치 삭제, 머지를 **모든 세션에서 같은 두께로** 막는다(D558을 넓힘). 사람 경로를 건드리거나, 시험을 약화하거나, 구조를 바꾸는 diff는 늘 사람에게 간다.
- 외부 글(PR 코멘트, 이슈)은 데이터로 감싸 인용 파일로 두고, 작성자를 거른다(D160, D566). 터미널에는 한 줄 알림만 넣는다.
- 앱 안 세션은 스스로 계약을 승인하거나 정책을 바꿀 수 없다(D520).
- 모델 판단과 장부는 결론을 엄격하게만 바꾼다. 증거가 없으면 '없음'이다.

## 3. 개념 모델과 일의 생애

```
[레포] 오래 남는 것. 모두 레포 안에 있고 PR로 바뀐다
  .relay/quality.json   사람 소유
    commands   fast: 건드린 범위의 시험·lint·타입 / full: 전체(CI 체크 이름으로 대신 가능)
    human      사람 경로: 보호 경로 목록(마이그레이션, 인증, 결제, 공개 API, CI …)
    ratchets   첫판 셋: 시험 수, lint·타입 오류 수, 파일 크기 상한
    rules      지식에서 승격된 검사의 위치(레포 lint 설정, 스크립트)
    auto       자동 조건 술어 목록(기본: 비어 있음)
  .relay/debt/<id>.md   빚 한 항목 = anchor · 종류 · 출처(Work·PR) · 까닭 · 날짜
  .relay/flaky          불안정 시험 목록
  docs/knowledge/       v2 형식(규칙 / 아직 따르지 않는 곳 / 정하지 않은 것 / 바뀐 이력)
  레포 시험 + 예시 자료  머지된 수용 시험과 예시 JSON이 쌓인다

[Work] = 계약 + 세션 + 증거 묶음 + 관문 결론
  계약(승인 때 기록, by: human | caller)
    줄 Cn: 종류(바뀜|새로|지킴|없앰|문서|사람) · 근거(코드 path:line | 요청 인용 | 지식 id | 추정)
           · 예시 id(입력 → 출력, 오류) · 확인(시험 | 관찰 | 사람)
    비목표 · 사람만 아는 규칙 · 곁들일 정리(빚 장부에서, 몫 상한)
  세션   방식은 자유. 도구: relay check, 계약 바꾸기 요청
  증거 묶음(SHA마다 앱이 계산. 세션은 못 씀. head가 바뀌면 낡음)
    줄 판정 · 명령 결과(base 캐시 ↔ head) · 래칫 차이 · 시험 약화 · 사람 경로 · 구조 변경
    · 지식 형식과 탐지기 · 리뷰 지적 · 주장(따로) · 전체 diff
  관문   gate(증거, 정책) → 사람 머지 | 자동 머지 후보 | 계약 다시

[앱 로컬]  기준선 캐시 · 증거 묶음 · 실적 장부(조건마다: 결론, by, 그림자 결론,
           머지 뒤 30일 되돌림·main 실패, 모델·effort·Claude Code·relay 버전)
[relay-v3 레포]  docs/devices.md 장치 등록부

흐름
  계약 ─승인→ 예시 자료 + 수용 시험 ─머지→ 레포 시험(회귀 래칫)
  결과 SHA ─계산→ 증거 ─→ gate ─→ 실적 장부 ─→ 조건 넓히기 제안(사람 승인) / 자동 좁히기
  사람이 받아들인 나빠짐 ─→ 빚 장부 ─(anchor ∩ 건드릴 경로)→ 다음 계약 초안의 곁들일 정리
  생성(세션) ≠ 평가(확인 실행기 + 리뷰어). 기준은 공개, 실행은 분리
```

**일의 생애**

1. **들어옴.** 사람이나 바깥 호출자(relay MCP)가 요청만 낸다. 유형은 없다.
2. **계약 초안.** 세션이 코드, 관련 지식, 근처 빚, 품질 기준을 읽고 줄을 쓴다. 앱이 근거를 확인하고, 확인되지 않은 줄과 빈칸만 묻는다(첫 기본값은 결정마다 확인). 이번 Work가 바꿀 구조가 있으면 한 단락으로 보인다.
3. **계약 승인.** 사람이 예시를 읽고 승인한다. 시험 코드는 읽지 않아도 된다. `driver=caller`면 호출자가 승인하고 `by: caller`로 따로 센다.
4. **구현.** 방식은 세션이 정한다. 예시 자료를 커밋하고 수용 시험으로 옮기는 시점도 세션이 정한다. 계약이 틀렸다고 보면 바꾸기 요청을 내고 나머지 줄은 계속한다.
5. **증거.** 계기마다 앱이 증거를 계산한다. 빠른 명령은 늘, 전체는 내보낼 때(또는 그 SHA의 CI). 리뷰는 비동기로 돈다.
6. **관문.** gate가 결론과 '결론을 정한 사실 한 줄'을 낸다. v3.0에서 자동 머지 후보는 그림자로만 적고 사람에게 보낸다. 사람은 그 한 줄을 먼저 보고, 줄별 판정·래칫 차이·리뷰·주장·diff는 펼쳐 본다.
7. **머지.** 앱의 [머지] 단추와 자동 경로는 머지 게이트(CI, 충돌, 항목 처리, head 일치)와 최신 대상과 합친 상태의 다시 확인(래칫·수용 시험 포함)을 따른다. merge queue가 있으면 그것을 쓴다. **사람은 그 밖(GitHub 등)에서 언제든 머지할 수 있다.** 그때 앱은 `by: human-override`와 넘긴 조건을 남기고, 나빠진 지표는 빚으로 적는다.
8. **머지 뒤.** 수용 시험은 레포 시험으로 남는다. 기준선이 앞으로 간다. 모델 없는 스캔이 빚과 지식의 anchor를 확인하고 사라진 것을 닫는다. 실적 장부에 결론, by, 그림자 결론이 남고 30일 동안 결과가 붙는다.
9. **끝.** 세션이 연 PR이 모두 머지되거나 닫히면 Work가 끝난다(D567). PR 없는 Work는 사람이 [끝]을 누르고, 그때도 증거는 한 번 돈다.

## 4. 여러 Work에 걸친 품질 장치

C4의 실제 위험은 기능 회귀보다 구조와 유지보수성의 흐름이다. 다만 이것도 아직 가설이다(근거는 두 사례). 그래서 장치는 '나빠지지 않음'과 '드러내고 기록하기'까지만 한다. **v3.0에는 자동 머지가 없으므로, 아래의 '자동 경로를 닫음'은 그림자 결론을 바꿀 뿐이다. v3.0에서 바닥의 힘은 경고와 기록이다.**

| 장치 | 언제 | 하는 일 | 바닥/가설 | 끄는 조건(예) |
|---|---|---|---|---|
| 빠른 명령 | 증거 계기마다 | base 캐시 ↔ head. 실패면 자동 경로 닫고 세션에 한 줄 | 가설 | 실패 알림 뒤 세션이 고친 비율이 낮고 사람 머지 판단도 바꾸지 못함 |
| 전체 스위트 | 내보낼 때, 머지 직전 | CI 결과 우선. 없으면 앱이 돌림 | 가설 | 빠른 명령과 결론이 늘 같음 |
| 수용 시험 편입 | 머지 | 다음 Work부터 회귀 래칫 | 가설 | 편입 시험이 이후 회귀를 한 번도 못 잡고 유지비만 듦 |
| 래칫 3종 | 증거 계기마다 | 나빠지면 경고, 자동 경로 닫음, 받아들이면 빚 기록 | 가설 | 장기 평가에서 켠 쪽과 끈 쪽이 δ 안에서 같음 |
| 시험 약화 신호 | 증거 계기마다 | 삭제·skip·only·수 감소 → 사람 | 바닥 | (꺼 보지 않음) |
| 사람 경로 | 증거 계기마다 | 지킴 파일·보호 경로 접촉 → 사람 | 바닥 | (꺼 보지 않음) |
| 구조 변경 신호 | 증거 계기마다 | 새 디렉터리·모듈·의존성·공개 이름 → 사람 | 바닥(무엇을 셀지는 조정) | 끄지 않음. '쓸모없음' 비율이 약 10%를 넘으면 세는 범위를 좁힌다 |
| 빚 장부 | 계약 초안, 머지 뒤 | 곁들일 정리 후보. 사라진 anchor는 닫음 | 가설 | 곁들인 정리 수용률과 해결률이 낮고 멀쩡한 항목을 깸 |
| 규칙 승격 | 규칙을 쓰거나 고칠 때 | 기계로 볼 수 있으면 검사로, 아니면 '말로만' | 가설 | 승격 검사의 '쓸모없음' 비율이 높음 |
| 지식 확인 | 계약 초안, 머지 전 | 형식·anchor 확인. 검토는 이번에 바뀐 줄만 | 가설 | 다시 말하기(PM1) 감소가 사라짐 |
| 독립 리뷰 | 내보내기 후보마다 | 구조·중복·의도 대조. 올리기만 | 가설 | 뺀 변형(n≥5)에서 숨긴 시험·선호·머지 뒤 지표가 δ 안 |
| 증거 되먹임 | 결과가 나올 때 | 쉬는 세션에 한 줄, 상한 3 | 가설 | 라운드당 토큰 대비 고친 비율이 낮음 |

**동시에 도는 Work.** 두 PR이 각자 merge-base에서는 래칫을 지나도 합치면 넘을 수 있다. 그래서 머지 직전 다시 확인에 래칫과 수용 시험을 넣는다. merge queue가 없으면 '최신 대상과 맞춤' 상태 검사를 요구한다. Work가 빚 항목을 곁들일 정리로 집으면 '잡힘'을 표시해 다른 Work의 초안에는 '진행 중'으로 뜨게 한다.

**누적 장치가 새 부채가 되지 않게.** anchor는 필수다. 장부 크기에 한도를 두고 항목의 나이를 보인다. 한 Work의 범위 지시는 규칙이 아니라 빚 항목으로 보낸다(D296). 정리 후보는 결정론 탐지기를 앞세운다(87.5% 대 66.7%). 장부는 해결률과 함께 '멀쩡한 항목 보존률'도 잰다. 평가에서는 `.relay/` 변경을 범위 판정에서 뺀다(scope 2.8 대 4.5를 되풀이하지 않게).

**미루는 것.** 사건을 계기로 앱이 정리 Work를 스스로 만드는 일은 첫판에서 뺀다. 리팩터링·정리 일은 자율로 잰 적이 없다. 그리고 '사람이 시작하지 않는다'(0/12)는 교훈이 '사람이 보지도 않는 자동 PR'로 번질 수 있다. 그 대가로 아무도 건드리지 않는 곳의 빚은 남는다. 이것은 장부의 나이로 숨기지 않고 보인다.

## 5. 위험에 비례한 자율과 완전 자동으로 가는 길

v3에서 '위험에 비례한다'는 이렇게 읽는다. 요청을 보고 위험을 맞히지 않는다. 끝난 diff의 사실과 '되돌릴 수 있는가'로 관문을 계산한다. 그리고 그 자동 조건의 실적이 자율의 폭을 정한다.

**솔직히 적는다.** v3.0의 사람 관문은 v2 자율과 같은 둘(계약 승인, 머지)이다. v3.0에서 바뀌는 것은 질문 깊이, 앱이 만든 증거, 레포의 바닥이다. 자동으로 가는 길은 열려 있지만, 실적으로만 연다.

**단계 0 (v3.0): 그림자.** 모든 Work에 관문 결론을 계산한다. 자동 머지 후보는 기록만 하고 사람이 머지한다. 그 기록을 사람 결정과 머지 뒤 30일의 결과에 맞대 본다. relay-v3 레포 자신부터 돌린다. 사람이 PR에서 GitHub auto-merge를 직접 켜는 것은 막지 않고 `by: human-preapproved`로 장부에 남긴다. 이것이 그림자 실적의 실제 표본이 된다.

**단계 1: 좁은 자동 조건에서 자동 머지.** 사용자가 허용한 뒤에만 연다. 모두 채워야 한다.
1. 서버 쪽 강제: 앱이 gh로 기본 브랜치 보호와 필수 상태 검사(CI 인프라에서 도는 것)를 확인한다. merge queue가 있으면 쓰고, 없으면 '최신 대상과 맞춤'을 요구한다. 앱이 로컬에서 돌린 결과만으로는 열지 않는다.
2. diff가 자동 조건 술어를 채운다. 계약의 모든 줄이 기계로 확인되고 '사람' 줄이 없다.
3. 사람 경로, 시험 약화, 구조 변경 신호가 없다. 래칫이 나빠지지 않았다. 리뷰가 올린 것이 없다.
4. `git revert` 하나로 되돌릴 수 있다. v3.0에서는 이것을 사람 경로 목록으로 근사한다(마이그레이션, 외부 부작용, 머지가 곧 배포인 레포, 공개 API는 사람이 그 목록에 적는다).
5. 그 조건의 그림자 실적이 미리 적은 기준을 넘는다. 예: 30건 이상, 사람 결정과 일치 95% 이상, 자동 후보의 머지 뒤 되돌림 0. 숫자는 사용자가 정한다.
6. 회로 차단기: 조건마다 하루 상한, 전체 끄기 스위치, 한 번에 되돌리는 단추가 있다.

첫 후보는 사람이 요청한 작은 Work 가운데 술어를 채운 것이다(예: 보호 경로 밖, 새 의존성 없음, +50줄 이하, 줄이 모두 시험으로 확인됨). 의존성 patch는 Renovate가 relay 없이 이미 잘 하므로 첫 후보로 두지 않는다. 한 사람의 레포는 Work가 적어 실적이 느리게 쌓인다. 그래서 같은 술어의 실적을 사용자의 여러 레포에서 합쳐 쌓고, 레포마다 끌 수 있게 한다.

**단계 2: 계약만 사람.** 사람이 계약은 승인하되 diff는 보지 않는 경로다. 실적이 쌓인 조건에서만 연다. 그 전에 평가 E-auto로 사람의 사후 교정 몫을 처음 숫자로 잰다. `driver=caller` 경로는 '계약까지 AI'를 재 볼 실험 통로로 쓴다. caller가 승인한 계약은 장부에서 따로 세고, v3.0에서는 늘 사람이 머지한다.

**단계 3: 미리 승인된 계약 틀.** 사람이 PR로 승인한 계약 틀이다. 범위 술어, 허용 변경, 요구 증거를 담는다. 라벨이나 봇 PR은 틀을 '제안'만 한다. 틀 자격은 끝난 diff가 범위 술어를 채웠는지로만 정한다. 자유 글 요청을 틀에 맞췄다고 할 때는 사람이 한 번 확인해야 의도 정리를 건너뛴다. 건너뛸 때 잃는 것은 범위가 아니라 사람만 아는 규칙이기 때문이다. 첫판에는 없다.

**끝까지 사람인 것**
- 계약, 정책, 품질 기준을 바꾸는 일, 자율을 넓히는 승인
- 사람 경로(마이그레이션, 인증, 결제, 공개 API, CI)를 바꾸는 일
- 머지가 곧 배포인 레포의 머지, 시험이나 CI가 없는 레포의 머지
- 외부에 글을 거는 일과 되돌릴 수 없는 동작
- 구조를 바꾸는 diff(구조 변경 신호)

**'모델이 발전하면'에 대한 답.** v3는 이 외삽을 구조에 미리 넣지 않는다. 더 강한 모델이 오면 두 곳에서 보이게 한다. 실적 장부가 깨끗해지면 사람이 조건을 넓힌다. 장치를 하나씩 꺼 보는 심사(8.3)에서 이득이 줄면 그 장치를 끈다. 계약과 증거는 '무엇'만 요구하고 '어떻게'는 묻지 않는다. 그래서 강한 모델에게 상한이 되기 어렵다고 본다. 이것도 단언이 아니라 가설이고, 강한 모델 설정의 평가로 확인한다.

## 6. 사람의 역할

사람은 단계를 승인하는 사람이 아니다. 다섯 자리를 맡는다.

1. **계약의 공동 저자.** 사람만 아는 규칙을 말하고, 예시를 읽고 고치고 승인한다.
2. **레포 기준의 주인.** 명령, 사람 경로, 래칫, 자동 조건을 PR로 정한다. relay는 처음 등록할 때 package.json·CI·lint 설정을 읽어 초안만 제안한다. 쓸모없는 지적과 규칙에는 '쓸모없음'을 누른다. 사람 결정 가운데 지렛대가 가장 크다.
3. **머지하는 사람.** 결론을 정한 사실 한 줄과 증거 묶음을 보고 머지한다. 하네스는 사람을 막지 않는다.
4. **신뢰를 맞추는 사람.** 실적 장부의 원 숫자(그림자 일치, 되돌림, main 실패)를 보고 조건을 넓히거나 줄인다. 장부 사건에 이의를 달 수 있다. 장치 상태를 바꾸는 일도 사람이 승인한다.
5. **레포를 이해하는 사람.** 자율이 넓어질수록 사람은 diff를 덜 읽는다. 그러면 사람만 아는 규칙에 답하는 힘, 구조를 판단하는 힘, 사고 때 고치는 힘이 함께 준다. 그래서 단계가 올라가도 구조 변경은 사람에게 가고, 계약 화면에는 '이번 Work가 바꿀 구조'가 보인다. 장기 평가에서 '모르는 코드에서 다음 계약을 쓰는 비용'을 잰다.

**사람이 하지 않게 되는 일.** 유형 고르기, 단계마다 승인, 형식 오류 보기, 정리 Work를 떠올려 만들기, 같은 규칙 다시 말하기, Work마다 자동 승인 다이얼 돌리기(D72, D529). 화면의 숫자는 규칙과 자율 범위를 정할 근거일 뿐 할 일 목록이 아니다. 사람이 대시보드를 보고 움직이기를 기대하지 않는다(0/12).

## 7. 안전 모델

**먼저 정직하게 적는다.** relay는 Claude Code 샌드박스를 켜지 않는다. 세션은 앱과 같은 OS 사용자, 같은 gh 자격으로 돈다. 그래서 로컬 관문(래칫, 리뷰, 사람 경로, 증거 저장소)은 '정직한 실수'를 막는 관문이다. 바뀐 것을 알아챌 수는 있지만, 주입된 세션 앞에서 막을 힘은 없다(D91과 같은 수준). 세션이 graphql로 auto-merge를 켜면 relay의 관문을 건너뛴다. 서버가 강제하는 것은 필수 CI 검사뿐이다.

**그래서 자동 머지는 서버가 강제하는 것 위에서만 연다.** relay의 관문 결론을 서버가 강제하게 하려면 GitHub App 신원의 check run이 필요하다. 데스크톱 앱에서는 어렵다. 그래서 v3.0은 그림자까지만 한다. 세션의 자격을 줄일지(샌드박스로 쓰기를 worktree에 묶기, push·merge 자격을 앱만 쥐기)는 사용자가 정한다. Windows 네이티브에는 샌드박스가 없다.

**겹마다 맡은 일**
1. **바닥** (2장 끝). 모든 세션에 같은 두께.
2. **비대칭.** 모델 판단과 장부는 결론을 엄격하게만 바꾼다. 느슨하게 하는 것은 사람이 승인한 정책 PR뿐이다.
3. **증거가 없으면 없음.** 시험이나 CI가 없는 레포는 늘 사람이 머지한다.
4. **확인 실행기의 안전.** 실행기는 세션이 쓴 코드를 돌린다. 포크 PR의 코드는 돌리지 않는다. 시간 제한을 두고, 앱의 토큰을 환경에서 빼고 돌린다.
5. **바깥에서 시작하는 일.** 이슈나 PR 코멘트에서 시작한 Work는 사람의 계약 승인 없이 시작하지 않는다. 호출자가 바깥 글을 근거로 Work를 열었으면 그 사실을 계약에 표시하고 같은 규칙을 적용한다.
6. **회로 차단기.** 라운드 상한 3(D171), 취소(D130), 토큰 예산, 백그라운드 작업 중 판정하지 않음(D129), 재시작 때 자동으로 진행하지 않음(D127).
7. **감사 기록.** 모든 결론에 근거 사실, 정책 버전, 승인 주체(by: human / caller / policy / human-override / human-preapproved), 건너뛴 것을 남긴다. 세션 커밋에는 결정론적 트레일러를 붙여 사람 커밋과 가른다.

## 8. 측정

### 8.1 제품 안의 측정

몸통 밖 모듈이 git과 gh에서 결정론적으로 센다. 처음 지표는 넷이다.
- **사람 교정:** '준비됨' 뒤 사람이 직접 한 커밋(트레일러로 가름). 대화 속 요구는 모델 판정이 필요하므로 세지 않는다.
- **머지 뒤 30일:** 되돌림과 그 커밋에 귀속되는 main 실패. 같은 줄의 후속 고침은 참고로만 본다(정상적인 후속 기능도 잡히므로).
- **지적의 처리:** 고쳐짐 / 넘김 / 틀림, 장치·규칙마다 '쓸모없음' 비율.
- **비용:** 사람 차례, 시간, 토큰, 확인 실행기의 분.

관문을 뺀 뒤에는 사람 교정률이 아니라 머지 뒤 지표로 판단한다. 사람 교정 지표는 에이전트에게 목표로 주지 않는다.

### 8.2 장기 평가 (철학의 성패를 가른다)

- **판.** 3~5천 줄에서 시작해 커지는 시나리오 레포. 요청 30개 열(기능, 버그, 리팩터링, 대충 쓴 요청, 규칙 변경, 원인이 둘인 버그). 절반은 봉인한다. 열 끝에 '구조가 좋으면 쉬운' 봉인 변경 과제를 둔다.
- **주지표는 래칫이 겨누지 않는 것에서 고른다.** 끝 봉인 과제의 통과율, 후반 Work 비용의 기울기, 각 쪽이 만든 레포에서 고정된 기준 에이전트로 같은 뒤 Work 열을 돌린 비용, 가린 '관리자라면 머지하겠나' 판정, 앞 Work 숨긴 시험의 누적 통과. 구조 지표는 보조로만 쓴다(v3가 그것을 래칫하므로 v3 쪽으로 기운다).
- **견줄 쪽은 셋으로 줄인다.** v3 핵, v3 핵 + 레포의 바닥(래칫·빚 장부), 맨 CLI. v2 자율과 v2 전용 유형은 같은 판에서 한 번만 기준 곡선으로 돌린다.
- **더할 것.** E-auto(사람이 diff를 보지 않는 쪽), E-risk(함정 diff 묶음: 마이그레이션, 인증 경로, 시험 삭제, CI 수정, 결제 계산 한 줄로 관문의 재현율·정밀도), 관문 안정성(같은 요청 5회: 줄 종류, '사람' 줄 여부, 결론이 갈리는지), '돌아오는 사람' 역할, 사람 역할이 묻지 않아도 아는 세부를 말하는 변형(의도 정리의 몫을 평가 설계와 떼어 재기), 더 강한 모델 설정 한 번.
- **방법.** v2의 강점을 그대로 쓴다. 숨긴 시험, 함정 패치 검증, 봉인 hold-out, 결과 전 고정 규칙(frozen 확인을 되살림), bootstrap 구간, 측정 코드의 단위 시험. 약점은 고친다. n≥5, 판정과 사람 역할에 다른 모델 섞기, 판정에 시나리오 목적을 주지 않기.

### 8.3 하네스를 깎는 규칙

- **심사 계기:** 모델이나 Claude Code가 바뀔 때, Work 50개마다, 마일스톤마다.
- **심사 방법:** 등록부의 줄마다 지표를 끄는 조건에 넣어 본다. 모델이 바뀔 때는 재생 평가로 장치를 하나씩 꺼 본다. 재생 묶음은 사용자 레포의 머지된 PR로 만든다(기준 커밋과 요청 초안을 되살리고, 그 PR의 시험을 숨긴 시험으로). 일부는 봉인한다.
- **재생 평가의 한계:** 요청을 사후에 되짓기 때문에 의도 정리의 값은 잴 수 없다. 의도 쪽 장치는 장기 평가와 M0의 뺀 변형으로만 판단한다.
- **바꾸는 규칙:** 최소 n 전에는 상태를 바꾸지 않는다(안전 사고는 예외). 상태를 바꾸는 것은 사람이 승인한다.

### 8.4 틀렸다고 볼 조건 (결과를 보기 전에 고정)

조건마다 동등 한계 δ와 필요한 n을 미리 적는다. 차이의 구간이 ±δ 안이면 '같음', 걸치면 '모름'이다. '모름'이면 더 싼 쪽을 기본으로 두되, 등록부에 '모름'으로 남기고 n을 늘린다. 넣기와 빼기에 같은 규칙을 쓴다.

- 30 Work 뒤 '레포의 바닥'을 켠 쪽과 끈 쪽이 주지표에서 같으면, 기본에서 뺀다.
- 리뷰 뺀 쪽이 숨긴 시험, 결과 선호, 머지 뒤 지표에서 같으면, 리뷰를 표본 리뷰로 줄인다.
- 근거 확인 초안이 44에서 결정마다 확인보다 낮으면, 근거 확인 방식을 기본으로 올리지 않는다.
- 교차 평가(cross-general 18개 + 리팩터링 18~20)에서 tests 점수가 v2 전용 유형보다 낮으면, 유형을 '덮어쓸 수 있는 제안'으로 남긴다.
- 그림자에서 자동 후보의 머지 뒤 되돌림이 사람 검토 변경보다 많으면, 그 조건은 열지 않는다.
- E-auto가 사람이 diff를 보는 쪽보다 숨긴 시험에서 낮으면, 그 모델에서는 단계 2를 열지 않는다.
- 관문 결론이 결정론적 입력만으로도 5회 반복에서 갈리면, 그 입력을 관문에서 뺀다.
- 작은 요청과 명세 같은 요청에서 시간·토큰이 맨 CLI의 X배를 넘거나 사람 차례가 1.5배를 넘으면, 리뷰를 표본으로 줄이고 계기를 줄인다(X는 사용자가 정한다).

### 8.5 정직한 한계

- 한 사람의 레포에서 나오는 Work 수는 적다. 조건별 판단은 오랫동안 '증거 부족'으로 나올 것이고, 그대로 보인다. 자율은 느리게 넓어진다. 그것이 의도다.
- 장기 평가는 비싸다. v2의 지식 실험 하나에 $705와 46시간이 들었다.
- AI 사람 역할은 진짜 사람의 피로와 신뢰를 다 담지 못한다.
- 측정 모듈 자체도 새 WorkRunner가 될 수 있다. 그래서 크기 상한과 '빼는 이유' 심사를 똑같이 받는다.

## 10. 사용자가 정할 열린 결정

✅는 v2에서 사용자가 직접 정한 결정이다. 이것을 뒤집는 것은 기능 변경이 아니라 철학을 다시 정하는 일이다.

1. **유형 선택을 없앨지 (D236 ✅, D423 ✅).** 제안: 없앤다. 다만 M2 교차 평가(8.4)에서 tests 점수가 떨어지면 '덮어쓸 수 있는 제안'으로 남긴다.
2. **앱이 레포 명령을 직접 돌릴지 (D7 ✅를 바꿈).** 제안: 빠른 명령은 앱이, 전체는 CI를 먼저. 시간·비용 예산도 정한다.
3. **사용자 레포에 `.relay/quality.json`, `.relay/debt/`, 예시 자료, 수용 시험을 커밋할지.** `.relay/types/`(D450 ✅)라는 선례가 있다. 새로 정할 것은 앱이 quality.json을 읽어 실행하는 일과 시험을 커밋하는 일이다. CLAUDE.md는 계속 건드리지 않는다(D290).
4. **체크 없는 레포의 머지 판정 (D176 ✅).** 제안: '없음'으로 보이고 늘 사람이 머지한다.
5. **자동 머지를 허용할지 (D15 ✅, D152 ✅, D518 ✅).** 제안: v3.0은 그림자까지만. 단계 1의 그림자 기준 숫자도 이때 정한다.
6. **늘 도는 리뷰를 받을지.** D562에서 사람은 '리뷰는 필요하면 세션이 스스로, 지침도 넣지 말자'고 했다. 늘 도는 리뷰는 그 바람을 뒤집는다. 토큰 비용도 든다. 막는 힘은 주지 않는다.
7. **질문 깊이의 첫 기본값.** 자료의 방향(같은 배치 3/5 대 1/5)은 결정마다 확인 쪽이다. 제안: 결정마다 확인으로 시작하고, 근거 확인 방식을 M2에서 견준다.
8. **래칫의 첫 지표와 세기.** 제안: 셋(시험 수, lint·타입 오류 수, 파일 크기 상한), 경고와 기록만. 중복 탐지를 첫판에 넣을지도 정한다.
9. **세션의 자격을 줄일지.** 샌드박스로 쓰기를 worktree에 묶을지, push·merge 자격을 앱만 쥘지.
10. **팀에서 쓸 때.** 제안: v3.0은 '레포 하나에 relay 운영자 하나'를 전제로 한다. 팀에서는 정책에 영향을 주는 사건(자동 내림, 되돌림)만 레포 쪽에 남겨 모든 팀원의 앱이 같은 상태를 보게 한다. 개인 성과로 읽힐 원 숫자는 로컬에 둔다.
11. **사건 계기 스캔과 정리 Work 자동 생성 (D153, D395).** 제안: 첫판은 스캔과 장부 갱신만.
12. **미리 승인된 계약 틀(상시 의도)을 언제 열지.** '의도 승인은 늘 사람'을 뒤집는 일이다. 제안: 첫판에는 없다.
13. **첫판의 범위.** 자식 Work 장치와 Codex 엔진. 제안: 둘 다 뒤로.
14. **장기 평가를 기능보다 먼저 만들지와 그 예산.** 이 철학의 성패가 거기에 달려 있다.

## 11. 첫 단계

작게 시작해 평가로 넓힌다. 마일스톤마다 8.4의 조건을 결과 전에 고정한다.

**v3.0 최소 핵.** 계약 도구(예시 자료 포함), 확인 실행기(빠른 명령, base·head), 증거 묶음, 독립 리뷰(올리기만), 래칫 3종과 받아들인 나빠짐의 빚 기록, 사람 경로·시험 약화·구조 변경 신호, 사람 머지, 관문 함수(그림자 결론만), 장치 등록부, 바닥. 나머지(곁들일 정리, 규칙 승격, 실적 장부의 자동 좁히기, 자동 조건별 자동 머지, 계약 틀)는 등록부에 '꺼짐'으로 올리고 하나씩 켠다.

- **M0. 재는 판부터 만든다 (v3 코드 전).**
  - M0a 귀인 가르기: v2 평가 도구 위에서 뺀 변형을 돌린다. {전부 켬, 리뷰 뺌, 판정표 뺌, 증거 의무 뺌, 질문 얕게}. 시나리오 07, 08, 14, 42, 43, 44, 리팩터링 19, 21~27 일부. n≥5. 같은 실험을 더 강한 모델 설정에서도 한 번. 결과로 핵의 장치와 기본 상태를 확정한다.
  - M0b 장기 평가 판: 8.2의 판을 만들고 v2 자율, v2 전용 유형, 맨 CLI로 기준 곡선을 그린다. E-auto와 E-risk 묶음도 이때 만든다.
- **M1. 확인 실행기와 관문 함수 (앱 없이 CLI로).** 품질 기준 초안 만들기, base·head 실행과 SHA별 캐시, 흔들리는 시험 규칙, 증거 묶음 JSON, 사람 경로·시험 약화·구조 변경 신호. 관문 함수는 [단위] 시험과 E-risk로 재현율을 본다. 실행기는 [어댑터] 시험. relay-v3 자신의 품질 기준(코어 5,000줄, 파일 600줄, 의존 방향)과 `docs/devices.md`를 이때 둔다.
- **M2. 한 Work의 생애 (자동 없음, 그림자만).** 계약 도구, 자유 구현, 증거 계기 셋, 독립 리뷰, 사람 머지를 잇는다. 07, 10, 14, 40, 43, 44, 45에 리팩터링 18~20과 설계 33·34를 더해 v2 자율, 맨 CLI와 n≥5로 견준다. 변형으로 근거 확인 초안, 리뷰 뺌을 함께 돌린다. 형식 되돌림 0회, 사람 차례, 44의 이득, tests 점수를 확인한다. 여기서 유형 고르기를 없앨지 정한다.
- **M3. Work 사이, 하나씩.** 래칫과 빚 기록(핵) → 곁들일 정리 → 규칙 승격 순서로 하나씩 켠다. 하나를 켤 때마다 M0b 판에서 켠 쪽과 끈 쪽을 견준다. 같으면 기본에서 뺀다.
- **M4. 그림자 실적.** 세션 커밋 트레일러, 머지 뒤 30일 추적, 조건별 그림자 일치율, 모델·버전 칸, 관문 5회 반복 안정성. relay-v3 레포 자신부터 돌린다.
- **M5. 좁은 자동 조건 하나에서 자동 머지 (사용자가 허용한 뒤에만).** 서버 쪽 브랜치 보호와 필수 검사를 확인한 뒤 연다. 하루 상한과 전체 끄기 스위치를 함께 둔다. E-auto와 그림자 실적이 8.4에 걸리지 않을 때만 연다.

## 부록 A. 낱말

| 낱말 | 뜻 |
|---|---|
| 계약 | v2의 의도. 완료조건 줄(종류·근거·예시·확인), 비목표, 사람만 아는 규칙 |
| 증거 묶음 | 앱이 정해진 SHA에서 계산한 결과 모음. 세션은 쓰지 못한다 |
| 래칫 | '나빠지지 않음'만 강제하는 지표 비교(merge-base ↔ head) |
| 빚 장부 | 레포 안 `.relay/debt/`. anchor가 붙은 정리할 거리. 다음 Work 초안에 닿는다 |
| 사람 경로 | 늘 사람에게 가는 파일·경로(지킴 파일 + 보호 경로) |
| 그림자 기록 | 자동이었으면 했을 결론을 적기만 하는 것 |
| 자동 조건 | diff에서 계산하는 술어. 채우면 자동 머지 후보 |
| 수용 시험 | 계약의 예시 자료를 읽어 줄을 확인하는 시험. 머지되면 평범한 레포 시험이 된다 |
| 곁들일 정리 | 이번 Work가 건드릴 경로에 걸린 빚 항목. 계약 초안에 후보로 뜨고 사람이 받거나 뺀다 |
| 장치 등록부 | 장치마다 가정·비용·지표·끄는 조건·상태를 적은 표(`docs/devices.md`) |
