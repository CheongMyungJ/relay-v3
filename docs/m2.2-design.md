# M2.2 설계: M2.1 평가에서 남은 마찰

- 상태: 설계(2026-11-06). 사용자 결정(✅ 2026-11-05): 큰 평가 없이 시험과 작은 시범으로 확인한 뒤 M3로 간다.
- 근거: [M2.1 보고](experiments/m2.1/report.md) 6절, [result.md](experiments/m2.1/result.md)의 판정, 판정 에이전트가 적은 마찰(봉인 셋과 설계 셋).
- 방향: 단계를 더하지 않는다. 끄는 조건에 걸린 장치는 뺀다(원칙 5). 새 장치는 없고, 있던 장치(V23, V25, V26)의 모양만 고친다.

## 1. 무엇을 바꾸나

| 결정 | 무엇 | 근거(M2.1) |
|---|---|---|
| V32 | 제출 때 기준 확인(V28)을 뺀다 | 확인이 돈 제출 18%(40 Work). 끄는 조건(20% 아래)에 걸렸다. 세션은 대개 승인 뒤에 시험을 쓴다 |
| V33 | 지킴 시험이 기준에서 불러지지 않으면, 고칠 길을 사실에 붙인다 | 지킴 줄 '증거 없음'이 39, 19, 40에서 되풀이됐다. 되먹임을 받은 세션은 시험을 기준 API만 쓰는 파일로 옮겨 고쳤다(39에서 3/3) |
| V34 | 같은 값을 박아 쓴 태그 시험은 '예시와 시험 불일치'가 아니다. 계약 예시는 값으로 쓴다 | 47, 09, 14, 07에서 이 지적이 상자를 띄웠고, 사람은 매번 [그래도 끝내기]로 넘겼다. 계약 예시가 글이라 세션이 값으로 읽지 못했다 |

## 2. 항목

**V32 제출 때 기준 확인을 뺀다.** `engine/probe.ts`, `main/works-probe.ts`, core `probeVerdicts`, 렌더러의 기준 배지와 요약 줄, `WorkRecord.probe`·`WorkView.probe`, 지침의 제출 때 확인 사실을 지운다. 지침의 '지킴 시험은 기준에 있는 API만 쓴다'는 사실로 남긴다(V33이 쓴다). 등록부의 V28 줄은 상태를 '뺌'으로 두고 M2.1의 값을 남긴다. core에서 줄이 줄어 상한에 여유가 생긴다.

**만든 것(2026-11-06).** 위대로 지웠다. 설계가 정하지 않은 곳과 작게 바꾼 곳은 아래다.
- 지운 것: `engine/probe.ts`, `main/works-probe.ts`, `renderer/src/probe.ts`(머리 한 줄 `probeSummary`, 꼬리표 `probeBadge`)와 그 CSS, core `probeVerdicts`와 `ContractProbe`, `WorkRecord.probe`·`WorkView.probe`·`ContractDesk.shownProbe`, events.jsonl의 `probe` 기록, 지침 §3의 제출 때 확인 문단. 시험은 [단위] `probe.test.ts`·`renderer-probe.test.ts`, [흐름] `probe.test.ts`·`works-probe.test.ts`를 지웠다.
- V28이 함께 바꾼 것도 V28 앞으로 돌렸다: `ExampleEvidence.message`(확인만 썼다)를 지우고, lines.ts의 `fileFailures`는 경로만, `loadFailure`는 `'same_file' | 'some_file' | null`을 돌려준다(판정은 그대로). engine `resolveRefs`·`loadQuality`·`readDiff`(check.ts)와 `overlayPaths`(judge.ts)는 다시 모듈 안 함수다. src/core는 4,903줄에서 4,863줄이 됐다.
- 남긴 것: 지침 §1의 'relay also runs the tests of change and keep lines on the base, so a keep test can use only what the base already has.'(V33이 쓴다). V29의 증상 곁 지킴 줄 문장은 제출 때 확인('If its tagged tests are committed when you submit, the check in §3 runs them on the base')을 가리켰으므로 'The evidence runs its tagged tests on the base too; an example that fails there shows that the behavior is part of what the request reports.'로 고쳤다. §3은 V28 앞의 글('checks the contract. If it returns errors, fix the contract and call it again.')로 돌렸다.
- 계약 호출의 차례 번호(cancelled, superseded)는 남겼다. V28의 긴 확인 때문에 넣었지만, 근거 확인(git)과 submit의 초안 예시 자료 쓰기도 기다림이라 그 사이 끊긴 호출이나 뒤 호출에 밀린 호출이 상태를 덮을 수 있다. submit은 근거 확인 뒤와 초안 쓰기 뒤에, request_contract_change는 근거 확인 뒤에 본다. 그 시험은 지운 `works-probe.test.ts`에 있었으므로 [흐름] `works-contract.test.ts`에 새로 뒀다(잠금 없이 근거 확인의 기다림으로).
- 옛 work.json: M2.1 빌드가 남긴 `probe` 칸은 `upgradeWork`가 읽을 때 버린다(저장하면 사라진다).
- 시험: [흐름] `works-contract.test.ts`(시험을 먼저 커밋하고 기준에서도 통과하는 바뀜 예시로 내도 승인을 기다리고 `probe` 기록·칸이 없음, 끊긴 제출 cancelled·밀린 제출 superseded), [단위] `instructions.test.ts`(남는 사실과 지운 문단), `work-exports.test.ts`(옛 probe 칸을 버림). [스모크]는 세션이 시험을 먼저 커밋하고 내는 흐름을 그대로 두고, 계약 판에 기준 결과의 한 줄과 꼬리표가 없음을 본다. `npm run test:replay`는 그대로 통과한다(관문은 바뀌지 않음).
- 남는 것: relay-v2 평가 도구(`app/eval`)는 M2.1 지표로 events의 `probe` 기록을 센다. 이 빌드에는 그 기록이 없으므로 이 빌드로 돌린 실행에서는 V28 지표가 0으로 나온다(작은 시범은 V28을 재지 않으므로 도구는 고치지 않았다. relay-v2는 이 일의 범위 밖이다).

**V33 지킴 시험이 기준에서 불러지지 않을 때.** 지킴 줄이 '증거 없음'이고 까닭이 '기준에서 시험 파일을 불러오지 못함'이면, 그 사실의 글에 고칠 길을 붙인다: '지킴 시험은 기준에 있는 API만 불러야 한다. 새 함수를 부르는 시험과 다른 파일에 둔다.' 이 글은 [증거]와 상자, 되먹임 파일(V24), `relay_check`에 같은 꼴로 간다. 판정 규칙은 바꾸지 않는다(기준 확인 없이 met으로 보지 않는다).

**만든 것(2026-11-06).** 위대로 붙였다. 설계가 정하지 않은 곳과 작게 바꾼 곳은 아래다.
- 판정이 고칠 길을 칸으로 든다: `LineVerdict.fix?: { kind: 'keep_base_api'; examples: string[] }`(types.ts `LineFix`). 사람용 글(한국어)은 detail 끝에 붙고(core `lineFixText`), 세션에 가는 글(영어)은 `feedbackFacts`가 이 칸에서 쓴다(지금까지대로 사람용 detail은 세션에 넣지 않는다). 그래서 [증거]의 줄 판정은 렌더러를 고치지 않고 detail로 보인다.
- 지킴 줄의 detail: 불러오지 못한 예시를 '기준에서 시험 파일을 불러오지 못함: C3.1'로, 다른 까닭의 예시를 '기준에서 통과를 확인하지 못함: C3.2(skipped)'로 나눠 적은 뒤 고칠 길을 붙인다. 불러오지 못했는지는 바뀜 줄과 같은 `loadFailure`로 본다. 파일을 모르는 러너(node:test)는 파일 단위 실패가 하나라도 있으면 그렇게 보고 '(파일은 확인하지 못함)'을 적되, 고칠 길도 붙인다(같은 까닭일 가능성이 크고 판정은 그대로다).
- 상자의 열린 것(관문의 줄 사실)은 detail을 100자로 자른다. 고칠 길이 잘리지 않게 까닭만 자르고 고칠 길은 그대로 붙인다(`gate.ts` `lineDetail`).
- 영어 글: 'No base result for C3.1: a test file failed to load on the base. A keep test may call only the API the base already has: put it in a different file from the tests that call new functions.' 되먹임 파일과 `relay_check`의 `facts`가 같은 `feedbackFacts`를 쓰므로 같은 꼴이다. `relay_check`의 `lines`에는 `fix`를 더하지 않았다(사실에 이미 있다).
- 바뀜 줄에는 붙이지 않는다: 바뀜 줄은 기준에서 불러오지 못함을 기준 실패로 보고 met이다(지금과 같다).
- 시험: [단위] `lines.test.ts`(vitest 같은 파일: 증거 없음 그대로이고 detail·fix, node:test와 다른 까닭이 섞인 줄, 다른 파일이거나 파일 단위 실패가 없으면 붙이지 않음, 바뀜 줄에는 없음), `gate.test.ts`(긴 까닭은 자르고 고칠 길은 남김), `review-feedback.test.ts`(영어 고칠 길, 한국어 detail은 넣지 않음). [흐름] `check-keep-load.test.ts`(새 파일. `check.test.ts`는 600줄 상한에 닿아 따로 뒀다. 실제 node:test에서 지킴 시험이 새 함수를 부르는 시험과 한 파일에 있으면 기준에서 불러지지 않아 fix가 붙고, 열린 것과 `feedbackFacts`에 같은 고칠 길). 렌더러를 바꾸지 않아 [스모크]는 돌리지 않았다. `npm run test:replay`는 그대로 통과한다(판정과 관문의 결론은 그대로).

**V34 예시와 시험 불일치의 뜻.**
- 리뷰 프롬프트: 태그 시험이 승인된 예시의 입력과 출력(오류)을 그대로 확인하면, 값을 예시 파일에서 읽지 않고 시험에 적었어도 불일치가 아니다. 입력·출력·오류가 승인된 예시와 다르거나, 그 예시를 확인하는 시험이 없을 때만 `example_test_mismatch`다. 프롬프트 판을 올린다.
- 지침: 예시의 입력과 출력은 시험이 그대로 쓸 수 있는 값(JSON)으로 쓴다. 글로만 쓸 수 있는 예시는 note에 둔다.
- V27(앱이 예시 자료를 씀)은 그대로다. 커밋된 예시 파일이 승인본과 다르면 여전히 사람 머지 사실이다.

**V35 넘기고 다시 걸기.** 상자의 [세션에 넘기기]는 지적과 사실을 세션에 보내고(V24 꼴), 끝을 '고친 뒤 끝냄'으로 다시 건다. 세션이 쉬고 새 head의 증거와 리뷰에 열린 것이 없으면 Work가 끝난다(V25의 걸린 끝과 같은 길). 열린 것이 있으면 상자가 다시 뜬다. 사람은 [취소]로 언제든 푼다. [증거] 탭의 [세션에 넘기기]는 끝을 걸지 않는다(지금과 같다).

**V36 몰아 두기 5초.** `DEBOUNCE_MS`를 5초로 줄인다. 미리 리뷰의 상한(Work당 4번, 내보내기마다)은 그대로라 리뷰가 늘어날 수 있는 만큼은 막힌다. 등록부 V4(V23) 줄의 끄는 조건은 그대로다.

**V37 끝난 뒤의 메모.** 걸어 둔 끝이나 한 번 끝이 메모(관문 사실이 아닌 지적)를 남기고 끝나면, 끝난 Work의 화면에 '끝낼 때의 메모 n개'를 접어 보인다. 끝을 막지 않는다. `ended` 사건에 `memos` 수를 더한다.

## 3. 확인

- 각 항목은 맞는 층에 시험을 둔다. `npm run check`, [스모크], `npm run test:replay`(관문이 바뀌지 않음을 본다)가 통과해야 한다.
- 작은 시범(판정에 넣지 않음): M2.1 평가 도구로 relay3-m21 빌드를 39, 47, 09에서 1번씩 돌려, 넘기고 다시 걸기(V35), 몰아 두기 5초(V36), 끝난 뒤 메모(V37)가 화면에서 도는지 본다. 결과는 `docs/experiments/m2.2/pilot.md`에 적는다.

## 4. 하지 않는 것

- 지킴 시험을 기준 확인 없이 met으로 보지 않는다(V33은 글만 붙인다).
- 예시 자료를 앱이 커밋하지 않는다(V20, V27 그대로).
- 큰 평가를 다시 돌리지 않는다(사용자 결정).
