두 쪽 모두 경로별 시험을 더했다. A는 동시 실행, 선점 해제, 이틀 연속 일정까지 다룬다.
  - 경험 전체 relay3-m21 (relay-v3 M2.1 8, relay-v3 M2 + 미룬 고침 6) — A가 시간, 차례, 입력량 모두 적었고 버튼으로 지적을 넘겨 흐름이 매끄러웠다. B는 증거 불일치와 반복된 리뷰 때문에 직접 옮겨 쓰는 일이 늘었다. 확신 면에서만 B가 약간 앞섰다.
- 판정 #4: 결과 선호 relay3-m21 — 두 결과 모두 같은 두 원인을 고쳤다. 하나는 요약 키에 runId가 들어가서 재실행 때 키가 달라지던 것이다. 다른 하나는 제한 시간을 넘긴 성공을 실패로 보고 다시 보내던 것이다. 키에서 runId를 빼고, 보내기 전에 키를 선점(claim)하게 했고, 느린 성공은 slow로만 표시한다. 숨긴 시험은 둘 다 모두 통과했다.

A는 일시 오류로 못 보낸 사람이 남으면 스케줄러가 최대 maxAttempts번까지 다시 돌게 해서, 못 보낸 요약을 다시 보내야 한다는 요구까지 챙겼다. 시험도 새 파일 test/digest-duplicates.test.js에 경로별로 나눠 썼다. 재실행, 다른 시각, 느린 성공, 재시도, 소진 후 재실행, 다음 tick, 동시 실행, 선점 해제를 다루므로, 경로마다 근거를 보고 싶다는 요청에 맞는다. 단점은 .relay/examples JSON 파일을 더한 것과 선점에 만료 기한이 없다는 점이다.

B는 선점에 임대 만료(claimLeaseMs)를 두었다. 응답 지연(ESOCKETTIMEDOUT)은 나간 것으로 보고 다시 보내지 않는데, 이는 메일 서버 담당자 말과 맞는 세심한 처리다. 하지만 기대 밖 파일 src/notifier.js를 바꿨고, 가짜 전송에 새 오류 종류를 더했다. 시험은 test/digest.test.js와 helpers 수준이라 경로별 근거가 A보다 약해 보인다.

전체적으로 A가 시험 근거와 요구 범위 면에서 낫다.
  - 경험 전체 relay3-m21 (relay-v3 M2.1 7, relay (자율 유형) 6) — A가 수고와 명확성에서 앞선다. B는 확신과 복구에서 낫지만 정정과 직접 지적이 필요했다. 전체로는 A가 근소하게 낫다.
- 판정 #5: 결과 선호 relay3-m2p — 두 결과 모두 키에서 runId를 빼고 제한 시간 초과를 실패로 보던 동작을 고쳐 숨긴 시험을 통과했다. 하지만 A는 `has` 확인 뒤 `await`로 보내는 구조라, 서버 두 대가 동시에 돌 때(1분쯤 차이 나는 중복) 둘 다 보낼 수 있고 이 경로는 시험도 없다. B는 보내기 전에 키를 선점(`claim`)하고, 실패하면 풀며(`release`), 크래시로 남은 선점은 TTL 뒤 풀리게 했다. 동시 실행, 공유 기록을 쓰는 notifier 두 개, 실패 뒤 재실행, 선점 만료를 시험으로 확인했고, 느린 성공은 보낸 것으로 보되 실제 실패는 재시도하는 요구도 지킨다. B는 README와 `notifier.js`를 건드려 범위가 조금 넓지만, 공유 기록 연결과 문서화를 위한 변경이라 정당하다.
  - 경험 전체 relay3-m21 (relay-v3 M2.1 7, relay-v3 M2 + 미룬 고침 6) — 사용 경험은 A가 낫다. 수고가 훨씬 적고 흐름이 매끄러웠다. B는 동시 실행 원인까지 잡고 근거도 더 풍부했지만, 사람이 직접 짚어서 넣어야 했고 C3 혼란과 긴 대기가 있었다.
- 판정 #5: 결과 선호 relay3-m21 — A는 두 원인을 모두 고쳤다. 하나는 키에 들어 있던 runId를 뺀 것이고, 다른 하나는 성공한 느린 발송을 시간 초과 오류로 바꾸던 것을 없앤 것이다. 숨긴 시험 3개가 모두 통과했고 바뀐 범위도 작다. 실제 시간 초과 오류(ETIMEDOUT)는 그대로 재시도하므로 못 나간 요약은 다시 보낸다. 시험은 경로마다 근거를 남기도록 짰다. 약점은 동시에 도는 두 서버를 막는 선점 장치가 없다는 점이다. 키는 발송 후에야 기록되므로 완전히 동시에 시작하면 중복이 남을 수 있다.
B는 원인 수정은 같고 키 선점(claim)까지 넣어 동시 실행 쪽은 더 꼼꼼하다. 그러나 응답 시간 초과(SendTimeoutError)를 전부 '발송됨'으로 처리해서, 실제로 못 나간 요약을 다시 보내야 한다는 요구를 어겼다. 숨긴 시험 '요약 실패는 재시도'가 실패했다. 이 때문에 요약이 누락될 위험이 있다. 어댑터 분류와 fake 전송을 바꾼 것도 범위를 넓혔다.
  - 경험 전체 relay3-m21 (relay-v3 M2.1 7, relay (자율 유형) 6) — A는 시간과 입력이 적었고, 승인 전에 경로별 근거를 보고 독립 리뷰의 지적까지 반영했다. B는 선택지를 통한 통제는 좋았지만 수고가 더 컸다. 마지막 확인이 터미널 글에 의존했고, 중간에 잘못된 방향을 사람이 직접 잡아야 했다.

### 사람 역할의 말

- [relay3-m21#1 좋음] 계약 단계에서 서버 두 대 경로를 짚자 계약에 반영되었다. 경로마다 예시와 시험이 붙어서 한 통만 나가는지 근거를 볼 수 있었다.
- [relay3-m21#1 불편] 끝내기를 누르자 리뷰 지적 4개가 있는데도 열린 것 없이 바로 끝났고, 지적 내용은 못 봤다. 계약을 다시 내는 과정(C6 종류 변경)도 처음엔 낯설었다.
- [relay3-m21#2 좋음] 에이전트가 원인 두 가지를 짚어 방향을 물었고, 계약과 줄 판정이 '기준에서 실패, 결과에서 통과'로 보여서 경로마다 근거를 확인하기 쉬웠다.
- [relay3-m21#2 불편] 리뷰 지적이 남은 채 Work가 끝났다. 끝내기를 두 번 눌러야 했고, 리뷰가 도는 동안 기다리는 시간이 길었다.
- [relay3-m21#3 좋음] 에이전트가 코드만 보고 짐작하지 않고 사람만 아는 것(느린 응답은 메일이 나간 것으로 보는지, 못 보낸 요약은 어떻게 다시 보내는지)을 먼저 물었다. 계약에 원인 두 가지와 줄별 예시, 비목표가 적혀 있어 승인하기 쉬웠고, 증거 탭에서 기준은 실패하고 결과는 통과하는 것까지 볼 수 있었다.
- [relay3-m21#3 불편] 리뷰 지적이 시험 값을 예시 파일에서 읽느냐 같은 형식 문제 위주였다. 끝내기를 누르면 걸림, 열린 것 상자, 새 커밋 때문에 다시 걸림이 이어져서 단계를 따라가기 번거로웠다. 마지막에 남은 지적은 내가 그냥 받아들이고 끝냈다.
- [relay3-m21#4 좋음] 계약에 원인과 경로별 예시가 줄마다 나와 있어서 서버 두 대 동시 실행 같은 빠진 경로를 승인 전에 짚을 수 있었다. 줄마다 충족 판정이 붙은 증거 탭도 도움이 됐다.
- [relay3-m21#4 불편] 리뷰가 돌 때마다 새 지적이 나와서 끝내기를 세 번 눌렀다. 마지막에 남은 지적은 예시가 글이라 값을 읽을 수 없다는 형식 문제였는데, 그대로 두고 끝냈다.
- [relay3-m21#5 좋음] 계약에 원인 두 가지와 경로별 예시(느린 성공, 다른 runId로 재실행, 실제 실패 재발송)가 근거와 함께 나와서, 승인하기 전에 무엇을 고치는지 알 수 있었다. 독립 리뷰가 시험이 예시 값을 읽지 않는다는 점을 잡았고, 그것을 세션에 넘겨 고치게 한 것도 좋았다.
- [relay3-m21#5 불편] 계약이 영어로 길게 나와서 읽는 데 시간이 걸렸다. 끝내기를 두 번 눌러야 했고, 리뷰를 기다리는 동안 결론이 계속 '사람 머지'로 떠 있어서 무슨 뜻인지 헷갈렸다. 끝낼 때 PR 없이 '머지 없이 끝남'이 되는 것도 어색했다.
- [relay3-m2p#1 좋음] 세션이 원인 두 가지를 먼저 짚고, 메일 서버 늦은 응답처럼 내가 아는 사실을 물어서 경로별 계약과 시험으로 만들어 준 점이 좋았다.
- [relay3-m2p#1 불편] 증거 탭에 '예시 자료가 승인된 예시와 다름'이나 'C4 못 미침' 같은 기계적인 이유가 떠서 내가 터미널에서 세션에게 고치라고 시켜야 했다. 세션도 이유를 모르겠다고 했다.
- [relay3-m2p#2 좋음] 계약에 경로별 원인과 "한 통만 나간다는 근거"가 적혀 있어서 승인 전에 빠진 경로(서버 두 대)를 짚고 고치게 할 수 있었다. 독립 리뷰가 실제 위험(release 주인 확인)도 잡아 줬다.
- [relay3-m2p#2 불편] 예시 문구가 계약과 글자 그대로 달라서 증거가 전부 '못 미침'으로 나왔고, 이유가 "예시 자료가 다름"뿐이라 원인을 추측해야 했다. 끝내기 뒤 새 커밋이 생길 때마다 다시 눌러 기다리는 것도 번거로웠다.
- [relay3-m2p#3 좋음] 계약에 경로별 예시가 있어서 승인 전에 무엇이 고쳐지는지 알 수 있었다. 시간 초과 경로가 실제로 2통 나간다는 재현을 에이전트가 직접 보여 줬고, 계약 변경도 받아들이기와 거절하기로 처리할 수 있었다.
- [relay3-m2p#3 불편] 처음에는 예시 json이 승인된 예시와 달라서 증거가 전부 못 미침으로 나왔고, 내가 짚고 나서야 고쳤다. 명령 하나가 1분 넘게 걸리는 동안에는 진행 중인지 멈춘 건지 알기 어려웠다. 끝내기 뒤에 커밋이 생기면 끝내기를 다시 눌러야 하는 것도 번거로웠다.
- [relay3-m2p#4 좋음] 계약 단계에서 원인과 경로별 예시(느린 성공, 타임아웃 오류, 동시 실행, 재실행)를 먼저 확인하고 승인할 수 있었다. 증거 탭이 시험을 기준 커밋과 비교해 판정해 줘서 경로마다 근거를 볼 수 있었다.
- [relay3-m2p#4 불편] 증거 탭의 '예시가 승인된 예시와 다름', 'keep 줄이 기준에서 실패함' 같은 판정 때문에 계약과 증거를 맞추는 데 한 바퀴를 더 돌았다. 리뷰 지적도 내가 직접 세션에 옮겨 말해야 했고, 지적이 라운드마다 새로 나와 길어졌다.
- [relay3-m2p#5 좋음] 계약에 줄별 근거와 예시가 있어 무엇을 고치는지 승인 전에 알 수 있었다. 계약 변경 절차 덕에 서버 두 대 동시 실행 같은 범위 밖 원인도 짚어서 넣을 수 있었다.
- [relay3-m2p#5 불편] C3가 못 미침으로 나왔을 때 이유가 화면에 모호하게 나왔고 세션도 몰랐다. 변경 코드를 직접 열어 예시 파일이 계약과 다른 것을 찾아야 했다. 처음 계약은 동시 실행을 범위 밖으로 두었는데, 내가 짚어서 묻기 전에는 에이전트가 먼저 꺼내지 않았다.
- [relay@auto#1 좋음] 의도 정리에서 에이전트가 코드를 읽고 중복 경로를 구체적으로 짚으며 선택지로 물었다. 서버 두 대 경로가 빠졌을 때 짚어 말하니 완료조건에 반영됐다. 완료조건마다 확인 방법이 붙어 있어 근거를 보기 쉬웠다.
- [relay@auto#1 불편] 처음 의도 초안에는 서버 두 대 동시 실행이 빠져 있어 내가 따로 짚어야 했다. 자율 단계에서는 중간 승인 없이 한 번에 끝나서, 결과는 diff로만 확인했다. 진행 중에는 터미널에 "Pontificating" 같은 문구만 떠서 무슨 일을 하는지 알기 어려웠다.
- [relay@auto#2 좋음] 의도 정리 단계에서 선택지로 범위와 재발송 방식을 먼저 물어 주었다. 내가 짚으면 에이전트가 바로 인정하고, 수정 전 테스트 실패까지 확인해 경로별 근거표로 보여 주었다.
- [relay@auto#2 불편] 처음 요약에서는 서버 두 대 경로와 어댑터가 응답 대기 중 오류를 던지는 경로가 빠져 있었다. 내가 diff를 읽고 두 번 짚은 뒤에야 다뤄졌다. 자율 유형이라 중간 승인 없이 진행돼, 직접 확인하지 않았다면 놓쳤을 것이다.
- [relay@auto#3 좋음] 의도 정리에서 원인 후보를 코드로 짚고, 범위와 시간 초과 처리를 선택지로 물어서 내가 아는 사실(메일 서버 담당자 말)을 반영할 수 있었다. 완료조건마다 확인 방법이 붙어 있어 경로별로 근거를 보기 쉬웠다.
- [relay@auto#3 불편] 자율 단계는 승인 없이 끝까지 진행되어, 코드를 diff로 직접 열어 보기 전에는 결과가 맞는지 판단하기 어려웠다. 완료 화면의 판정표는 비어 있었다. 터미널 선택지에서 직접 입력으로 답하는 방법도 조금 헷갈렸다.
- [relay@auto#4 좋음] 의도 정리에서 범위를 선택지로 물어 줘서 방향을 쥘 수 있었다. 끝에는 경로별 시험 표와 수정을 되돌려 본 검증까지 보여 줘서 믿을 만했다.
- [relay@auto#4 불편] 메일 서버가 응답이 늦어도 메일을 보낸다는 점은 묻지 않아서 내가 직접 짚어야 했다. 운영 구성 질문은 내가 답하기 전에 가정으로 채워져 있었고, 질문 화면 문구와 내가 고른 범위가 어긋나 정정할 때도 있었다.
- [relay@auto#5 좋음] 의도 정리에서 선택지로 범위, 재발송, 다중 서버를 짚어 물어 줘서 방향을 내가 정할 수 있었다. 원인 두 가지와 바뀐 내용, 남은 위험을 경로별로 설명해 줬다.
- [relay@auto#5 불편] 자율 유형은 승인 대기와 완료 화면이 없어서 마지막 확인을 터미널 글만 보고 해야 했다. 코드 diff는 열어 보지 않았다. 시간 초과 건을 unknown으로 두는 결정은 내가 짚기 전에는 그대로 나갈 뻔했다.

#### friction이 높았던 차례

- relay3-m2p#2 차례 8 (friction 2): 예시 파일이 승인한 계약 문구와 달라 판정이 못 미침이다. 맞춰 달라고 한다.
