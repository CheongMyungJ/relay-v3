한계도 하나 있다. 두 결과 모두 모듈별로 나뉜 커밋이나 PR이 있는지는 기록에 나와 있지 않아 이 점은 비교할 수 없었다.
  - 경험 전체 relay3-m21 (relay-v3 M2.1 7, relay-v3 M2 + 미룬 고침 7) — 수고는 비슷했다. B는 리뷰 지적을 세션에 넘겨 고치고 재검토까지 받아 명확성·복구·확신에서 앞섰다. A는 계약 단계의 질문과 통제가 좋았지만 지적을 남긴 채 끝났고, 후속 커밋 때문에 모듈별 커밋이 흐려졌다.
- 판정 #5: 결과 선호 relay@auto — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고, 핵심 로직은 거의 같습니다. 환불(음수)은 합계에서 빠지고, 기준값과 같은 재고도 부족으로 보며, 쉼표가 든 이름은 따옴표로 감쌉니다.

A는 변경이 필요한 파일(src 세 개와 test 세 개)만 건드렸습니다. 시험은 코드에 바로 적혀 있고 범위가 넓습니다. 환불 포함 합계, 입력 순서와 무관한 정렬, 빈 입력, 잘못된 입력의 예외, 재고 경계와 이름순 정렬, 원본 배열 유지, CSV 따옴표 처리, 이메일 마스킹 때문에 로컬 부분이 노출되지 않는 경우까지 확인합니다. monthlyTotals에 입력 검증을 넣은 것은 요청에 없던 동작입니다. 다만 이상한 날짜나 금액을 조용히 넘기지 않는 쪽이라 해가 되지 않고 합리적입니다.

B는 .relay/examples/*.json이라는 도구용 산출물을 저장소에 넣었고, 시험이 이 파일을 읽어 씁니다. 그래서 시험을 읽기 어렵고, 시험이 레포 밖 산출물에 묶입니다. test/keep.test.js는 기존 함수를 그대로 확인하는 시험인데, 'still pass'라는 문자열을 단언하는 무의미한 줄이 들어 있습니다. B의 monthlyTotals 시험은 두 건뿐이고, 재고 시험도 A보다 적습니다. 반면 B는 이메일 마스킹의 엣지 케이스(이모지, 도메인이 없는 이메일)를 더 다룹니다.

두 결과 모두 모듈별로 변경이 나뉘어 있어 리뷰어별 분리 선호에는 비슷하게 맞습니다. 정확성은 비슷하지만 범위, 코드와 시험의 품질은 A가 낫습니다.
  - 경험 전체 relay3-m21 (relay-v3 M2.1 7, relay (자율 유형) 6) — B는 처음부터 모듈별 커밋을 반영했고, 계약 예시와 리뷰로 신뢰 근거를 더 얻었다. 대기와 리뷰 판단 부담이 있었지만 A의 재요청과 확인 부족보다 나았다.
