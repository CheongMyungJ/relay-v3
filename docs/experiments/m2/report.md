# M2 평가 보고

2026-11-05. 숫자와 계산의 원본은 [result.md](result.md)(규약대로 낸 표), 도중에 본 것은 [log.md](log.md)에 있다. 이 글은 그것을 쉬운 말로 다시 쓴 것이다.

## 한 줄 요약

**새 앱(v3)은 결과의 질은 옛 앱(v2)과 비슷했지만, 사람이 손을 훨씬 많이 써야 했다.** 그 까닭은 대부분 고칠 수 있는 절차의 마찰이었다. 그리고 사람이 결과를 확인하지 않으면 어느 도구든 결과가 나빠졌다. 그래서 다음은 '더 많은 장치(M3)'가 아니라 '마찰 줄이기(M2.1)'다.

## 1. 무엇을 견줬나

같은 일을 네 가지 방식으로 시켰다.

| 이름 | 무엇 |
|---|---|
| **v3** (relay3) | 이번에 만든 새 앱. 계약을 사람과 맞추고, 앱이 시험을 돌려 증거를 모으고, 독립 리뷰어가 따로 본다 |
| **v3 리뷰 끔** (relay3-noreview) | 같은 새 앱에서 독립 리뷰만 끈 것. 리뷰가 값을 하는지 보려고 |
| **v2 자율** (relay@auto) | 옛 앱의 자율 모드 |
| **맨 CLI** (cli) | 앱 없이 Claude Code만 쓴 것 |

- 일은 9가지다. 버그 두 개 고치기, 시간대 버그, 원인이 둘인 중복 알림 버그, 리팩터링, 라이브러리 셋 만들기, 대충 쓴 요청 등이다. 방식마다 5번씩 돌렸다.
- 사람 역할은 AI가 맡았다. 사람 역할은 요청을 넣고, 질문에 답하고, 계약을 승인하고, 결과를 보고 끝낸다. 몇몇 사실은 **물어볼 때만** 알려 준다(예: "round는 0.5를 0에서 먼 쪽으로 올린다").
- 결과가 맞았는지는 **숨긴 시험**으로 본다. 작업하는 쪽은 이 시험을 볼 수 없다.
- 따로, "사람이 손을 떼면 어떻게 되나"도 봤다(**손 뗀** 쪽). 사람 역할이 결과를 확인하지 않고, 에이전트가 끝났다고 하면 그대로 받아들인다. 질문에는 평소처럼 답한다. v3와 맨 CLI만 5가지 일에서 돌렸다.
- 모두 230번 돌렸다. 그중 1번은 앱이 뜨지 않아(도구 문제) 뺐다.

## 2. 무엇을 쟀나

| 지표 | 쉬운 뜻 |
|---|---|
| 숨긴 시험 통과율 | 결과가 실제로 맞았나. 가장 중요하다 |
| 시험 점수(1~5) | 판정 AI가 매긴, 작업하는 쪽이 쓴 시험의 질 |
| 사람 차례 | 사람이 화면에서 무언가 해야 했던 횟수(승인, 답, 기다림, 끝내기 등) |
| 걸린 시간 | 사람 역할이 생각하는 시간을 뺀 작업 시간 |
| 토큰 | 에이전트와 리뷰어가 쓴 양. 비용에 가깝다 |

## 3. 결과

### 결과의 질과 수고 (9가지 일의 평균)

| | v3 | v3 리뷰 끔 | v2 자율 | 맨 CLI |
|---|---|---|---|---|
| 숨긴 시험 통과율 | 88% | 87% | 91% | 87% |
| 시험 점수 | 4.1 | 3.9 | 4.1 | 3.2 |
| 사람 차례 | **25.7** | 18.2 | 14.2 | 6.1 |
| 걸린 시간(분) | 9.9 | 6.3 | 5.4 | 3.0 |
| 토큰(천) | 1,143 | 795 | 889 | 557 |

- **통과율은 넷이 비슷했다.** 차이는 이번 횟수로는 우연과 가를 수 없을 만큼 작다.
- **v3는 사람 차례가 v2 자율보다 11.5번 많았다.** 이 차이는 우연이 아니다.
- 시험의 질은 앱을 쓴 세 쪽이 맨 CLI보다 분명히 나았다.

### 사람이 손을 떼면 (5가지 일의 평균)

| | 평소 | 손 뗌 |
|---|---|---|
| v3 통과율 | 79% | **52%** |
| 맨 CLI 통과율 | 76% | **56%** |

둘 다 크게 떨어졌다. 사람의 확인이 실제로 틀린 것을 잡고 있었다는 뜻이다.

## 4. 네 질문과 답

평가 전에 질문 넷과, 결과가 어떻게 나오면 무엇을 할지를 정해 두었다([protocol.md](protocol.md) 5절). 결과를 보고 규칙을 바꾸지 않으려는 것이다.

| 질문 | 답 | 그래서 |
|---|---|---|
| **1. 독립 리뷰가 값을 하나?** | 시험의 질을 조금 올렸다(4.1 대 3.9). 통과율 차이는 가를 수 없다. 대신 사람 차례가 7.5번, 시간이 3.6분 늘었다 | 리뷰는 **남긴다.** 다만 비싼 방식을 고친다(M2.1) |
| **2. v3가 v2 자율보다 나은 방향인가?** | 통과율은 가를 수 없고, 사람 차례는 분명히 많다 | 정해 둔 규칙대로 **다음 단계(M3: 여러 Work에 걸친 품질 장치)로 가지 않는다.** 먼저 사람 차례를 줄인다(M2.1) |
| **3. 계약만 사람이 보고 나머지는 AI에게 맡겨도 되나?** | v3 통과율이 79% → 52%로 떨어졌다 | **아직 아니다.** 사람이 결과를 보는 자리를 없애지 않는다 |
| **4. 자동 머지 판단이 믿을 만한가?** | '자동으로 머지해도 된다'고 본 것이 5번뿐이었고, 그중 2번만 맞았다 | 판단하기엔 자료가 적다. **자동 머지는 꺼 둔 채로 둔다** |

## 5. 장면 넷

**① 계약이 반쪽이면 아무도 못 잡는다 (중복 알림 버그, 원인이 둘).**
v3는 5번 중 4번 첫 번째 원인만 찾고 바로 계약을 썼다. 사람은 그 계약을 승인했다. 계약에 적힌 것은 모두 지켜졌고, 리뷰도 문제를 올리지 않았다. 앱은 "자동으로 머지해도 된다"고 판단했다. 그런데 4번 중 3번은 숨긴 시험에서 실패했다. 계약을 기준으로 보는 모든 확인이 계약이 빠뜨린 것은 보지 못한 것이다. 자동 머지를 꺼 두고 기록만 쌓아 두는 까닭이 여기 있다. 맨 CLI는 같은 일에서 5번 중 4번 두 원인을 다 찾았다.

**② 의도를 묻지 않으면 틀린다 (대충 쓴 요청).**
요청에 세부가 없고, 세부는 사람이 물어볼 때만 알려 줬다. 묻지 않는 맨 CLI는 5번 모두 틀렸다. 묻는 쪽(v3, v2 자율)은 대부분 맞혔다. "의도를 분명히 하는 것이 결과를 가른다"는 처음 관찰을 뒷받침한다.

**③ 손을 떼면 묻지 않은 것이 그대로 남는다 (라이브러리 셋, 손 뗌).**
v3 5번 중 4번이 `round(-2.5)`를 −3이 아니라 −2로 계산했다. 세션이 음수 반올림을 묻지 않았기 때문이다. 평소 모드에서는 사람이 계약이나 결과를 보며 바로잡아 5번 다 맞았다. 맨 CLI도 묻지 않았지만, 구현 방식이 우연히 맞았다.

**④ 일을 나누면 절차가 곱절이 된다 (라이브러리 셋).**
사람이 라이브러리마다 Work를 하나씩 만들었다. 그 결과 계약 승인, 리뷰, 끝내기를 세 번씩 했다. v3의 사람 차례는 40.8번으로, v2 자율(15.4)의 두 배를 넘었다.

## 6. v3가 사람 손을 많이 쓴 까닭

사람 차례를 하나하나 분류해 보니(v3 30번 실행, [p3-decomposition.md](p3-decomposition.md)), 대부분 원칙이 요구하지 않는 절차에서 나왔다.

| 까닭 | 실행마다 늘어난 차례 | 고칠 방향(M2.1) |
|---|---|---|
| 일을 Work 여러 개로 나눔 | 약 2.5 | 한 요청은 Work 하나. 단위는 계약 안에서 나눈다 |
| 리뷰 지적을 사람이 손으로 옮기고 다시 끝내기 | 약 1.8 | 계약 안의 지적은 세션에 바로 전한다 |
| 예시 자료 파일을 세션이 손으로 베끼다 틀림 | 약 1.5 | 앱이 승인된 계약에서 파일을 쓴다 |
| 끝내기를 누른 뒤에야 리뷰가 시작돼 기다림 | 약 1.2 | 세션이 쉴 때 리뷰를 미리 돌린다 |
| 끝내기가 늘 두 단계 | 1.0 | 열린 문제가 없으면 한 번에 끝낸다 |
| 계약 예시를 승인 뒤에야 기준에 대 봄 | 약 0.6 | 계약을 낼 때 미리 대 본다 |

평가 중에 버그 셋도 찾아 고쳤다.

- 계약을 바꾸자는 요청에 새 계약이 빠져도 받아 주던 것
- 있던 시험에 표시를 붙이면 '시험이 사라졌다'고 잘못 보던 것
- 예시 하나라도 고치기 전에도 맞으면 '못 미침'으로 보던 것

## 7. 다음

1. **M2.1을 만든다.** 위 표의 고침과, 장면 ①을 막는 두 가지다. 하나는 계약이 요청의 증상을 다 설명하게 하는 것이고, 다른 하나는 리뷰어가 계약만이 아니라 요청도 읽는 것이다. 설계는 [m2.1-design.md](../../m2.1-design.md)에 있다.
2. **작은 평가로 다시 잰다.** 실제 실행 65번이다(사용자 승인). 사람 차례가 v2 자율 수준으로 내려오는지, 통과율이 떨어지지 않는지, 잘못된 자동 판단이 0인지 본다.
3. **바꾸지 않는 것:** 사람이 계약을 승인하고 결과를 보는 자리, 자동 머지 꺼짐.

## 8. 읽을 때 조심할 것

- **사람 역할이 AI다.** 실제 사람은 덜 기다리거나 더 꼼꼼할 수 있다. 사람 차례에는 사람 역할의 버릇(따로 '끝'만 말하는 차례 등)이 조금 섞여 있다.
- **방식마다 일마다 5번이다.** 그래서 작은 차이는 '가를 수 없음'으로 나온다. '같다'가 아니라 '이번 횟수로는 모른다'는 뜻이다.
- **9가지 일 가운데 다섯은 모두가 맞힐 만큼 쉬웠다.** 통과율 차이는 원인이 둘인 버그와 대충 쓴 요청에서만 났다.
- 이 평가는 한 모델(sonnet)에서 했다. 모델이 바뀌면 3번 질문(손을 떼도 되나)의 답도 바뀔 수 있다. 그래서 다시 잴 수 있게 남겨 둔다.
