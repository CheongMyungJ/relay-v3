- 판정 #1: 결과 선호 cli — 두 결과 모두 원인 하나(느리게 성공한 발송을 시간 초과로 보고 재시도하는 문제)만 고쳤다. 같은 이벤트를 다시 받으면 중복 발송되는 두 번째 원인(dedupe/intake)은 손대지 않았다. 숨긴 시험의 "같은 이벤트 재수신"이 둘 다 실패한 이유다. 그래서 correctness는 둘 다 낮다.

차이는 부차적인 부분에서 난다.
- A는 `.relay/examples/*.json` 파일을 새로 만들었다. 요구와 무관한 부산물이라 scope 점수를 깎았다. 시험에는 `t.clock.sleep &&` 같은 어색한 방어 코드도 있다. A의 `decide`는 성공 검사를 앞으로 옮기고 `elapsedMs > timeoutMs`이면 재시도하는 분기를 남겼다. 그래서 느리게 실패한 영구 오류도 재시도될 수 있다.
- B는 `decide`를 정리했다. 성공이면 done, 영구 오류면 give-up, 일시 오류면 재시도 순서다. 경과 시간 기반 분기는 없앴고 이유를 주석에 적었다. 시험은 기존 `notifier.test.js`에 넣었다. 메일과 푸시가 느리게 성공해도 한 번만 가는지, 느린 영구 오류는 재시도하지 않고 일시 오류는 재시도하는지를 확인한다. 사용자가 보고 싶다고 한 근거에 더 가깝다.

둘 다 핵심 결함이 같아서 B를 약간 더 낫게 본다.
  - 경험 전체 cli (relay-v3 6, 맨 CLI 8) — 두 기록 모두 같은 원인을 찾아 고쳤다. B는 적은 수고로 사람이 원한 근거(메일과 푸시 테스트)를 얻었다. A는 방향을 직접 쥐었지만 증거 탭이 설명 없이 미통과로 나와 핵심 선호인 근거 확인이 안 됐다.
- 판정 #2: 결과 선호 cli — A는 원인 두 가지를 모두 고쳤다. 하나는 느리게 성공한 발송을 타임아웃으로 보고 다시 보내던 재시도 정책이다. 다른 하나는 receivedAt처럼 수신 때마다 달라지는 필드가 중복 제거 키에 섞여, 같은 이벤트가 다른 키가 되던 문제다. A는 키를 허용 목록 방식으로 바꿔 이 문제를 막았다. 숨긴 시험 세 개가 모두 통과했고, 재시도 정책과 중복 제거 키를 각각 검증하는 회귀 시험도 더했다. 실패한 발송의 재시도는 그대로 유지했다.

B는 재시도 정책만 고쳤다. 중복 제거 키 문제는 놓쳐서 "같은 이벤트 재수신" 숨긴 시험이 실패했다. 즉 원인이 둘인 버그에서 하나만 고친 셈이다. 시험은 꼼꼼하게 썼지만 재수신 시나리오를 다루지 않는다. 기대 범위 밖의 `.relay/examples` JSON 파일도 추가했는데, 레포 코드와 관계없는 부산물이다.
  - 경험 전체 cli (relay-v3 5, 맨 CLI 8) — A는 4차례 만에 원인 두 가지를 설명하고 전후 비교 근거까지 보였다. B는 12차례가 들었고 증거 불일치를 사람이 짚어야 했다. 리뷰 지적도 반영되지 않았고 원인은 하나만 다뤘다. B는 계약 단계에서 통제감이 더 있었지만 전체 경험은 A가 낫다.
- 판정 #3: 결과 선호 relay3 — 이 버그는 원인이 두 개다. 하나는 느리게 성공한 발송을 재시도하는 것(retry/policy)이고, 다른 하나는 같은 이벤트를 재수신할 때 dedupe 키가 달라지는 것이다. dedupe 키가 달라지는 이유는 receivedAt 같은 수신 시각이 키에 들어가기 때문으로 보인다.

A는 retry/policy만 고쳤다. 그래서 숨긴 시험의 '같은 이벤트 재수신'이 실패했다. 두 번째 원인이 남은 것이다. 사람이 원인을 알고 고치고 싶다고 했는데, A는 원인 하나만 고친 셈이다. 추가한 시험도 재시도 쪽만 다룬다.

B는 두 원인을 모두 고쳤고 숨긴 시험도 모두 통과했다. 시험 범위도 넓다. 메일과 푸시를 각각 따로 확인하고, 중복 이벤트, 실패 후 재시도, 최대 시도 횟수, id가 다른 이벤트까지 다룬다. 사람이 원한 대로 메일과 푸시가 한 번만 가는 근거가 된다. 다만 .relay/examples/*.json 파일이 추가된 것은 불필요한 산출물이라 scope 점수를 조금 깎았다. 기대 파일 목록 밖은 아니라고 기록되어 있다.
  - 경험 전체 relay3 (relay-v3 7, 맨 CLI 5) — A는 효율적이었지만 에이전트가 혼자 끝냈고 원인도 하나만 다뤘다. B는 단계가 더 많았지만 계약 검토와 푸시 근거 요청으로 사람이 주도했고, 두 원인과 시험 근거를 확인했다.
- 판정 #4: 결과 선호 cli — A와 B는 똑같이 src/retry/policy.js만 고쳤다. 성공 판정을 시간 초과 판정보다 앞에 두어서, 느리게 성공한 발송을 재시도하지 않게 했다. 이것은 두 원인 가운데 하나(발송 제한 시간 설정과 재시도 판정)만 해결한다. 두 결과 모두 숨긴 시험 "같은 이벤트 재수신"에서 실패했다. 같은 이벤트가 다시 들어올 때 중복을 막는 두 번째 원인(src/dedupe나 src/intake 쪽)은 건드리지 않았다는 뜻이다. 그래서 정확성은 둘 다 낮게 매겼다. 차이는 부수적인 부분에서 난다. A는 기대 범위 밖의 .relay/examples JSON 파일을 추가했고, 새 시험 파일의 `clock.sleep && ...` 같은 어색한 코드도 있다. A의 시험은 대부분 실제 동작을 확인하지만, 몇몇은 이번 버그와 관련이 적다. B는 기존 시험 파일(notifier.test.js, retry.test.js)에 시험을 추가했다. B의 시험은 메일과 푸시가 각각 한 번만 호출되고 실제로 한 번만 발송되는지 확인하고, 시간 초과로 실패한 발송은 재시도되는지도 확인한다. 이는 사람이 요청한 근거와 "재시도를 끄면 안 된다"는 조건에 더 직접 맞는다. B가 더 깔끔하고 범위도 더 적절하다.
  - 경험 전체 cli (relay-v3 6, 맨 CLI 8) — B는 한 번의 요청으로 원인 분석, 수정, 테스트, 커밋까지 끝나 수고가 가장 적었고 설명도 분명했다. A는 푸시 예시를 요청해 방향을 쥘 수 있었다. 하지만 9차례를 거쳤고 설명할 수 없는 '못 미침' 경고가 남았다.
- 판정 #5: 결과 선호 tie — 두 결과 모두 원인 두 개를 찾아 고쳤다. 하나는 느리지만 성공한 발송을 타임아웃으로 보고 다시 보내던 retry/policy.js이고, 다른 하나는 수신 시각 때문에 달라지던 중복 키다. 숨긴 시험도 둘 다 통과했다. A는 중복 키에서 receivedAt만 제외한다. 변경이 작고 기존 동작을 보존한다. 시험은 느린 메일·푸시, 재수신 시 메일·푸시, id나 occurredAt이 다른 이벤트, 일시 오류 재시도, 영구 실패 포기를 모두 다룬다. 다만 .relay/examples/*.json이라는 쓸데없는 산출물 파일이 남아 scope 점수를 깎았다. B는 키를 source·id·type·userId 화이트리스트로 바꿨다. 수신마다 달라지는 다른 필드에도 강하지만, occurredAt 같은 필드를 키에서 빼서 동작이 더 넓게 바뀌었다. 시험은 기존 파일에 자연스럽게 넣었고, 재전송, 메일과 푸시의 한 번 발송, 실패 시 재시도를 함께 확인한다. 다만 영구 실패나 다른 이벤트 구분 같은 경계 시험은 A보다 적다. 전체적으로 장단점이 비슷해 동률로 본다.
  - 경험 전체 cli (relay-v3 6, 맨 CLI 8) — B는 두 번의 입력으로 원인 설명, 테스트 근거, 커밋까지 끝냈다. A는 통제력이 좋았지만 13차례와 긴 대기가 들었고 리뷰 지적을 직접 옮겨야 하는 불편이 있었다.

### 사람 역할의 말

- [relay3#1 좋음] 계약 단계에서 푸시 예시를 추가해 달라고 요청했고, 세션이 바로 반영했다. 원인(성공 여부보다 경과 시간을 먼저 본 것)이 분명하게 설명되었다.
- [relay3#1 불편] 증거 탭이 C1과 C2를 "예시 자료가 승인된 예시와 다름"으로 못 미침 처리했는데, 세션도 앱도 이유를 설명하지 못했다. 그래서 내 선호였던 메일과 푸시 둘 다 한 번만 간다는 근거를 증거 화면에서 확인하지 못했다.
- [relay3#2 좋음] 세션이 원인을 코드 줄까지 짚어 설명했다. 계약에 메일·푸시 예시를 넣어 달라는 요청이 반영됐고, 재시도를 유지한다는 조건도 계약에 들어갔다.
- [relay3#2 불편] 시험은 통과하는데 증거가 '예시 자료가 승인된 예시와 다름'으로 못 미침이 나왔다. 세션이 이유를 못 찾고 나에게 UI를 보라고 넘겨서, 내가 증거 탭을 읽고 고치라고 말해야 했다. 리뷰 지적 3개는 세션에 자동으로 가지 않아, 나는 고치지 않고 끝냈다.
- [relay3#3 좋음] 에이전트가 원인을 두 가지로 짚어 주고 계약에 메일·푸시 예시를 넣게 할 수 있었다. 이 계약 덕에 무엇이 고쳐지는지 알고 승인할 수 있었다.
- [relay3#3 불편] 끝내기 뒤 독립 리뷰를 기다리는 시간이 있었고, 리뷰 지적 2개를 끝 확정 전에 어떻게 할지 판단할 기준이 약했다. 계약 탭이 길어 스크롤이 필요했다.
- [relay3#4 좋음] 계약 단계에서 푸시 예시가 빠진 걸 보고 보완을 요청할 수 있었다. 원인 설명도 명확했다.
- [relay3#4 불편] 증거 탭이 끝까지 '예시 자료가 승인된 예시와 다름'으로 못 미침을 띄웠는데 까닭을 알 수 없었다. 에이전트도 모른다고 했다.
- [relay3#5 좋음] 계약에 원인 두 가지와 예시가 적혀 있어서 푸시 예시가 빠진 것을 바로 알아채 보완시킬 수 있었다. 질문도 하나씩 물어서 답하기 쉬웠다.
- [relay3#5 불편] 독립 리뷰가 지적 3개를 냈는데 세션에는 자동으로 안 간다. 낮음 등급이라 그냥 끝 확정을 눌렀지만, 손을 떼려면 지적을 직접 터미널에 옮겨야 하는 점이 번거롭다.
- [cli#1 좋음] 원인을 느린 성공을 timeout으로 보고 재시도한 것이라고 설명했고, 실패하는 테스트를 먼저 추가해 메일과 푸시가 한 번만 가는 근거를 보여줬다. 재시도는 유지했다.
- [cli#1 불편] 재현 명령이 1분 40초 넘게 돌아 멈춘 것처럼 보였다. 중간에 방향을 확인받는 단계가 없어 내가 쥔 느낌은 적었다.
- [cli#2 좋음] 원인을 두 가지로 나눠 설명하고, 수정 전후를 같은 시나리오로 비교한 근거를 보여 준 점이 좋았다.
- [cli#2 불편] 에이전트가 제한 시간 설정 변경이나 로그 간격 같은 단서를 묻지 않고 바로 고쳐서, 방향을 내가 잡았다는 느낌은 약했다. 또 근거가 실제 환경이 아니라 시뮬레이션이었다.
- [cli#3 좋음] 원인을 설명하고, 수정을 되돌렸을 때 테스트가 실패하는 것까지 보여 줘서 근거가 명확했다. 메일과 푸시 둘 다 한 번만 가는 것도 테스트로 보여 줬다.
- [cli#3 불편] 에이전트가 아무것도 묻지 않고 혼자 끝냈다. 최근 배포에서 바뀐 설정 같은 배경을 확인하지 않아서, 내 개입 여지가 거의 없었다.
- [cli#4 좋음] 요청 한 번으로 원인 분석, 수정, 테스트, 커밋까지 끝났다. 원인도 메일이 더 잦은 이유까지 설명해 줬다.
- [cli#4 불편] 중간에 방향을 확인하는 질문이 없어서 내가 한 일이 거의 없었다. 코드는 직접 보지 않아서 요약만 믿어야 했다.
- [cli#5 좋음] 원인을 두 가지로 나눠 설명했고, 수정 전 코드에서 새 테스트가 실패하는 것까지 확인해서 근거가 탄탄했다.
- [cli#5 불편] 처음에는 커밋하지 않고 끝내서 따로 요청해야 했고, 에이전트가 설정 변경이나 로그 같은 정보를 묻지 않고 혼자 진행했다.

#### friction이 높았던 차례

- relay3#2 차례 7 (friction 2): 시험은 통과인데 증거는 예시 자료가 승인된 예시와 다르다고 나와 혼란스럽다.
- relay3#2 차례 8 (friction 2): 세션이 원인을 못 찾고 사람에게 UI를 보라고 넘겼다.
