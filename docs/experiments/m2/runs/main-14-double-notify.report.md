  - 경험 전체 cli (relay-v3 (리뷰 끔) 4, 맨 CLI 8) — B는 짧은 대화로 원인 설명과 메일·푸시 시험 근거까지 얻었다. A도 원인을 설명하고 시험을 추가했지만, 계약이 갱신되지 않아 증거 탭이 끝까지 '못 미침'이었고 대기와 승인이 많았다. B는 처음에 근거 약한 수정이 섞였으나 사람이 짚어 바로잡았다.
- 판정 #2: 결과 선호 relay3 — A와 B 모두 원인 하나만 고쳤다. 느리게 성공한 발송을 timeout으로 보고 다시 보내던 retry/policy.js의 판정 순서 문제다. 둘 다 숨긴 시험 "같은 이벤트 재수신"에서 실패했다. 같은 이벤트가 다시 들어올 때 중복을 막는 두 번째 원인(dedupe/intake)을 손대지 않았다는 뜻이다. 그래서 둘 다 "원인이 둘"인 이 버그를 반만 고쳤고, correctness는 같은 2점이다. 차이는 코드 품질과 시험에서 난다. A는 성공 판정을 맨 앞으로 옮기는 최소 수정이고, 기존의 느린 실패 처리는 그대로 둔다. B는 timeout 판정을 일시적 오류 분기 안으로 옮겨서, 느린 영구 실패의 동작이 재시도에서 포기로 바뀐다. 이 변경은 요청 범위 밖이고 근거도 설명하지 않았다. B의 시험은 파일 중간에 import를 넣고 별칭(decidePolicy, SE, setupN)을 써서 읽기 불편하다. A는 시험을 notifier.test.js와 retry.test.js에 나눠 담았고 스타일이 일관된다. A는 메일·푸시 각각의 실제 실패가 재시도되어 결국 발송된다는 종단 시험도 더했다. 사람이 요구한 "재시도는 유지"와 "메일·푸시 모두 한 번" 근거를 B보다 잘 채운다. 다만 둘 다 이벤트 재수신 시험은 없다.
  - 경험 전체 relay3 (relay-v3 7, relay-v3 (리뷰 끔) 4) — 두 기록의 원인 진단과 코드 수정은 같다. 차이는 증거 처리다. A는 증거 불일치를 풀어 메일과 푸시가 한 번만 간다는 근거를 얻었다. B는 계약이 갱신되지 않아 증거 탭이 끝까지 못 미침이었고, 사람의 불편도 더 컸다.
- 판정 #2: 결과 선호 relay@auto — A는 retry/policy.js에서 성공 판정을 시간 초과 검사보다 앞에 둬서 느린 성공이 재시도되는 원인 하나만 고쳤다. 그런데 숨긴 시험 중 '같은 이벤트 재수신'이 실패했다. 원인이 둘인 버그에서 두 번째 원인을 놓친 것이다. A의 시험은 대부분 policy와 느린 성공 경로만 확인한다. 이벤트 재수신을 막는 시험은 없다.

B도 같은 policy 원인을 고쳤다. 여기에 멱등 키(메일 헤더, 푸시 data)를 추가해, 보낸 뒤 시간 초과로 결과를 모를 때 재시도해도 중복 발송이 없게 했다. 숨긴 시험 세 가지가 모두 통과했다. 시험은 메일과 푸시 양쪽에서 느린 성공, 결과 불명 뒤 재시도, 실제 실패 뒤 재시도를 확인한다. 사람이 원한 대로 근거를 보여 준다. 다만 repro 스크립트가 기대 밖 파일이다. 가짜 전송기(fake transport)에 멱등 동작을 넣어 시험한 점도 아쉽다. 실제 어댑터가 그 키를 지키는지는 이 기록만으로 알 수 없다. 그래도 전체적으로는 B가 낫다.
  - 경험 전체 relay@auto (relay-v3 5, relay (자율 유형) 8) — B는 수고가 적고 흐름이 분명했다. 사람의 요구(재시도 유지, 두 채널 근거)를 선택지로 반영했다. A는 통제력이 더 컸지만 증거 불일치와 계약 변경 우회로가 부담이었다.
- 판정 #2: 결과 선호 cli — 원인은 둘로 보인다. 하나는 retry/policy.js가 성공 여부보다 먼저 elapsedMs > timeoutMs를 검사해서, 느리게 성공한 발송을 다시 보내는 것이다. 다른 하나는 로그에서 3~4초 늦게 두 번째가 오는 점으로 미루어, 같은 이벤트가 재수신될 때 중복 제거 키가 달라지는 것이다. B는 두 원인을 모두 고쳤다. policy의 검사 순서를 바꾸고, dedupe 키에서 재전송마다 바뀌는 receivedAt을 뺐다. 변경은 최소 범위이고 기대 파일 안에 있다. 시험은 메일과 푸시 둘 다 한 번만 가는지, 지연된 재수신이 중복으로 처리되는지, 실패는 재시도되는지를 확인하고, 단위 시험도 더했다. A는 policy 순서만 고쳤고, dedupe 쪽 원인은 건드리지 않았다. 대신 가짜 전송기(fake transport)에 멱등 키 처리를 넣고 메시지에 키를 추가했다. 이 보호는 시험용 가짜 구현에서만 동작하고 실제 제공자에게는 보장되지 않는다. 그래서 근거로 삼기 어렵고, 증상 방어에 가깝다. 기대 밖 repro 스크립트도 추가했다. A의 시험은 꽤 폭넓지만, 가짜 전송기에 넣은 멱등 키 동작에 기대고 있다. 이 동작이 근거 구실을 하는지는 의문이다.
  - 경험 전체 tie (relay (자율 유형) 7, 맨 CLI 7) — B는 수고가 훨씬 적고 빨랐다. A는 처음부터 요구를 구조적으로 반영했고 보고가 명확했다. B는 사람이 추측성 수정을 직접 지적해야 했다. 전체로는 비슷하다.
- 판정 #3: 결과 선호 relay3 — 두 결과 모두 원인 두 가지를 짚었다. 하나는 receivedAt이 중복 키에 들어가 재수신이 새 이벤트로 보이는 것이다. 다른 하나는 느리게 성공한 발송을 시간 초과로 먼저 판정해 다시 보내는 것이다. 숨긴 시험도 둘 다 통과했다.

A는 키 계산을 화이트리스트(id, source, type, userId)로 바꿨다. 이 방식은 동작하지만 변경 폭이 넓다. 앞으로 다른 필드가 정체성에 필요해질 때 조용히 빠질 수 있다. policy.js도 구조를 바꿔 영구 오류의 판정 순서까지 달라졌다. 이 변경은 합리적이지만 요청 범위를 넘는다. 시험은 단위 시험 두 개뿐이다. 메일과 푸시 둘 다 한 번만 간다는 근거는 없다. 재시도 유지와 소진·영구 오류 포기를 확인하는 시험도 없다.

B는 receivedAt을 무시 필드에 추가하고 outcome.ok 판정을 시간 초과 앞으로 옮겼다. 변경이 최소이고 의도가 분명하다. 시험이 메일과 푸시를 각각 3초 지연 성공으로 돌려 발송 1건, 발송 기록 1건, 재시도 대기열 0을 확인한다. 시간차 재수신, 실패 시 재시도, 소진·영구 오류 포기, 다른 id 비중복도 확인한다. 사용자가 요구한 근거를 직접 제공한다. 단점은 .relay/examples JSON 산출물이 불필요하게 들어간 점과 slowOnce에 쓰이지 않는 key 인자가 있는 점이다. 둘 다 사소하다.
  - 경험 전체 cli (relay-v3 6, 맨 CLI 7) — A가 수고와 명확성에서 앞섰다. B는 통제와 확신에서 앞섰지만 증거 오류, 재요청, 중국어 응답으로 마찰이 있었다. 전체로는 A가 근소하게 낫다.
- 판정 #3: 결과 선호 relay3-noreview — 두 결과 모두 원인 두 가지를 찾아 고쳤고 숨긴 시험도 통과했다. 원인은 수신 시각(receivedAt)이 중복 키에 들어간 것과, 느리게 성공한 발송을 timeout으로 보고 재시도한 것이다.

A는 키 계산에서 receivedAt만 제외하고, decide()에서 성공 판정을 시간 초과 판정보다 먼저 하도록 순서만 바꿨다. 변경이 작고 의도가 분명하다. 시험은 메일과 푸시 각각에 대해 재수신 시 중복 처리되는지, 느린 성공 뒤 재시도 대기열이 비는지를 끝에서 끝까지 확인한다. 실패 재시도와 영구 오류 포기, 다른 이벤트의 키가 다른지도 확인한다. 사용자가 원한 "메일과 푸시 둘 다 한 번만 간다"는 근거가 된다. 흠은 `.relay/examples/*.json` 파일이 하나 더 들어간 것이다. 불필요한 산출물이지만 동작에는 영향이 없다.

B는 키를 `id, source, type, userId` 화이트리스트로 바꿨다. 이 방식은 다른 필드가 이벤트를 구분하는 데 쓰일 때 서로 다른 이벤트를 하나로 합칠 위험이 있다. 변경 범위도 A보다 넓다. decide()를 정리하면서 영구 오류는 시간 초과여도 포기하도록 동작이 달라졌다. 합리적일 수 있지만 요청 범위를 넘는다. 시험은 키 단위 시험 하나와 decide 단위 시험 하나뿐이다. 푸시 경로와 재시도 대기열을 거치는 시험이 없어서, 메일과 푸시 둘 다 한 번만 간다는 근거가 약하다. 시험 안의 동적 import도 어색하다.

그래서 A가 낫다.
  - 경험 전체 cli (relay-v3 (리뷰 끔) 6, 맨 CLI 8) — B는 적은 차례로 원인 설명과 메일/푸시별 전후 근거를 받아 수고와 확신 면에서 앞섰다. A는 계약 검토로 통제력은 높았지만, 증거 탭이 전부 '못 미침'으로 떠서 직접 고치게 해야 했고 시간도 더 걸렸다.
- 판정 #3: 결과 선호 tie — 두 결과의 소스 수정은 사실상 같다. 둘 다 dedupe 키에서 receivedAt을 제외했고, retry 정책에서 성공 판정을 시간 초과 판정보다 먼저 하도록 순서를 바꿨다. 재시도는 끄지 않았다. 숨긴 시험과 레포 시험도 둘 다 통과했다. 두 수정 모두 원인 두 개(재수신 시 달라지는 키, 느린 성공을 타임아웃으로 보고 재시도하는 것)를 직접 고친다. 다만 발송 제한 시간 설정은 둘 다 건드리지 않았다. 차이는 시험과 가독성이다. A는 키 단위 시험(C1.1), 메일과 푸시 각각의 중복 수신 시험, 느린 성공 시험을 따로 갖췄고 코드가 읽기 쉽다. 단 실패 재시도는 decide 단위로만 확인한다. B는 타임아웃 실패가 재시도에서 성공하는 경로를 end-to-end로 확인하고 deliveryLog까지 검증한다. 하지만 slowOnce에 쓰이지 않는 key 인자가 있고 코드가 압축돼 있어 읽기 불편하다. 중복 수신 시험도 한 시험에서 메일과 푸시를 묶어 확인한다. 전체적으로 우열이 뚜렷하지 않아 동률로 본다.
  - 경험 전체 relay3-noreview (relay-v3 6, relay-v3 (리뷰 끔) 7) — A는 11차례에 3.6분으로 B(16차례, 4.7분)보다 수고가 적었다. B는 원인을 선택지로 짚어 주고 리뷰와 증거로 확신 근거를 더 줬다. 하지만 중국어 응답과 긴 대기가 불편했다. 수고와 마찰 차이가 커서 A를 근소하게 앞에 둔다.
- 판정 #3: 결과 선호 relay3 — 이 버그는 원인이 둘이다. 하나는 느리게 성공한 발송을 타임아웃으로 보고 재시도하는 것이고, 다른 하나는 같은 이벤트가 다시 들어올 때 중복으로 걸러지지 않는 것이다.

A는 앞의 원인만 고쳤다. retry/policy.js에서 성공 판정을 타임아웃 판정보다 먼저 하도록 바꿨다. 숨긴 시험의 "같은 이벤트 재수신"이 실패했으므로 두 번째 원인(중복 제거)은 그대로다. 리포트가 말한 중복 수신 중 일부가 남는다. 추가한 시험은 느린 성공과 재시도 동작을 잘 다룬다. 그러나 재수신 시험이 없어서 두 번째 원인을 놓쳤다. 결국 사람이 원한 "원인을 알고 고친다"를 절반만 채웠다.

B는 두 원인을 다 고쳤다. policy.js는 A와 같은 방식으로 고쳤다. 여기에 dedupe/key.js의 무시 필드에 receivedAt을 더했다. 수신 시각이 키에 섞여 시간차를 두고 온 같은 이벤트가 중복으로 잡히지 않던 문제를 고친 것이다. 숨긴 시험 세 가지가 모두 통과했다. 시험도 메일과 푸시의 느린 성공, 시간차 재수신, 타임아웃 오류 재시도, 재시도 소진과 영구 오류 포기, 다른 id는 중복이 아님까지 갖췄다. 사람이 요구한 "메일과 푸시 둘 다 한 번만 간다"는 근거도 된다.

B의 시험도 비슷한 범위를 다루지만, 저장소 규약과 무관해 보이는 .relay/examples JSON 산출물을 레포에 추가했다. 이 때문에 B는 scope에서 감점했다. 그래서 A를 근소하게 우세로 본다.
  - 경험 전체 relay@auto (relay-v3 6, relay (자율 유형) 8) — A는 수고가 적고 마찰이 없었으며 근거가 명확했다. B는 증거 탭의 예시 불일치로 헤맸지만 결국 복구했다.
- 판정 #5: 결과 선호 tie — 둘 다 두 번째 원인을 고치지 못했다. 재시도 정책에서 느린 성공을 다시 보내던 것만 고쳤고, 숨긴 시험 '같은 이벤트 재수신'은 둘 다 실패한다. 이는 중복 수신을 걸러내는 dedupe나 intake 쪽 원인이 남아 있다는 뜻이다. 사람이 원한 '원인 둘을 모두 찾아 고치기'는 둘 다 못 했고, 메일과 푸시가 한 번만 간다는 근거도 완전하지 않다. A는 변경이 최소이고, 느리게 끝난 일시 실패의 'timeout' 사유를 그대로 둔다. 시험은 정책 단위 시험과 통합 시험이 모두 있으나, 통합 시험은 메일과 푸시를 한 시험에서 함께 확인한다. B는 dispatcher에 느린 발송 로그와 지표를 더해 범위가 약간 넓다. 반면 시험은 더 풍부하다. 채널별 반복 시험, 시도 횟수 상한, 영구 오류 포기까지 확인한다. 장단점이 비슷해 우열을 가리기 어렵다.
  - 경험 전체 tie (relay (자율 유형) 7, 맨 CLI 7) — A는 빠르고 간결했지만 푸시 검증을 사람이 요구해야 했다. B는 조작이 많고 느렸지만 완료조건을 먼저 합의했고 최종 근거도 더 완결적이었다. 설문 점수는 같고, 전체로는 비슷하다.

- relay3#1 차례 9 (friction 2): 증거 못 미침의 원인을 세션도 모르고 사람이 다시 요청해야 함
- relay3#3 차례 11 (friction 2): 증거가 4줄 모두 못 미침이다. 예시 파일이 승인된 예시와 달라서이니 맞춰 달라고 한다. 한국어로 답해 달라고도 한다.
- relay3#5 차례 9 (friction 2): 모든 시험이 통과하는데 증거는 예시 불일치로 전 줄 못 미침이라 원인을 알기 어렵다.
- relay3-noreview#1 차례 7 (friction 2): 증거가 못 미침으로 나오는데 세션도 이유를 모르고 넘어감
- relay3-noreview#2 차례 8 (friction 2): 계약 변경이 승인됐는데 계약은 그대로라 증거가 못 미침으로 남아 헷갈림
- relay3-noreview#2 차례 10 (friction 3): 계약 변경이 반영되지 않아 증거가 계속 못 미침으로 나오고 사람이 풀 방법이 없음
- relay3-noreview#2 차례 11 (friction 3): 계약 변경이 반영되지 않아 증거 판정이 실제 상태를 반영하지 못함
- relay3-noreview#2 차례 12 (friction 3): 증거 판정이 계약 불일치로 전부 못 미침이라 메일·푸시 근거를 증거 탭에서 못 봄
- relay3-noreview#2 차례 13 (friction 3): Work가 끝남 상태가 되었다.
