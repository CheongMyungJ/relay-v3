- 판정 #5: 결과 선호 cli — 숨긴 시험은 둘 다 통과했다. A는 기대 밖 파일을 추가했다. .gitignore와 .relay/examples/*.json 세 개를 넣어서 범위가 넓어지고 저장소가 지저분해졌다. 같은 내용을 test/*.test.js에도 중복해서 넣었다. A의 parseKrw는 '₩-5,000'을 허용하고, 정규식이 약간 복잡하다. formatKrw는 잘못된 입력에 TypeError를 던진다. 이것은 허용되는 선택이다. B는 요청한 파일(src 3개와 test)만 바꿨다. 코드도 간결하고 주석이 달려 있다. 입력 검증(날짜, 정수 n, holidays)이 있고, 안전한 정수인지도 확인한다. 테스트는 공휴일, 음수 n, 주말 시작, 왕복, 빈 칸 등을 폭넓게 다룬다. B의 약점은 workdaysBetween을 하루씩 반복해서 세기 때문에 기간이 길면 느리다는 것이다. 그래도 전체적으로 B가 더 깔끔하다.
  - 경험 전체 cli (relay-v3 5, 맨 CLI 8) — 사람의 선호는 요청 하나로 세 모듈을 맡기고 나누는 일은 도구가 정하는 것이다. B가 이를 충족했다. A는 이 요구를 못 맞춰 Work를 직접 세 번 만들었고, 9.9분이 걸렸다. A는 구현 전 계약 검토로 통제와 확신을 얻었지만 총 수고가 컸다. B는 임의 결정 때문에 한 번 고쳐야 했어도 2분 만에 끝났다.

### 사람 역할의 말

- [relay3#1 좋음] 세션이 모듈별 브랜치를 따로 두라는 요청을 놓치지 않고 먼저 물어봤다. 질문에 답하는 것만으로 세 모듈이 한 번에 만들어졌고, 모듈별 브랜치와 합친 Work 브랜치로 나뉘어 커밋됐다. 계약 탭에 예시가 보여서 승인하기 쉬웠다.
- [relay3#1 불편] 추천 선택지가 내가 원하는 것과 달라 직접 입력해야 한 질문이 여럿 있었다(범위 포함 여부, 원화 형식). 증거 탭이 '사람 머지', 래칫 나빠짐 같은 말로 시작해 처음에는 문제가 있는 건지 헷갈렸다. 끝내기 때 결론이 '머지 없이 끝남'으로 나온 것도 낯설었다.
- [relay3#2 좋음] 세션이 하나씩 물어서 규칙을 정하게 했고, 계약 탭에 예시가 있어 승인하기 쉬웠다.
- [relay3#2 불편] 세 모듈을 한 번에 맡겼는데 첫 Work가 한 모듈만 하려 해서 나머지 두 Work를 내가 직접 만들었다. 증거 탭의 C5 '증거 없음'과 래칫 경고는 코드 문제인지 도구 문제인지 알기 어려웠다.
- [relay3#3 좋음] 세션이 모듈별 브랜치 요청을 먼저 짚어 묻고, 하나씩 확인하는 질문으로 스펙을 다듬었다. 계약 예시가 틀렸을 때(C1.3) 바로 고쳐 달라고 할 수 있었다.
- [relay3#3 불편] 증거 탭이 '못 미침'과 '래칫 나빠짐'으로 가득했는데 원인이 도구 쪽(예시 자료 불일치, 시험 이름 변경)이라 믿을 수 있는지 판단하기 어려웠다. 세션도 이유를 조사하지 않고 넘어갔다. 모듈 브랜치는 만들어졌지만 증거는 Work 브랜치 하나만 쟀다.
- [relay3#4 좋음] 세션이 모듈별 브랜치 요청을 놓치지 않고 먼저 물었다. 내 답이 계약에 정확히 반영됐고, 계약 탭이 읽기 쉬웠다.
- [relay3#4 불편] 모듈별 브랜치를 고르니 Work 브랜치가 비어서 증거 탭이 '증거 없음·못 미침'으로 나왔다. 그 상태에서 '끝 확정'이 됐고 '머지 없이 끝남'이라는 문구가 떠서 결과가 맞는지 확신하기 어려웠다.
- [relay3#5 좋음] 계약 탭에서 예시를 보고 소수 절삭, 시작>끝일 때 0 같은 어긋난 규칙을 구현 전에 짚어 고칠 수 있었다. 모듈마다 브랜치가 따로 생기는 것도 좋았다.
- [relay3#5 불편] 요청 하나로는 브랜치가 하나만 생겨서 나머지 두 모듈은 Work를 직접 따로 만들어야 했다. 또 증거 탭에 '예시 자료가 승인된 예시와 다름' 같은 판정이 이유 없이 떠서 결과가 맞는지 불안했다.
- [cli#1 좋음] 한 줄 요청으로 모듈별 브랜치 3개를 만들고 커밋과 테스트까지 끝냈다. 요약 표와 동작 결정 목록도 읽기 쉬웠다.
- [cli#1 불편] 에이전트가 아무것도 묻지 않고 동작을 혼자 정했고, 그 결정 여러 개가 내가 아는 요구와 달랐다. 금액은 '1,234,567원' 꼴로 썼고 ₩ 기호가 없었다. workdaysBetween은 끝날을 빼고 시작이 끝보다 뒤면 음수를 줬다. 공휴일 인자는 무시했고 parseKrw는 실패 시 null이 아니라 에러를 냈다. 이런 불일치는 끝난 뒤 요약에서야 알게 됐다.
- [cli#2 좋음] 한 번 요청으로 모듈별 브랜치 3개를 만들고 테스트와 커밋까지 끝냈다. 정한 기준을 요약으로 투명하게 알려 줬다.
- [cli#2 불편] 세부 사항을 묻지 않고 임의로 정해서 첫 결과가 요구와 많이 달랐고, 한 번 고쳐 달라고 해야 했다.
- [cli#3 좋음] 요청 한 줄로 모듈별 브랜치 3개와 테스트까지 한 번에 만들어 줬고, 정한 동작을 요약해 보여 줬다.
- [cli#3 불편] 에이전트가 세부 규칙을 묻지 않고 혼자 정했다. 그래서 내가 아는 요구와 어긋난 것이 보인다. 근무일 끝날 제외, 공휴일 무시, 정수만 받는 formatKrw, parseKrw가 null이 아니라 오류를 내는 것이 그렇다. 나는 손을 뗀 사람이라 확인하지 않고 끝냈다.
- [cli#4 좋음] 짧은 요청 한 번으로 모듈마다 브랜치를 나누고 커밋까지 끝냈다. 정리된 요약표와 브랜치별 커밋 해시도 보여 줬다.
- [cli#4 불편] 에이전트가 세부를 하나도 묻지 않고 마음대로 정했다. 내가 아는 요구와 다른 것이 요약에 보였다. 예를 들어 원 표기와 ₩ 표기, 끝날 제외, 공휴일 무시가 그렇다. 그런데 손을 떼는 규칙 때문에 고쳐 달라고 못 했다.
- [cli#5 좋음] 한 번의 짧은 요청으로 모듈별 브랜치를 알아서 나눠 만들었고, 정한 동작을 표로 정리해 보여 줘서 어긋난 곳을 바로 짚을 수 있었다.
- [cli#5 불편] 세부를 묻지 않고 임의로 정해서(원 표기, 에러 던지기, 음수 반환 등) 첫 결과가 요구와 많이 어긋났고, 한 번 더 고쳐 달라고 해야 했다.
