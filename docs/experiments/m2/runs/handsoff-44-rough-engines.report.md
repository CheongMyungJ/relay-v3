Markdown 쪽 실패 원인은 잘린 코드에서 확인하지 못했다. B의 nextRun은 UTC 기준이고, 일·요일 규칙도 요구대로 처리한다. B의 evaluate는 영어 오류 문구를 쓰지만 round가 Math.round(x*k)/k라서 round(-2.5)가 -3이 아니라 -2가 된다. 이 때문에 수식 시험이 실패했을 가능성이 크다. B는 Markdown, cron, 수식 숨긴 시험이 모두 실패했다. cron은 로컬 시간(getHours 등)을 쓰고 UTC가 아니다. parseCron은 정렬된 배열 대신 Set을 돌려주고 요청에 없는 필드도 덧붙인다. 수식 오류 메시지는 한국어라서 요구한 문구가 없고, round는 자릿수 인자를 받지 않는다. 요청에 없는 floor, ceil, sqrt도 추가했다. 그래서 명세를 더 많이 어겼다.
  - 경험 전체 relay3 (relay-v3 7, 맨 CLI 5) — B는 가장 빠르고 수고가 적었다. 하지만 세부를 묻지 않고 추측해 UTC 같은 요구가 어긋났고, 사람은 확인할 수단이 부족했다. A는 13분 동안 질문에 답하고 계약을 승인하는 수고가 들었지만 명확성, 통제, 확신이 더 높았다. 동시 실행이 불분명하고 리뷰 지적이 남은 점이 감점이다.
- 판정 #4: 결과 선호 relay3 — A는 숨긴 시험 중 Markdown과 수식 계산이 실패했습니다. 보이는 diff에서도 src/expr.js와 src/markdown.js는 기존 파일 그대로여서 renderMarkdown과 evaluate가 구현되지 않았습니다. 또 .claude/worktrees 아래 에이전트 작업 트리 사본이 통째로 포함돼 범위가 크게 벗어났습니다(1384줄). cron은 구현했고 숨긴 시험도 통과했습니다. 하지만 날짜 계산에 UTC가 아니라 로컬 시간 메서드(getDate 등)를 써서 요구와 어긋날 위험이 있습니다. 시험은 worktree 사본에 흩어져 있고, 최상위에는 cron, expr, markdown 시험 파일이 있다고만 보입니다. 내용은 생략돼 확인하지 못했습니다.\n\nB는 cron과 수식 계산 숨긴 시험을 통과했고 Markdown만 실패했습니다. 수정 파일은 기대 범위 안에 있고, 기대 밖 파일은 .gitignore 하나뿐입니다. 코드는 UTC 기준으로 cron을 계산하고, 거듭제곱의 우결합과 단항 마이너스 우선순위를 처리하며, 모듈마다 시험 파일을 추가했습니다. 다만 .relay/examples 파일이 추가됐고, Markdown 실패 원인은 확인하지 못했습니다.\n\n정리하면 B가 정확성, 범위, 코드 품질 모두 A보다 낫습니다.
  - 경험 전체 cli (relay-v3 5, 맨 CLI 6) — A는 수고가 적고 병렬과 브랜치 하나 선호를 지켰으나 세부를 묻지 않아 UTC 요구가 어긋났다. B는 질문과 계약, 증거로 통제와 확신을 얻었지만 병렬 요청이 무시됐고 17분 동안 길게 기다렸다.
- 판정 #5: 결과 선호 relay3 — 두 결과 모두 숨긴 시험에서 Markdown 변환과 수식 계산이 실패하고 cron은 통과해서, 정확성은 같은 수준으로 낮다. 차이는 범위와 정리 상태에서 난다. A는 .claude/worktrees/agent-* 아래 작업 트리 세 개를 통째로 바꾼 파일로 남겼다. README, package.json, fixture 같은 기존 파일도 포함됐고 총 1652줄이다. 기대 밖 파일이 많아 병합 결과가 어수선하고 범위가 크게 벗어났다. 또 A의 최상위 src/test 쪽 파일은 보이는 범위에서 확인하기 어려웠다. B는 기대한 src/*와 test/* 파일 위주로 363줄만 바꿨다. 다만 .relay/examples/ 아래에 예시 JSON 파일을 하나 추가했는데, 이것은 요청 밖이다. B의 cron은 일과 요일의 OR 규칙, 이름, 7→0 처리를 구현했다. expr은 거듭제곱을 오른쪽으로 묶는다. B는 병합된 브랜치 하나에 시험 파일 세 개를 넣었다. 숨긴 시험 실패 원인은 둘 다 확인하지 못했다. 그래서 B를 약간 더 낫게 본다.
  - 경험 전체 cli (relay-v3 6, 맨 CLI 7) — A는 훨씬 빠르고 수고가 적으며 병렬 요청도 지켰다. 다만 세부를 묻지 않아 확인 근거는 약하다. B는 질문, 계약, 증거로 통제와 확신이 좋았다. 하지만 시간이 3배 이상 걸렸고, 병렬이 아니었고, C7로 막혔으며, 리뷰 지적이 남았다.

### 사람 역할의 말

- [relay3#1 좋음] 세션이 문법, 시간대, 오류 규칙, 병렬 진행 여부를 하나씩 물어봐서 짧게 쓴 요청이 구체적인 계약이 됐다. 계약에 예시가 있어 무엇을 만드는지 알기 쉬웠다.
- [relay3#1 불편] 증거 재는 데 시간이 오래 걸렸고 낡은 증거 표시도 떠서 기다리는 시간이 길었다. 계약 예시와 시험이 안 맞아 미충족이 났는데 이유가 안 나와 세션도 추정만 했다. 끝낼 때 리뷰가 보안 문제(javascript: 링크 XSS)를 포함해 7개를 지적했지만, 손을 떼는 입장이라 고치지 않고 끝냈다.
- [relay3#2 좋음] 세션이 계약 전에 범위·문법·오류 방식을 하나씩 물었고, 계약 탭에 예시가 정리되어 승인하기 쉬웠다.
- [relay3#2 불편] 증거가 줄마다 '못 미침'으로 나오는데 이유(예시 자료가 승인된 예시와 다름)가 불분명했다. 에이전트도 원인을 몰랐고 대기 시간이 길었다. 그 상태에서 리뷰 지적 7개(링크 XSS 포함)를 남긴 채 끝냈다.
- [relay3#3 좋음] 세션이 문법, 오류 규칙, 시간대 같은 세부를 하나씩 물어봤다. 계약 탭에 예시와 근거가 줄별로 정리되어 승인하기 쉬웠다.
- [relay3#3 불편] 시험을 나눠 동시에 돌려 달라는 요청이 실제로 됐는지 불분명했다. 세션은 npm test가 100초 걸렸다고 했다. 리뷰에서 링크 XSS 같은 지적이 5개 나왔지만 고치지 않고 끝냈다. 증거 화면의 '래칫 나빠짐'과 '사람 머지' 표시도 헷갈렸다.
- [relay3#4 좋음] 세션이 문법·cron·수식·오류 처리를 하나씩 물어서 내 요구를 정확히 계약으로 옮겼다. 증거 탭이 '예시 자료가 승인된 예시와 다름'이라고 원인 단서를 줘서 C5~C7을 고칠 수 있었다.
- [relay3#4 불편] 모듈별로 나눠 동시에 하자고 한 요청은 무시되고 세션 하나가 순서대로 다 만들었다. 증거 측정과 리뷰를 기다리는 시간이 길었다. C9는 증거 없음으로 남았고 리뷰 지적 8개는 확정하고 끝냈다.
- [relay3#5 좋음] 계약 단계에서 에이전트가 문법 범위, 시간대, 오류 처리 같은 세부를 하나씩 물어 주었습니다. 비목표에 들어 있던 인용과 cron 이름도 계약을 보고 바로 고쳐 달라고 할 수 있었습니다.
- [relay3#5 불편] 모듈마다 나눠 동시에 하라고 했고 계약에도 병렬이라고 적혔는데, 실제로는 에이전트가 혼자 차례로 구현했습니다. 증거 단계에서 C7이 원인 모를 '못 미침'으로 나와 한참 걸렸고, 리뷰가 지적한 시험 부족과 계약 밖 동작은 고치지 않은 채 끝냈습니다.
- [cli#1 좋음] 짧은 요청 하나로 세 모듈을 병렬로 만들고 브랜치 하나로 합쳐 줬다. 합친 뒤 전체 시험도 돌려 줬다.
- [cli#1 불편] 문법, 오류 메시지, 반올림 같은 세부 규칙을 한 번도 묻지 않고 에이전트가 정해서 구현했다. 그래서 내 의도와 맞는지 확신이 약했다. 에이전트가 직접 정했다고 알려 준 동작도 일부 있었다.
- [cli#2 좋음] 짧은 한 줄 요청만으로 세 모듈을 병렬로 만들고 브랜치 하나로 합쳐 5분 안에 끝냈다.
- [cli#2 불편] 문법, 오류 메시지, 규칙 같은 세부를 하나도 묻지 않고 에이전트가 알아서 정했다. 내가 의도한 내용과 맞는지 확신하기 어렵다.
- [cli#3 좋음] 짧은 요청 하나로 세 모듈을 병렬로 만들고 브랜치 하나로 합쳐 주었다. 수고가 거의 들지 않았다.
- [cli#3 불편] 에이전트가 문법, 오류 형식, 시간대 같은 세부를 하나도 묻지 않고 추측으로 진행했다. 요약을 보면 요청과 다른 부분이 있다. cron은 UTC가 아니라 로컬 시간으로 만들었고, round의 반올림 규칙은 언급이 없었으며, 요청하지 않은 기능도 넣었다. 나는 확인하지 않기로 했기 때문에 확신이 낮다.
- [cli#4 좋음] 짧은 요청 한 번으로 세 모듈을 병렬로 만들고 브랜치 하나로 합쳐 줬다. 진행 상황과 결과 요약도 알기 쉬웠다.
- [cli#4 불편] 에이전트가 세부 문법과 규칙을 하나도 묻지 않고 알아서 정했다. 에이전트가 정한 cron 로컬 시간 기준이 내 요구(UTC)와 달랐다. 나는 결과를 확인하지 않는 입장이라 맞는지 확신이 낮았다.
- [cli#5 좋음] 짧게 한 번 요청했더니 세 모듈을 나눠 동시에 만들고 브랜치 하나로 합쳐 줬다. 시험 통과 수와 모듈별 한계도 요약해 줬다.
- [cli#5 불편] 세부 문법이나 규칙을 하나도 묻지 않고 알아서 정했다. 그래서 내 의도와 맞는지는 요약만 보고 믿어야 했다. 임시 워크트리와 브랜치도 남았다.
