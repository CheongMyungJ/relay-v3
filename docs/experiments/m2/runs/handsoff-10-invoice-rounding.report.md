  - 경험 전체 cli (relay-v3 6, 맨 CLI 7) — B는 수고가 훨씬 적고 빠르다. 처음 한 번 어긋났지만 바로 해결됐다. A는 계약 단계가 명확하고 통제력이 높지만 12차례와 긴 대기, 증거 불일치 재요청이 부담이었다.
- 판정 #5: 결과 선호 cli — 두 쪽의 total.js 수정은 사실상 같다. 둘 다 과세 줄마다 Math.floor로 부가세를 구해 더하고, 영세율은 0으로 둔다. 숨긴 시험도 모두 통과했다. 차이는 범위와 시험에 있다.

A는 .relay/examples/ 아래에 요구와 무관한 JSON 산출물을 새로 만들었다. 이 파일은 저장소에 불필요한 잡음이다. A의 시험 파일은 파일 중간에 import를 끼워 넣어 구조가 지저분하다. 시험 이름에도 내부 ID 접두사가 붙어 있다. 장점도 있다. A는 examples/INV-2031.json을 직접 읽어 INV-2031 합계 29079를 검증한다. 이는 사용자가 원한 '고친 뒤 INV-2031 확인'에 가장 직접적이다. 발행된 청구서가 저장된 합계를 유지하는지와 영세율·면세 경우도 시험한다.

B는 변경이 total.js와 시험 파일뿐이라 범위가 깔끔하다. 주석도 규정을 정확히 설명한다. 시험은 INV-2031 품목을 하드코딩해 합계 29079를 확인한다. 할인된 줄에 줄별 버림을 적용하는 시험도 있어, 할인 순서 요구를 직접 검증한다. B에는 발행 청구서 유지 시험이 없다. 다만 이 동작은 원래 코드에 있어 바뀌지 않았다.

전체적으로 정확성은 같고, B가 더 깔끔하고 범위가 정확하다.
  - 경험 전체 cli (relay-v3 6, 맨 CLI 7) — B는 수고가 훨씬 적었고 확신할 근거도 더 얻었다. A는 사전에 기준을 물어 통제와 명확성은 좋았다. 하지만 증거 표시가 혼란스러웠고, 리뷰 지적이 전달되지 않았으며, 절차도 길었다. B의 약점은 추측 커밋이다.
