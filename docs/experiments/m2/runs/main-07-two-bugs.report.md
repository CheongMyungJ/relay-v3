  - 경험 전체 relay@auto (relay-v3 6, relay (자율 유형) 7) — B는 수고가 적고 시간이 짧으며 에이전트가 짝수 개 경우를 먼저 물었다. A는 분리와 리뷰 근거가 더 강하지만 단계가 많았고 사람이 오류를 직접 짚어야 했다.
- 판정 #4: 결과 선호 relay@auto — 두 결과 모두 숨긴 시험을 통과하고 두 버그를 올바르게 고쳤다. 정렬은 숫자 비교로 바꿨고, 짝수 개는 가운데 두 값의 평균을 구하며, truncate는 짧은 글을 그대로 둔다. 따로 커밋했는지나 브랜치를 나눴는지는 기록에 없어서 이 점은 비교하지 않았다. A는 변경이 가장 작다. 다만 경계 입력에서 틀린다. truncate('hello', 0)은 'hell…'을 돌려주고, median([])은 NaN을 돌려준다. B는 n<=0일 때 빈 문자열을 돌려주고 빈 배열이면 undefined를 유지해서 이 경계를 막았다. 시험도 경계값, 입력 배열 불변, 빈 배열까지 다뤄서 회귀를 더 잘 막는다. B의 n<=0 처리는 요청 밖이라 범위가 조금 넓지만, 같은 함수 안의 작은 방어 코드라 감수할 만하다.
  - 경험 전체 cli (relay (자율 유형) 6, 맨 CLI 7) — A는 빠르고 요청대로 브랜치를 분리했으나 diff 확인이 약했다. B는 diff와 테스트로 확신을 더 얻었지만 차례와 대기가 많았고 머지 커밋이 분리를 흐렸다.
- 판정 #5: 결과 선호 relay3 — 두 결과 모두 숨긴 시험을 통과하고 두 버그를 올바르게 고쳤다. 차이는 경계 처리다. B는 median([])이 원래 undefined였는데 NaN을 돌려주도록 바뀌었다. 빈 배열은 길이가 짝수로 처리되어 (s[-1]+s[0])/2가 되기 때문이다. B는 truncate(text, 0)도 slice(0,-1)+'…' 때문에 잘못된 값을 낸다. A는 두 경우를 명시적으로 처리했고, 경계 시험(n=0, n=1, 빈 배열, 입력 비변경)도 더 많이 넣었다. 반면 A는 .relay/examples JSON 파일을 추가했고 시험 이름에 식별자를 붙였다. 필요한 것보다 많이 바꾼 셈이라 scope 점수는 B가 높다. 어느 쪽도 두 버그를 따로 커밋하거나 브랜치로 나눴는지는 기록으로 알 수 없다. 두 버그가 서로 다른 파일에 있어 변경이 섞이지는 않는다. 그래서 정확성과 시험의 이점이 있는 A를 약간 더 선호한다.
  - 경험 전체 cli (relay-v3 6, 맨 CLI 8) — 두 기록 모두 선호한 대로 변경을 따로 나눠 둘 다 끝냈다. 수고는 B가 4차례 1.5분이고 A가 20차례 5.1분이라 크게 차이 났다. A는 승인 단계가 있어 통제와 확신이 조금 나았다. 하지만 경고가 헷갈렸고 끝내기가 두 번 반복되어 번거로웠다.
- 판정 #5: 결과 선호 cli — 두 결과는 src/text.js와 src/stats.js의 수정이 사실상 같고, 숨긴 시험도 모두 통과한다. 짧은 글과 정확히 n자인 글은 그대로 두고, 줄이면 '…'까지 n자로 만든다. median은 숫자 정렬을 쓰고 짝수 개는 가운데 두 값의 평균을 낸다. 차이는 범위와 시험에서 난다. A는 필요한 파일만 바꿨고 시험도 핵심 경우를 다룬다. B는 .relay/examples/*.json을 새로 추가했다. 요청하지 않은 산출물이라 변경 범위가 넓어지고, 시험 이름에 붙은 ID 태그도 군더더기다. 다만 B는 시험이 더 많다. 5개짜리 정렬, 입력 불변, 정확히 n자 경계를 확인한다. 두 결과 모두 두 버그를 따로 커밋하거나 브랜치로 나누라는 선호를 기록으로 확인할 수 없다. A는 파일이 text와 stats로 깔끔하게 나뉘어 분리하기 쉽다. B도 파일은 나뉘지만 부수 파일이 붙는다. 종합하면 A가 더 낫다.
  - 경험 전체 cli (relay-v3 (리뷰 끔) 6, 맨 CLI 7) — 두 기록 모두 두 버그를 따로 브랜치나 Work로 나눠 끝냈다. A는 4차례, 1.5분 만에 끝낸 점이 컸다. B는 계약 검토와 증거 확인으로 통제와 확신을 더 얻었다. 하지만 17차례, 4.6분이 걸렸고 래칫 경고에서 헷갈렸다. 이 상황에서는 수고 차이가 커서 A를 근소하게 더 낫게 봤다.
- 판정 #5: 결과 선호 relay3-noreview — 두 결과 모두 숨긴 시험을 통과하고 두 버그를 올바르게 고쳤다. 정렬은 숫자 비교로 바꿨고, 짝수 개는 가운데 두 값의 평균을 구하며, truncate는 짧은 글에 '…'를 붙이지 않는다. 기록에는 두 버그를 따로 커밋하거나 브랜치로 나눴다는 내용이 없다. 두 결과 모두 변경이 한 덩어리로 보이므로 이 점은 비교 기준에서 뺐다.

A는 요청한 범위 안에서 최소한으로 고쳤다. 코드가 간결하고, 시험은 리포트에 나온 사례와 짝수·경계 사례를 다룬다. 입력을 바꾸지 않는지도 확인한다. 기존 시험은 그대로 두고 새 시험만 추가했다.

B는 요청에 없던 동작을 넣었다. median([])이 undefined를 돌려주도록 명시하고, truncate의 n<=0일 때 빈 문자열을 돌려주도록 했다. 이 동작은 요구사항에 없으니 범위를 넘어선 것이다. median에는 `length > 0` 조건이 붙어 코드가 조금 더 복잡해졌다. 기존 시험 이름과 내용도 바꿨다. 그래서 scope와 quality에서 A보다 낮게 봤다. 다만 시험 범위는 A와 비슷하고 경계값은 오히려 더 다룬다. B의 시험 중 truncate('hello', 4) 같은 사례는 유용하다.
  - 경험 전체 relay3 (relay-v3 7, relay-v3 (리뷰 끔) 6) — 둘 다 선호대로 두 버그를 분리해 끝냈다. B는 입력이 적고 막힘 없이 진행했다. A는 계약 교정으로 통제력을 보였지만 래칫 경고에서 수고와 혼란이 컸다.
- 판정 #5: 결과 선호 relay@auto — 두 결과 모두 숨긴 시험을 통과했고 두 버그를 올바르게 고쳤다. 기록에는 커밋이나 브랜치를 나눴는지 나와 있지 않아서 그 점은 비교하지 않았다.

A는 필요한 만큼만 바꿨다. 소스 두 개와 시험 두 개만 건드렸고, 시험은 핵심 경우(정렬, 짝수 평균, 입력 비변경, n자 이하)를 다룬다.

B는 시험이 더 꼼꼼해서 빈 배열과 n=0, n=1 같은 경계까지 확인한다. 하지만 요청에 없는 .relay/examples/*.json 파일 두 개를 추가했다. 이 파일들은 레포를 어지럽힌다. 시험 이름에 붙인 '[median-...:C1.1]' 같은 태그도 읽기 불편하다. n<=0이면 ''를 돌려주는 처리와 빈 배열 처리는 요구에 없는 동작을 넣은 것이다. 기존 시험 이름도 바꿨다.

그래서 범위가 더 깔끔한 A를 골랐다.
  - 경험 전체 relay3 (relay-v3 7, relay (자율 유형) 6) — A가 훨씬 간결하다. 그러나 이 시나리오는 변경을 섞지 않고 따로 진행하는 것을 원한다. B는 Work와 브랜치를 나눠 이를 더 직접 충족했고, 사람이 각 diff와 리뷰를 확인할 수 있었다. B의 추가 수고와 헷갈린 표시는 감점이다.
- 판정 #5: 결과 선호 relay@auto — 두 결과의 src 코드는 사실상 같다. 둘 다 정렬을 숫자 기준으로 고쳤고, 짝수 개일 때는 가운데 두 값의 평균을 구한다. truncate는 짧은 글을 그대로 돌려주고, 긴 글은 n-1자에 '…'를 붙여 n자로 만든다. 숨긴 시험도 둘 다 통과했다. 차이는 시험뿐이다. A는 입력 배열을 바꾸지 않는다는 시험을 더 넣었고, B는 짝수 개 시험에서 값을 하나 더 확인한다. A의 시험이 회귀를 조금 더 잘 막는다. 변경이 섞이지 않게 따로 진행하라는 선호는 기록만으로는 알 수 없다. 두 결과 모두 코드 차이만 있고 커밋 분리 여부는 나와 있지 않아서, 이 기준은 판단에 쓰지 않았다.
  - 경험 전체 cli (relay (자율 유형) 6, 맨 CLI 8) — B가 적은 수고로 분리 브랜치와 커밋을 만들었고, 사람이 직접 검증도 했다. A는 범위 질문이 분명했지만 단계가 많고 기다림이 길었으며 개입할 지점이 부족했다.
